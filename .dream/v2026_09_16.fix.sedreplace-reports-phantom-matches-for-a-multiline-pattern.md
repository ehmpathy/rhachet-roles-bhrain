# 🌙 dream: `sedreplace` reports phantom matches for a multiline pattern

- **kind** = fix
- **owner** = `ehmpathy/rhachet-roles-ehmpathy`
- **caught** = 2026-09-16

## .the cue that fired

i reached for `sedreplace` to swap a 3-line expression across 5 files — the paved path for a
bulk rename (`rule.prefer.sedreplace-for-renames`). the plan came back wrong in a way that was
loud enough to catch and quiet enough to have applied:

```
├─ old:         const lines = result.stderr
          .split('\n')
          .filter((l) => l.includes('pours') || l.match(/^\s+[├└]─ r\d+:/));
├─ new:         const lines = getAllPourAnnounceLines(result.stderr);
├─ glob: blackbox/*.acceptance.test.ts
├─ files: 8
├─ matches: 29
```

**the true count is 5, in 4 files.** and the preview named files with no such expression in them
at all (`driver.route.journey`, `driver.route.passage-gitignore`), with diff hunks that showed
their IMPORT blocks:

```
├─ blackbox/driver.route.journey.acceptance.test.ts (1)
│  ├─
│  │  -import * as fs from 'fs/promises';
│  │  -import * as path from 'path';
```

a second attempt with a narrower 3-line pattern returned **49 matches across 5 files** — a larger
count for a stricter pattern, which cannot be right.

## .the gap, precisely

`sedreplace` accepts a multiline pattern via `@stdin` and its `--help` documents that shape:

> `--old @stdin alone: reads entire stdin (allows newlines in pattern)`

⇒ so a multiline pattern is **advertised**, and the match it performs is not the match it
advertises. the preview and the count both describe some other operation.

**checkable evidence:** the two plan runs above, on this branch. a stricter pattern returned a
count 1.7× larger than the looser one, and both named files the pattern does not occur in.

🔴 **the hazard is that plan mode is the guardrail.** the whole reason `sedreplace` demands a plan
before `--mode apply` is that a bulk edit is hard to unpick. a plan whose count and preview are
both wrong does not merely fail to help — it is a guardrail that reports a state the apply will
not produce, which is worse than an absent one.

⚠️ **and the diff preview is what makes it dangerous rather than merely broken.** it renders
plausible removed lines from the head of each file, so a reader who skims it sees a normal-shaped
diff. i caught this only because i knew the true match count independently.

## .the shape of the fix

one of two, and the choice belongs to whoever owns the skill:

1. **make the multiline match real** — if `sedreplace` shells out to `sed`, a multiline pattern
   needs `-z` (NUL-separated) or a `perl -0777` equivalent. the per-line default cannot see a
   pattern that spans lines, and the current code appears to match per-line and then report a
   count against the whole pattern
2. 🔴 **or refuse it loudly**, which is cheaper and honest — if the pattern contains a newline,
   throw at parse:

```
🐢 bummer dude — a multiline pattern is not supported

  why: sedreplace matches per line, so a pattern that spans lines matches no line
  fix: pass a single-line pattern, or edit the files directly
```

⇒ option 2 is the one i would take first. an absent feature costs a fallback; a feature that
reports a wrong count costs a corrupted tree.

either way the `--help` text must stop to advertise `allows newlines in pattern` until the first
option lands.

## .why it is not done in this round

- **SAFE:** no. it is another repo's skill, and a change to the bulk-edit primitive touches every
  caller in the org
- **CLEAN:** no. it lands in `ehmpathy/rhachet-roles-ehmpathy`, never in this stone's deliverable
- **the immediate need was met** — the 5 sites were edited by hand, and the round lost only the
  two plan runs
