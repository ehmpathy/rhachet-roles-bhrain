# 🌙 dream: `keyrack firewall` passes a declared-but-absent key, so CI fails late and per suite

**kind** = reseed · **owner** = `ehmpathy/rhachet` · **caught** 2026-10-03

## .the cue that fired

vision case 4 of the openrouter cutover owes *"one red step, not forty"* when a maintainer pushes
before the actions secret exists. the CI credential step is `keyrack firewall`, so its behavior on an
absent key decides the case.

## .the gap, precisely

measured on rhachet 1.48.1, pinned by `blackbox/keyrack.firewall-key-absent.acceptance.test.ts`:

```sh
echo '{}' | npx rhachet keyrack firewall --env test --from 'json(stdin://*)' --into json
# every declared key → { status: absent, fix: rhx keyrack set --key <KEY> --env test }
# exit=0
```

the report names the key and the fix, which is good. but the step exits 0, so the workflow goes on,
and each suite that reaches a brain fails on its own. the maintainer reads N red suites where one red
step was available — and only a blocked key sets exit 2 today.

## .the shape of the fix

in `keyrack firewall`, treat a **declared** key reported `absent` as a halt:

1. exit 2 after the report, with one `✋ ConstraintError` header that lists each absent key and the
   grant that fills it (an actions secret, in CI)
2. keep the full report first, so every absent key is named in the one run
3. an escape for a manifest that declares a key a given job never reads — e.g. a per-key `optional`
   mark in `keyrack.yml` — so the halt does not punish an unused declaration

then, in `rhachet-roles-bhrain`, flip the pinned `toEqual(0)` in the acceptance test above to `2`.

## .why it is not done in this round

- **not clean** — the firewall lives in `rhachet`, and its exit semantics reach every repo in the
  fleet that shares the declapract workflow
- a bespoke check step in this repo's `.test.yml` would drift from the shared template
