- kind  = fix
- owner = `ehmpathy/rhachet-roles-bhrain`

## .the cue that fired

peer reviewer `arch-hazards-behavior` (r007, nitpick.1), on `5.1.execution.from_vision`:

> *"`stepRouteDrive` now reads `getDriveBlockerState` to compute `entered`, then calls
> `setDriveBlockerState` (which re-reads and rewrites the same file). the read and the write are not
> atomic … the duplicate dispatch is currently benign because the applier is idempotent (converge),
> so this is a latent hazard rather than an active defect … any future non-idempotent work placed
> behind the same `entered` flag would double-fire."*

## .the gap, precisely

🔴 **.amended 2026-09-14 (i010 r011)** — the inline pattern this dream first quoted no longer exists.
the read-modify-write was extracted into `applyStoneBrainOnEntry` (`brain/applyStoneBrainOnEntry.ts`),
which now reads `getDriveBlockerState`, compares the stone, and writes via `setDriveEntryStone` (a
dedicated SECOND writer, distinct from `setDriveBlockerState`'s count increment). the race is the same
in KIND — a non-atomic read-then-write of `.drive.blockers.latest.json`, now from two writers that both
route through `mutateDriveBlockerState`. the CURRENT shape:

```ts
// applyStoneBrainOnEntry.ts
const stateBefore = await getState({ route: input.route });
const entered = stateBefore.stone !== input.stone.name;
if (!input.dispatchAlways && !entered) return { outcome: 'none' };
const outcome = await setBrain({ guard: input.stone.guard, route: input.route });
await setEntry({ route: input.route, stone: input.stone.name }); // setDriveEntryStone
return outcome;
```

the original inline shape (for the record):

```ts
const stateBefore = await getDriveBlockerState({ route });
const entered = stateBefore.stone !== stone.name;
const { state } = await setDriveBlockerState({ route, stone: stone.name });
const brained = entered
  ? await setStoneBrain({ guard: stone.guard ?? null, route })
  : ({ outcome: 'none' } as const);
```

two concurrent hook invocations on one bound route can each read the same `stateBefore.stone`, so
each computes `entered === true` for the same stone. the consequences today:

| effect | its grade today |
|---|---|
| a duplicate `/model` dispatch | **benign** — the applier is convergent (F14), and a re-run changes the engine, never the session |
| a lost count increment | latent — the 21-block cutoff drifts by one under a race nobody has observed |

⇒ **the window pre-dates this feature.** `setDriveBlockerState` already read-then-wrote; what this
change added is a second reader of the same value.

## .the shape of the fix

🔴 **.amended 2026-09-14 (i010 r011)** — both writers now route through
`mutateDriveBlockerState({ route, project })`, which reads-modifies-writes in ONE place. that is the
single choke point the atomicity fix lands at: an atomic rename (write to a temp path, then
`fs.rename`) or a per-route lock added inside `mutateDriveBlockerState` closes the window for BOTH
writers at once, with no caller change.

⇒ the entry-detection read (`applyStoneBrainOnEntry`) is still a separate read ahead of the write, so
a fuller fix has `mutateDriveBlockerState`'s `project` return whether the stone changed and threads
that back — but the cheap, high-value step is the atomic write at the one choke point, which the
extraction now makes a single-site change rather than a two-site one.

the reviewer's original words (for the record): *"have `setDriveBlockerState` return whether the stone
changed instead of a separate pre-read."* — still valid in spirit; the return now rides
`mutateDriveBlockerState` rather than `setDriveBlockerState` directly.

🟡 **and it pairs with a second latent defect in the same operation**, caught separately:
`.dream/v2026_09_09.fix.drive-blocker-count-never-resets-on-stone-change.md`. both are repairs to
`setDriveBlockerState`'s contract, and both are cheaper done together than apart.

## .why it is not done in this round

**SAFE — no. CLEAN — no.**

- **safe** — `setDriveBlockerState` is a shared engine operation with callers outside this feature's
  reach. a change to its return shape touches the drive's blocker-count path, which the 21-block
  cutoff and the stop-hook both depend on
- **clean** — it ripples into a file this wish opened for one three-line insertion. the diff already
  spans 9 files and 11 blockers; a contract change to the engine's state writer is a second feature
  riding along, which `rule.always.fix-forward-under-scouts-honor`'s CLEAN question refuses

⇒ **and the reviewer's own grade agrees**: a nitpick, *"a latent hazard rather than an active
defect"*, because the one act placed behind the flag is idempotent by ruling (F14).

⚠️ the condition that would make it urgent is named in the reviewer's own words: **any future
non-idempotent work placed behind the same `entered` flag**. that is the trigger to pick this up.
