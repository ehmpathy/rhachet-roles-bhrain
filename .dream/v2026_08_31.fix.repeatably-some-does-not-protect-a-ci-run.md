# 🌙 dream: `when.repeatably` + `criteria: 'SOME'` does not protect a CI run

**kind**: fix · **owner**: this repo (`rhachet-roles-bhrain`) · **caught** 2026-08-31

## .the cue that fired

a release run failed on `blackbox/review.refs-single.acceptance.test.ts`. its attempt table:

| attempt | verdict | duration |
|---|---|---|
| 1 | ✓ all four assertions | 1047 ms |
| 2 | ✓ all four assertions | 1019 ms |
| 3 | ✕ all four assertions | 1004 ms |

**two of three attempts passed, and the suite still exited 1.**

## .the gap, precisely

`rule.require.repeatable-for-llm-tests` declares the contract:

```ts
const REPEATABLE_CONFIG = { attempts: 3, criteria: process.env.CI ? 'SOME' : 'EVERY' } as const;
```

| criteria | the stated semantics |
|---|---|
| `'SOME'` | pass if **ANY** attempt succeeds — what CI selects |
| `'EVERY'` | pass if **ALL** attempts succeed — what local selects |

⇒ under `'SOME'`, attempt 1 alone is a pass. jest reported `Tests: 4 failed, 8 passed, 12 total`
and exited 1 anyway.

🔴 **the arithmetic is the tell: 12 = 4 assertions × 3 attempts.** each attempt is emitted as its
own jest `when` block, so **jest counts the attempts as independent test cases** and its exit code
is a plain count of failures. the `SOME` criterion is applied — if at all — somewhere jest's tally
never reads.

## 🔴 .why it is worth more than one flaky suite

**every LLM test in this repo leans on this config.** the whole reason `when.repeatably` exists is
that a probabilistic call fails sometimes and the suite should not. if `SOME` does not reach jest's
exit code, then:

- **the retry buys latency and no protection** — 3× the tokens, 3× the time, same failure rate
- **`EVERY` and `SOME` behave identically in CI**, so the `process.env.CI` branch is a decoration
- 🟡 and it fails in the direction that looks like diligence. a run that retries and still fails
  reads as *"we tried three times, it is a real defect"* — the exact opposite of what happened

## 🟡 .a second defect rode in with it — the error is masked

all four failures print the same line:

```
UnexpectedCodePathError: useThen: tried to access value before test ran
    at Object.get (test-fns/src/domain.operations/useThen.ts:31:15)
    at cli (blackbox/review.refs-single.acceptance.test.ts:75:20)
```

line 75 is `expect(res.cli.stderr)…` — **the proxy getter, never the throw site.** the `useThen`
body threw, the proxy swallowed it, and every downstream `then` reports the proxy's complaint
instead of the cause.

⇒ **attempt 3's real error is unreadable from the log.** a genuine defect and a transient flake
present identically, which is `rule.forbid.failhide` at the harness layer — and it is why this
dream can say only *that* attempt 3 failed, never *why*.

## .the shape of the fix

two separable repairs, and the first is the one that pays:

1. **make the criterion reach the exit code.** either collapse the attempts into ONE jest case that
   internally loops (so jest counts one pass), or have the harness mark the failed attempts
   `skipped` once a peer attempt succeeded. **the invariant to hold: under `SOME`, one attempt that
   succeeds ⇒ jest exits 0**
2. **surface the cause through the proxy.** when a `useThen` body throws, downstream accesses should
   re-throw the **original** error, with the proxy's message as context — never in place of it

🟡 write the clamp before the fix (`rule.require.clamp-edge-cases`): a test where attempt 1
succeeds and attempt 3 throws, asserted to exit 0. it must go red under today's harness.

## .why it is not fixed in this round

the wish's bound is **briefs only — no skills, no code**. a change to the repeatable harness is
code, and it reaches every LLM test in the repo. it landed mid-release with the tree verified green
otherwise, and **a change that alters which suites pass is not a change to slip in beside a ship**
(`rule.always.fix-forward-under-scouts-honor`).

## .the fulcrum

> **a retry that cannot change the verdict is not a retry — it is three times the cost for one
> attempt's protection, and it wears the appearance of diligence.**
> rework: **dirty** — the harness governs every LLM test, so the blast radius is the whole suite.

## 🔴 .occurrence 2 — 2026-09-22, and it lands on the OPPOSITE attempt

confirmed on `rhachet-roles-bhrain` @ `beav/feat-review-cost-meter`, stone `5.1`, on the i022 gate
sweep. `blackbox/review.by.guard-peer.acceptance.test.ts`, `[case-seam-pass-aggregation]`:

| attempt | verdict |
|---|---|
| 1 | ✕ two snapshot assertions |
| 2 | ✓ all five |
| 3 | ✓ all five — and it short-circuited at **1 ms**, so `SOME` DID apply |

🔴 **and the suite still exited 2.** attempt 3's 1 ms proves the criterion was evaluated and the
harness stopped early; jest's counter had already recorded attempt 1's two failures.

⇒ **so the criterion reaches the RUNNER and does not reach the EXIT CODE**, which is sharper than
occurrence 1 could state — that one could not tell whether `SOME` was applied at all.

### 🟡 the failure POSITION varies and the outcome does not

| | attempt 1 | attempt 2 | attempt 3 | exit |
|---|---|---|---|---|
| occurrence 1 (2026-08-31) | ✓ | ✓ | ✕ | 1 |
| occurrence 2 (2026-09-22) | ✕ | ✓ | ✓ | 2 |

⇒ **any single failed attempt reds the run, wherever it falls.** with 3 attempts and a per-attempt
failure rate `p`, the suite's real failure rate is `1 − (1−p)³` — the retry makes a flaky suite
**three times more likely to red**, which is the exact inverse of its purpose.

### what flaked, and why it is a clean read this time

occurrence 1 could say only *that* attempt 3 failed — the `useThen` proxy masked the cause. here
the cause is fully legible, and it is the honest kind:

> the fixture is `code is clean` and the snapshot expects `approved · 0 blockers`. attempt 1's
> **live reviewer raised 1 blocker on clean code**. every other line of the 20-line diff is tree
> render downstream of `rejected` rather than `approved`.

⇒ a genuine false positive by a probabilistic reviewer — **precisely what `when.repeatably` exists
to absorb**, and it was not absorbed.

### 🔴 the second-order cost this occurrence measured

a driver mid-round cannot part this from a regression without work, and the work is not small:

- the run before it was **3,661 passed / 0 failed**; this one **3,657 / 4**
- a re-run of the same file gave **2 failed**, in a *different* case — the count itself varies
- ⇒ the only clean proof available was a **logical** one: attempts 2 and 3 produced
  snapshot-identical output under the same code, so the code is deterministic across attempts and
  the brain is not

🟡 **that proof is available only because `SOME` kept the later attempts.** under `EVERY` the run
would have stopped and a driver would have had a red suite, a changed diff, and no way to tell
which caused it. so the harness half that works is what rescued the half that does not.

⇒ the clamp `rule.require.clamp-edge-cases` asks for is now writable from a **measured** shape
rather than a hypothesized one: *attempt 1 fails, attempt 2 passes, assert exit 0.*

## 🔴 .occurrence 3 — 2026-09-22, and it exposed a SECOND defect the flake had hidden

same branch, `5.3.verification`. `blackbox/review.by.learner.acceptance.test.ts`, `[case-all]`:

| attempt | verdict |
|---|---|
| 1 | ✓ all four |
| 2 | ✓ all four |
| 3 | ✕ `then: exit 0` — received **2**, expected 0 |

🔴 **the suite exited 2 on 3,665 passed / 1 failed.** the position matches occurrence 1 (the
third attempt), the cause matches occurrence 2 (a live reviewer raised a blocker on a `clean.ts`
fixture). so the class is confirmed a third time and the arithmetic stands.

### 🟡 what is NEW, and it is the most valuable result this occurrence bought

attempt 3 printed **three green assertions beside the red one**:

```
✓ then: both rubrics run and pass (32526 ms)
✕ then: exit 0 (3 ms)
✓ then: BOTH rubrics appear in the tree, each with a pass mark (1 ms)
```

⇒ at first read that looks like a CONTRADICTION — three assertions say the review passed and the
exit code says it did not. it is not a contradiction. **both green lines were failhide:**

| the line | what it claimed | what it asserted |
|---|---|---|
| `useThen('both rubrics run and pass')` | a pass | **naught.** the body only invokes the cli and returns |
| `then('… each with a pass mark')` | a mark **per rubric** | `toContain('✓')` — and a REJECTED row renders `0 nitpicks ✓` too |

🔴 **so an assertion strictly weaker than its own label sat green through a real rejection**, and
it would have sat green through a genuine regression just as happily. `toContain('✓')` could not
tell an approval from a rejection at all.

⇒ repaired in place: the label now says what the body proves, and the assertion checks the mark
per rubric (`r1 term-application ✓` / `r2 term-aggregation ✓`, the `genReviewByStdout` render).
**proven red** by a swap to `✗` — 11 passed / 1 failed — which is the property the old assertion
never had.

### 🔴 why this belongs in THIS dream rather than its own

because the flake is what surfaced it. a suite that goes red for a brain's false positive drags a
human into the attempt table, and the attempt table is the only place those two green lines sit
beside the red one where anyone would read them together.

⇒ **so the harness defect has a second-order benefit nobody would design for, and it does not pay
for itself**: three occurrences, one masked failhide found. the fix this dream asks for stands.
