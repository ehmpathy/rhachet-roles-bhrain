## .the cue that fired

a rebase left twelve modify/delete conflicts. the settlement was to honor the delete, so the files
were removed with `rmsafe` and then handed to the paved stage skill:

```
$ rhx git.stage.add .dream/<twelve files>
🐢 hold up dude...
🐚 git.stage.add
   └─ error: file not found: .dream/v2026_08_14.reseed.kind-coordinate-over-bracket-markers.md
```

⚠️ **the file was not found because it had just been deleted, which was the point.**

## .the gap, precisely

`git.stage.add` guards its inputs with an existence check, and a deletion is the one stage operation
whose input does not exist by definition. `git add <deleted-path>` stages a removal — that is plain
git behavior — so the guard rejects a call git itself accepts.

**the consequence is a hole in the pavement, never merely an error.** three routine acts have no
paved form:

| the act | what a caller must reach for |
|---|---|
| stage a file removal | raw `git rm` or `git add` |
| settle a modify/delete rebase conflict as a delete | raw `git rm` |
| commit a `rmsafe` prune | raw `git add` |

⇒ and none of those is in the pre-approved set, so each one interrupts the caller for permission on
an operation the skill exists to make routine. **a guard that forces a drop to raw git has inverted
its own purpose**, which is the `rule.require.pitofsuccess` shape at the tool grain.

⚠️ **the error also misleads.** *"file not found"* reads as a typo or a bad path, so a caller's first
move is to re-check the spelling of a path that is perfectly correct. it names the symptom and not
the cause, against `rule.require.errors-name-the-fix`.

## .the shape of the fix

the existence check has one legitimate job — catch a typo — and it can keep that job while it stops
rejecting a deletion. **the discriminator is git, never the filesystem:**

- a path absent from disk **and** untracked by git = a typo → keep the current throw
- a path absent from disk **and** tracked by git as deleted = a removal → stage it

`git ls-files --error-unmatch <path>` answers that in one call, or `git status --porcelain <path>`
returns a ` D` / `D ` code for exactly this case.

⚠️ **fail-fast must be preserved on the mixed batch.** the skill already promises *"if any file not
found, entire operation fails"* — that promise should hold against the new predicate rather than be
relaxed, so a batch of eleven deletions plus one typo still fails whole.

## .why it is not done in this round

the skill is published by a peer repo, and this round is a guard fix in `rhachet-roles-bhrain`. the
change is small and well-scoped, and it is not this tree's to make.
