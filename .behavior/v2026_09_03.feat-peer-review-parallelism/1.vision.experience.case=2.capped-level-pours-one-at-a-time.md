# case=2 — the capped level pours one at a time

**cell** — `driver × multi-cap-1 × all-fresh × happy`
**feel · care** — happy · **critipath**

⚠️ these `[tn]` sketches are illustrative, not proof. no code exists yet.

## .the narrative — the driver's pov

level 3 is where the expensive brains live. three reviewers sit there, all behind the same rate
limited provider, and the provider permits one heavy call in flight per key.

if level 3 fanned out like level 1, i would not get a fast level. i would get three calls, two
429s, and two lanes that return `malfunction`. then i would spend my next twenty minutes on
`rule.always.diagnose-reviewer-malfunctions`, read the stderr, find a rate limit, and conclude
that a reviewer i never touched is broken. the fan-out would not have made level 3 fast — it would
have made it *wrong*, and it would have made the wrongness look like somebody else's defect.

so the guard declares `concurrency: 1` at level 3. i run `--as arrived`. level 1 fans out to four
and clears in 52 seconds. level 3 then runs its three, strictly one at a time, and takes the sum
of the three — and that is correct, because the sum is what the provider permits.

the aha: **the bound is not a limitation on the feature; it is what makes the feature safe to
turn on.** a level that cannot take the pour says so, and is obeyed.

## .the bdd sketch

```gherkin
given [case1] a guard that declares level 1 with no cap and level 3 with `concurrency: 1`
  and level 1 holds four reviewers
  and level 3 holds three reviewers, each of which records its own start and end

when [t0] the driver runs `--as arrived` and level 1 clears

then [t1] level 3 begins
  and at every instant exactly one level-3 reviewer is in flight
  and no level-3 reviewer's in-flight window overlaps another's
  and level 1 still fanned out to four — the cap at 3 does not leak upward or downward
```

## .the clamp this owes (acceptance 4 + 7)

```gherkin
given [case1] a level that declares `concurrency: 1` and holds three reviewers
when  [t0] the level executes
then  the observed max-in-flight count at that level is exactly 1
```

⇒ **prove it bites**: raise the cap to 3, re-run — max-in-flight reads 3, test goes red. restore
`1`, re-run — 1, green.

🔴 **an overlap assertion, never a duration assertion.** *"it took about as long as the sum"* is
satisfiable by a scheduler that merely happens to be slow. the wish asks for *provable*
serialization, so the test must record each reviewer's in-flight window and assert that no two
windows intersect. that is the difference between "likely serial" and "serial".

## 🔴 .the fixture this clamp requires — found in self-review r3, and it is a TOOTH problem

⚠️ **with the extant mock, this clamp does not bite.** verified:
`blackbox/.test/assets/route-peer-budget-parallel-l1/.test/mock-review-alpha.sh` is `echo`-only and
returns in milliseconds.

⇒ so a lane finishes before its co-member is spawned, and **the windows do not intersect even when
the cap is broken and three run at once.** the assertion reads green under both arms. per
`rule.require.clamp-edge-cases`, *"a clamp that passes under the un-fixed defect (no teeth) =
blocker"* — and a clamp with no teeth *"reads as protection while it guards naught."*

**repaired: the mock must DELAY.** the pattern is extant in this repo, not coined —
`blackbox/.test/assets/route-peer-review-timeout/.test/mock-review-timeout.sh:14` is a `sleep`-based mock authored to make
a duration observable. a ~200ms delay makes a broken cap's overlap unmistakable while 20 runs stay
seconds.

⚠️ **this is a fixture requirement, never an implementation one.** it changes what the test asset
holds, not what the feature does — which is why it belongs in the clamp section rather than the
narrative.
