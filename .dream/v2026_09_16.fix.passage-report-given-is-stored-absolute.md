# 🌙 dream: `PassageReport.given` is stored as an absolute, machine-specific path

kind: fix
owner: driver
caught: 2026-09-16

## .the cue that fired

the wisher asked for the `given` field in `passage.jsonl` disputed/conceded rows to be a
relative path. two example rows showed `given` as a full absolute path
(`/home/camper/git/ehmpathy/_worktrees/.../​.reviews/peer/...md`) beside a `fulcrum` field that
was already relative (`.fulcrums/inventory.of=fulcrums.case=F047-...md`).

## .the gap, precisely

`PassageReport.given` is written from `given.pathGiven` in
`src/domain.operations/route/stones/setStoneAsConcernAbsorbed.ts:262`. that value originates in
`getAllRouteGuardReviewPeerGivens.ts:82` (`pathGiven: givenPath`), which comes from
`enumRouteGuardReviewPeerFiles` → `enumRouteFiles` → `enumFilesFromGlob`
(`src/utils/enumFilesFromGlob.ts:15`), which calls `globby(..., { absolute: true })` **by
design** — every other consumer of this utility across the route/guard system relies on getting
back absolute, cwd-independent paths.

`fulcrum` looks relative only because `assertFulcrumPathExists.ts` documents (and the code
honors) that the fulcrum path is **stored verbatim as the driver typed it** — never re-derived.
it happened to be typed relative by convention (`.fulcrums/inventory.of=fulcrums.case=F0NN-...md`
is the canonical form `assertFulcrumPathExists.ts`'s own error text recommends). `given` has no
equivalent "stored verbatim" escape hatch — it is always derived from the absolute source.

## 🔴 why this is NOT a small fix — `pathGiven` is a comparison key, not just data

`PassageReport.given` is compared, by exact string equality, against a **freshly recomputed**
`given.pathGiven` on every future round, in the entrance-gate's own predicate:

- `getStoneUndeclaredConcerns.ts` → `computeUndeclaredConcernLabels.ts:49`
  (`one.given === input.pathGiven`)
- `getStoneReviewAbsorptions.ts:116` (`getAbsorptionOnConcern`:
  `stance.given === input.given`)
- `assertAbsorptionIsNotContrary.ts` (R3, the contrary-stance refusal) — same key

if the STORED value is relativized without also relativizing the value it's compared against on
every future read, every stance ever declared on a stone would stop matching, and the entrance
gate would read every already-disputed/conceded concern as **undeclared again** — silently
re-blocking a stone that already passed (this route's own stone `5.1.execution.from_vision`
among them).

the comment at `getAllRouteGuardReviewPeerGivens.ts` and `setStoneAsPassed.ts:130-134` /
`runStoneGuardReviews.ts:308-311` both already carry the intended target: *"paths in output
should be relative to git root ... not route"* — so gitroot-relative is the established
convention this fix should converge on; the gap is that `pathGiven` never actually reaches it.

## .the shape of the fix

1. relativize `pathGiven` **at its source** — `getAllRouteGuardReviewPeerGivens.ts`, using
   `path.relative(repoRoot, givenPath)` (repoRoot via `getRepoRootWithFallback`), so every
   consumer across the whole peer-review guard subsystem receives an already-relative,
   internally-consistent identity — not a patch applied at one write site
2. check `getAllRouteGuardReviewPeerTakenMetas.ts` for an independent absolute-path computation
   on the taken side, since `getRouteGuardReviewPeerPathTaken({ pathGiven })` derives the taken
   path by string substitution on `pathGiven` — it must stay internally consistent (relative in,
   relative out) with however the taken side computes its own comparison path
3. audit every direct `fs.readFile`/`fs.access` call site that currently relies on `pathGiven`
   (or a path derived from it) being reachable from the **process** cwd rather than repoRoot —
   confirm `rhx` always runs from repoRoot in practice, or add an explicit lookup step before
   the read
4. add a regression test that clamps this specific failure mode: a stance declared, then a
   **second** round on the same stone, asserting the concern still reads as declared (not
   resurrected) — this is the test that would have caught the bug in the first place
5. re-run the FULL suite (unit/integration/acceptance) afterward — many snapshots across the
   route/guard domain assert on rendered paths and will likely need `--resnap` after the format
   changes system-wide, not just within this feature's tests

## .why it is not done in this round

**not safe, not clean** by the SAFE/CLEAN test
(`rule.always.fix-forward-under-scouts-honor`): it touches the entrance-gate's core comparison
predicate for the whole peer-review guard subsystem, repo-wide, for every route — not scoped to
this feature. attempting it hastily, deep inside an already-long verification pass on an
unrelated feature, risked a silent regression to a system every route in the org depends on.
surfaced to the wisher for a scope decision rather than acted on unilaterally.
