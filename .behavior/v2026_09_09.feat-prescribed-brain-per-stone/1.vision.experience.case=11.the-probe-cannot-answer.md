# case 11 — the-probe-cannot-answer

**actor** = driver-clone · **feel** = sharp · **care** = critipath
**cell** = `driver-clone × apply × {other-known, other-unknown, same-as-live} × {live, deaf}` —
the probe-malfunction region under the two reach values that assumed a clean read

> 🔴 **found at peer review r5 (verification), against the shipped implementation.**
> `StoneBrainHaltCause` (`src/domain.operations/route/brain/StoneBrainHaltCause.ts`) names seven
> reasons a switch was never dispatched. `case=2` demos one — `unenrolled`, the clean rejection
> (**F-a**, exit 2). the other six were never itemized nor demoed.

## .the six causes, and why they are ONE family and not six cases

each names a different point where the two-step sequence — `clone whoami`, then `clone say` — can
fail to confirm or land the switch, **without the clean, typed rejection `case=2` walks**:

| cause | which step | what actually happened |
|---|---|---|
| `killed` | the probe | `clone whoami` died by a SIGNAL, not an exit code — an oom killer, a ci cap, a supervisor |
| `timed-out` | the probe | `clone whoami` was still alive at its 2s cap and was killed by the cap itself |
| `unreadable-clone` | the probe | the probe did not answer, or failed for a reason this build does not read |
| `unreadable-address` | the probe | the probe answered cleanly and its payload held no address this build can use |
| `unreadable-payload` | the probe | the probe exited 0 and wrote bytes that are not JSON at all |
| `spawn-failed` | 🔴 the dispatch | the probe DID confirm an address — the `clone say` child that carries `/model` never launched |

⇒ **five are probe (`clone whoami`) failures; one is a dispatch (`clone say`) failure that happens
AFTER a successful probe.** `spawn-failed` is the one cause of the seven whose `outcome` and
`cause` fields agree (`StoneBrainHaltCause.ts:36-40`) — every other cause describes a failed
clone probe; this one describes a failed clone command.

**why one case, not six**: all seven causes render through the same `formatStoneBrainUndispatched`
halt shape — a stone halt, naming what was prescribed, what is unknown, why, and a runnable fix.
`case=2` already demos that shape once. what this case adds is the property `case=2` alone cannot
show: **the fix line DIFFERS by cause**, and a build that collapsed them into one generic "could
not confirm" message would repeat `case=4`'s exact harm — a reader handed the wrong remedy for the
failure they actually hit.

## .the narrative

i am the driver, mid-route, entering `5.3.verification`. its guard prescribes `claude-opus-5[1m]`.
i am enrolled — `rhx enroll` gave me an address hours ago, and every stone before this one switched
cleanly. this is not `case=2`.

i run the probe:

```
$ rhx clone whoami --output json
```

and this time it does not answer with a clean rejection or a clean address. it dies mid-flight,
carried off by something outside my control — an oom killer reaping the heaviest process on a
loaded box, a ci runner enforcing its own cap, a supervisor that decided i had run too long. node
reports this as `code === null`: no exit code at all, because there was no orderly exit to report.

**the tempting read is to fold this into `unreadable-clone` — "the probe could not be read" — and
move on.** it is the cheaper build. it is also a small failhide: `unreadable-clone`'s own message
says the *instrument itself broke*. that is not what happened. the instrument was fine; something
else terminated it. a reader pointed at "read the payload, then report the shape it carries" would
debug the wrong thing entirely — there is no payload to read, because the process never got to
write one.

so the halt says exactly what is known and no more:

```
🗿 5.3.verification
   └─ ✋ brain switch could not land

   the stone prescribes = claude-opus-5[1m]
   this driver runs     = unknown — the clone probe was terminated

   why: `clone whoami` died by a signal rather than an exit code, so no address
        was confirmed and the switch was NOT dispatched. this is NOT the 2s
        cap — the cap reports `timed-out` and settles first, so another party
        ended the probe: an oom killer, a ci runner cap, or a supervisor.

   fix: run the probe by hand, then read what ended the last one —
     rhx clone whoami --output json

   or:  remove `brain:` from the stone's guard, and accept the inherited
        brain deliberately rather than by accident —
     5.3.verification.guard
```

⇒ **the "aha": a probe that cannot answer is not the same experience as a probe that answers
"no".** `case=2` is a clean, expected, everyday rejection with one obvious fix. this family is an
instrument malfunction, and the honest fix is "go look at the instrument" — a fundamentally
different act, and one that fails the reader if it is dressed in `case=2`'s clothes.

## .the bdd `[tn]` timeline

```
given a driver enrolled and reachable moments ago — every prior stone switched cleanly
  and  a stone 5.3.verification whose guard declares `brain: claude-opus-5[1m]`

  when [t0] the hook runs `clone whoami`, and the probe process dies by SIGNAL
    then node reports `code === null` — no exit code, because there was no orderly exit
    and  the cause is classified `killed`, never folded into `unreadable-clone`
    and  the switch is NOT dispatched — no `/model` is submitted with an unconfirmed address

  when [t1] the hook reports the failure
    then the message names what is known: the probe was terminated, not merely unreadable
    and  it names what it is NOT: not the 2s cap (`timed-out` settles first and would have fired)
    and  the fix points at the probe and its terminator, not at a payload that never existed

  when [t2] the same sequence runs and the probe answers cleanly, but its address is unusable
    then the cause is `unreadable-address`, and the fix reads the payload's actual shape
    and  the fix line differs from [t1]'s — a version-skew hunt, not a signal hunt

  when [t3] the probe answers cleanly and confirms an address, and the SECOND step fails to launch
    then the cause is `spawn-failed` — the one cause where outcome and cause AGREE
    and  the fix restores local binaries (`npm ci`), never `rhx enroll` — the address was already
         good; re-enrolling would repair naught and cost a route restart for no gain

  when [t4] a driver reads any one of the six halts
    then the fix line matches the cause that actually happened
    and  no reader is sent to debug a payload, a signal, or a binary they do not have
```

## .the fail-safe grade

| obligation | how this family meets it |
|---|---|
| **fast** | `[t0]` — the classification happens at the same boundary `case=2`'s does, before any dispatch is attempted |
| **loud** | `[t1]` — a stone halt, not a warn buried in hook output |
| **teaches the fix** | `[t1]`–`[t3]` — six causes, six fix lines, each addressed to the thing that actually broke |
| **holds the limit** | shared with `case=2`: no `/model` is ever submitted with an unconfirmed address, for any of the seven causes |

⇒ this family's fail-safe rests entirely on the DISTINCTNESS of the fix line. a build that folded
all six into `case=2`'s single message would still be fast, loud, and would still hold the limit —
and would still fail the reader, because "teaches the fix" demands the *right* fix, not merely *a*
fix. that is the same axis `case=4`'s warn-vs-silence turn was measured on.

## .why this is a critipath and not a nitpick

**freq × cost**: any driver on any shared or resource-capped host — a ci runner, a laptop under
memory pressure, a container with a cpu limit — can have its probe reaped by something outside
this feature's control. it is not exotic; it is what happens when a 2s-capped subprocess shares a
machine with everything else running. cost is a driver debugging the wrong layer entirely, on a
route that otherwise looked healthy.
