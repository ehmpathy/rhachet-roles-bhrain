# 🌙 dream: reap orphaned temp files beside the drive-blocker state

**kind** = fix · **owner** = `ehmpathy/rhachet-roles-bhrain` · **caught** 2026-09-15

## .the cue that fired

an L3 review (`enroll-impl-arch-defects`) flagged it and offered *"a one-line dream if not fixed
now."*

## .the gap, precisely

`setDriveBlockerStateUnlocked` writes `${statePath}.${process.pid}.tmp`, then renames it over the
target, and unlinks the temp in a `finally`:
- the `finally` covers a thrown error — never a process killed between write and rename (OOM,
  `kill -9`, a host crash, a hook cap)
- ⇒ that temp is orphaned for good; no operation reaps `*.tmp` siblings

## .the shape of the fix

inside `mutateDriveBlockerState`'s critical section, before the write, unlink any
`${base}.*.tmp` sibling. under `withDriveStateLock` no other writer is live, so every such sibling
is an orphan.

**the clamp it owes:** write `${statePath}.99999.tmp` by hand, call `mutateDriveBlockerState`, assert
the orphan is gone.

## .why it is not done in this round

- **SAFE** — now yes: the lock this dream waited on has shipped, so no live temp can be reaped
- **CLEAN — no.** it adds a `readdir` to every state write, on the path the scope-leak fix narrowed to
  brain-declared stones to remove I/O. it wants a design call — conditional, or batched

⇒ low severity: small files, a rare trigger.
