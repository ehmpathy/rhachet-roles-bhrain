# 🌙 dream: reset the drive-blocker count when the stone changes

**kind** = fix · **owner** = `ehmpathy/rhachet-roles-bhrain` · **caught** 2026-09-09

## .the cue that fired

a line-by-line read of `stepRouteDrive.ts`'s `onStop` branch, done to settle fulcrum `F7` (does a
stone-entry signal exist?). it walked past this on the way.

## .the gap, precisely

`setDriveBlockerState` increments the count whatever the stone:

```ts
// src/domain.operations/route/drive/setDriveBlockerState.ts
project: (before) =>
  new DriveBlockerState({
    count: before.count + 1,     // 🔴 never compared against before.stone
    stone: input.stone,
    brain: before.brain,
  }),
```

and `stepRouteDrive.ts` halts past it:

```ts
const maxBlocks = 21;
if (state.count > maxBlocks) { …exit 1, "the route is stuck"… }
```

⇒ **the 21-block cutoff is a per-ROUTE budget where its own message claims a per-STONE one.** a route
that spends 15 stop-blocks on stone 1 and 7 on stone 2 halts as *"stuck"* on a stone it has visited
seven times.

## .the shape of the fix

one branch in `setDriveBlockerState`'s `project`:

```ts
project: (before) => {
  const stoneChanged = before.stone !== null && before.stone !== input.stone;
  return new DriveBlockerState({
    count: stoneChanged ? 1 : before.count + 1,
    stone: input.stone,
    brain: before.brain,
  });
},
```

- `before.stone !== null` keeps a fresh state from a read as a stone change
- `setDriveEntryStone`, the second writer, preserves the count and is unaffected

**the clamp it owes:** two `onStop` calls on stone A, then one on stone B → count is 1, never 3.

## .why it is not done in this round

- **SAFE — no.** the cutoff is a live safety mechanism on every route; to change when it fires is to
  change when a stuck drive escalates to a human
- **CLEAN — no.** it reaches the 21-block semantics, the *"the route is stuck"* text, and any
  snapshot that pins a count

⇒ deferred for safety, not size — so a dream and no fulcrum.
