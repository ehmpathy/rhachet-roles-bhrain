## .the gap, precisely

- `compileReviewPrompt.ts:303` refuses any prompt over 75% of the window. there is no partition path:
  one reviewer = one prompt, always
- per the refused run's own `tokens.expected.md` (repo-rules reviewer): 1.6M tokens post-polluter —
  `src/` 71.0%, `.behavior/` 11.2%, `blackbox/` 11.0%. real code alone exceeds the 786k gate, so no
  polluter filter can make a whole-branch reviewer fit

## .the shape of the fix

1. when a reviewer's projected prompt exceeds the gate, pack its targets into K partitions that each
   sit under ~60% of the window; run the K calls in parallel under the same rubric
2. partition along the import graph where possible (a test and the code it tests share a partition),
   with stable partition keys so each partition's prefix stays byte-identical round over round (cache)
3. every partition carries the same compact map of the whole scope (paths + outlines), so no
   partition is blind to the rest of the branch — the cohesion concern
4. merge: dedupe concerns by (file, line, rule); the reviewer's blocker/nitpick counts are the sums;
   the K partitions absorb as ONE reviewer (one `.given`, one `.taken`), so the absorb gate is unchanged
5. a coverage ledger records which partition read which file; the gate refuses passage if any
   in-scope file was read by no partition

this composes with the peer dreams caught the same day — progressive disclosure over turns, and a
radius around diff hunks — and should be the LAST resort, after those shrink what each target sends.

## .open question 1 — how do we know whether a reviewer is partitionable?

the wisher's question. a best-guess answer, to be settled before the build:

a rubric is partitionable to the degree its verdict on a file depends only on that file. the
dependency takes four values (the attribute's name is unsettled — name it at itemization, once):

| the verdict on a file depends on | example rubrics | how to partition |
|---|---|---|
| that file alone | given-when-then shape, snapshot blemishes, gerunds | any partitions |
| that file and one counterpart | test intent (a test and the code it tests), a snapshot and its test | partitions that keep pairs together (match by import or by name) |
| the file's import neighbourhood | directional deps, decode friction across calls | partitions along the import graph's connected components |
| the whole set at once | experience coverage ("every journey has a test"), "no duplicate operation" | bodies cannot be partitioned. map-reduce: partitions emit facts, one final call checks the set property over the facts plus the whole-scope map |

three ways to learn which value a rubric holds, cheapest first:
1. **the rubric declares it** in its frontmatter, the same way it could declare its corpus. visible,
   reviewable, and wrong only where its author was
2. **infer it once from the rule text** (a cheap model reads the rule's detect question) and record
   the guess for a human to confirm. never inferred silently per run
3. **measure it**: on a scope that fits in one prompt, run the reviewer whole and partitioned, and
   diff the concerns. concerns lost under the partition are the cross-file loss; zero loss over
   several runs is evidence the verdict depends on the file alone

default for an undeclared rubric: treat it as whole-set, the safe assumption, so an unknown rubric
never partitions silently.

## .open question 2 — how do we know a partition's contents did not change, so its verdict is cacheable?

the wisher's question. a best-guess answer:

- **key each partition's verdict by all that could change it**: hash of (rubric bytes · brain slug ·
  prompt template version · the sorted list of (path, content hash) for the partition's targets · the
  hashes of whatever context the rubric depends on — the counterpart for a pair rubric, the
  neighbourhood for a graph rubric). same key → reuse the stored concerns, marked `cached`; they
  still count
- **partition assignment must be stable**, or a single changed file reshuffles every partition and
  every key misses. pack by a consistent hash (or by connected component id) so a change perturbs
  only the partition that holds it
- **the shared whole-scope map must stay OUT of the key for a file-alone rubric.** the map changes
  whenever any file changes, so if it is in the key, no partition ever hits. it rides as advisory
  context; only a whole-set rubric keys on it, and only in the final reduce call
- **a finer grain is possible**: cache per (rubric, file) inside the partition, so a partition with
  one changed file re-sends only that file plus a list of its clean neighbours with their cached status
- **invalidation**: any rubric edit, brain change, or template version bump voids every key for that
  rubric. a final full sweep before passage is the backstop for staleness the key failed to capture
- this repo already keys a clean reviewer by artifact hash
  (`howdoes.the-guard-caches-a-clean-reviewer-by-artifact-hash`); a partition key is that same idea at
  a finer grain, and should reuse its seam

## .why it is not done in this round

- SAFE — no: it changes how every guard reviewer runs and how verdicts are tallied
- CLEAN — no: a new composer path, a merge step, a ledger, and the absorb seam; a feature of its own,
  not a ride-along on a verification stone
