# 🌙 dream: a role's hook entry declares its fault mode, and `rhachet init --hooks` renders the envelope

- kind: reseed
- owner: ehmpathy/rhachet (Role.hooks, `rhachet init --hooks`)
- caught 2026-11-01

## .the cue that fired

the l3 arch-defects review of `fix-memory-guard-fails-open` read `memory.guard.sh` and named its fail-open envelope generic: locate the cli from the skill's own package, bound the link hops, hold a node-side deadline, map exit codes, render one fault line. that is most of the skill, and none of it is about memory.

## .the gap, precisely

- `rhx` maps a skill lookup fault to exit 2, which claude code reads as block
- `Role.hooks` has no way to say what a hook's fault should mean
- so each advisory guard must hand-roll the envelope beside its own logic; the learner's memory.guard did, and the driver hooks (fulcrum F2, its own dream) share the same hazard unrepaired

## .the shape of the fix

a fault mode on the hook entry:

```ts
{ command: 'rhx memory.guard --mode hook', timeout: 'PT5S', onFault: 'allow' }   // advisory
{ command: 'rhx forbid.secrets --mode hook', timeout: 'PT5S', onFault: 'block' }  // safety gate
```

`rhachet init --hooks` renders the envelope around `command`: on a lookup fault, a load fault, or a timeout, `allow` prints one line that names the fault and its fix and exits 1; `block` exits 2. the skill keeps only its verdict.

## .why it is not done in this round

the seam lives in rhachet, another repo. and it has one caller today: the learner's guard. the driver hooks would be the second, so the reseed waits for them (`rule.prefer.wet-over-dry`) and carries this guard's envelope as the worked example.
