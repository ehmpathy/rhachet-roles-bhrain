# 🌙 dream: a local resnap writes later-attempt snapshot keys that a clamp then refuses

kind = fix · owner = rhachet-roles-bhrain (test infra) · caught 2026-10-16

## .the cue that fired

for the second time in one release, `snapshotsHoldOnlyFirstAttemptKeys` went red after a local
`--resnap`. 24 entries in `review.by.acceptance.test.ts.snap` were rebuilt by hand.

## .the gap, precisely

- locally, `REPEATABLE_CONFIG.criteria = 'EVERY'`, so a `when.repeatably` block runs all three
  attempts. each attempt's `when` label carries `, attempt N`, so `--resnap` writes three keys
- in CI, `criteria = 'SOME'` skips attempts 2 and 3 once attempt 1 passes. so keys 2 and 3 are
  obsolete there, and the clamp correctly refuses them
- ⇒ the resnap and the clamp disagree by construction. the only cure today is a hand prune
- seen in this round: `driver.route.partition-journey` (case1 t6, case2 t0) and `review.by` (12
  cases × 2 attempts)

## .the shape of the fix

pick one, in preference order:

1. snapshot only under attempt 1: a helper `thenSnapOnce` (or an `attempt` field on the
   repeatably context) that calls `toMatchSnapshot` only when `attempt === 1`, and asserts
   byte-equality against attempt 1's capture on later attempts
2. or strip `, attempt N` from the key: a custom snapshot name via `toMatchSnapshot(name)` that
   omits the attempt suffix, so all attempts share one key
3. then the clamp stays as the gate and a resnap can never trip it

## .why it is not done in this round

the cure touches every `when.repeatably` suite with a snapshot (dozens of files) and the
`test-fns` patch. that is a ripple past this release's diff — safe, but not clean.
