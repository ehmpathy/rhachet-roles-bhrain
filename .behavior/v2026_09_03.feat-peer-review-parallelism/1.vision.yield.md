# 1.vision.yield — peer reviews at one level run concurrently

## .the outcome world

### a day in the life

a driver finishes an artifact and runs `--as arrived`. level 1 holds four reviewers. all four go
at once. the fastest lands at 20 seconds, the slowest at 52, and at 52 seconds the level is done
and the ladder moves on. level 3 holds three expensive reviewers behind a rate limited provider,
so its guard declares `concurrency: 1` and it pours one at a time — which is correct, because one
at a time is what the provider permits.

the driver fixes the blockers and arrives again. and again. four or five rounds, the way a real
stone goes.

the prose above and the table below describe this feature in durations; **its entire visible surface
is a terminal**, and a reader had to imagine it. below it is a sight.

#### today — one lane at a time, and the second one does not exist yet

🔴 **r2's header is absent, and that absence IS the cost.** the reviewer has not been spawned — the

⇒ **the sum is not an arithmetic artifact — it is on the screen**, as one clock that starts only
after another clock stopped.

⚠️ **and note the fixture's own name.** the file is `peer-budget-parallel-l1`; this is what
`parallel` means in it today — two reviewers that **sit** at one level, run one after the other.
that collision is recorded under `.a term collision found en route — parallel is already taken`, and
this render is what makes it concrete.

#### 🔴 after — ONE spinner, on the last line, that speaks for the whole level

⚠️ **the wisher settled this contract mid-round, and it replaced what this section first drew.** the
three constraints, verbatim:

> *"we can only overwrite the last line in a review spinner"* · *"we require the spinner to say how
> long all has been inflight"* · *"we want to know how many are left too"*

⇒ **so the spinner is not per-lane. it is a single tail status line**, and every settled block
appends **above** it:

```
🦉 the way speaks for itself
   │
   ├─ r1: alpha-checker (l1, 1/5) — inflight
   ├─ r2: beta-checker  (l1, 1/5) — inflight      ← announced at t=0, then never touched again
   │
   └─ ⠸ 2 inflight · 0 done · 2 left · 34.8s      ← THE only line that moves
```

r2 lands first at 42.2s. its block appends **above** the status line, which then redraws in place:

```
   ├─ r1: alpha-checker (l1, 1/5) — inflight
   ├─ r2: beta-checker  (l1, 1/5) — inflight
   │
   ├─ r2: beta-checker (l1, 1/5)                  ← appended; never written back into its announce
   │   ├─ rejected 42.2s
   │   ├─ 1 blocker 🔴
   │   ├─ 0 nitpicks ✓
   │   ├─ given: …r002._.given.by_peer.beta-checker.md
   │   └─ taken: …r002._.taken.by_self.beta-checker.md
   │
   └─ ⠴ 1 inflight · 1 done · 1 left · 42.4s      ← same line, redrawn
```

**each field answers one of the three constraints:**

| field | the constraint it serves |
|---|---|
| `34.8s` | *how long **all** has been inflight* — the **level's** clock, started when the group did, never any one lane's |
| `2 left` | *how many are left* — 🔴 **not yet settled**, so `inflight + queued`. see below |
| `2 inflight · 1 done` | what *"several are up, and here is which have come down"* reduces to, in one line |
| its **position** — always last | *only the last line can have a spinner* |

🔴 **`left` is `inflight + queued`, never `queued` alone** — so the invariant is `done + left =
members`, and the frame above reads `1 done · 1 left` on a two-member level ✅.

⚠️ **peer review i023/r2 parsed it the other way** and computed `0 left`, which is the whole reason
the definition is now stated rather than assumed. **the two senses coincide on an unbounded level**
(the queue is never occupied, so `left == inflight`) and **diverge at `concurrency: 1`** — the level
this feature exists to make possible. ⇒ `case=8` carries the full argument under `` `left` means
NOT-YET-SETTLED ``.

#### 🔴 and this collapses fulcrum F4 — the peak's cursor math is not needed

**the mechanism is the extant one, unchanged.** `seal()` ends every line with `\n`, so after any
append the cursor sits on a fresh **last** line — which is exactly where `overwrite()`'s `\r` works
(`genContextCliEmit.ts:47-56, :59-67`). the loop is:

```
overwrite(status)              # the tail spinner, on the last line
… a lane settles …
seal(block line 1..n)          # pads over the status line, then appends the block
overwrite(status')             # redraw the status on the NEW last line
```

⇒ 🔴 **no `\x1b[{n}A`, no frame buffer, no multi-line redraw.** the wish warned the peak *"is most
likely to eat the whole round"*, and **F4's cost was an artifact of the per-lane spinner, not of live
feedback.** one aggregate line delivers live status **inside** the floor's own `never overwrite an
earlier line` rule, because it never overwrites an *earlier* line — only the last one, which is the
one `\r` owns.

⚠️ **and it repairs the defect this render exists to avoid.** the extant `clearActive()` fires at the
head of every branch (`:205`, `:235`), so under a per-lane design r2's start kills r1's interval and
**at most one lane could ever animate — which one is a race.** with a single tail spinner there is
**one interval for the whole level**, so there is no second interval to kill.

**non-tty is unchanged:** `overwrite` falls back to a plain newline (`:52-55`), so a piped CI log
gets one status line per tick instead of an animation — append-only, no escape codes, identical
information.

⚠️ **at a level that declares `concurrency: 1` this picture is deliberately the TODAY one.** that is
the valve at work, never the feature absent — see `.the measured shape of a real guard — and the
tension it exposes` below, where the same point is made in durations.

#### 🔴 a bound this render exposed — the oracle and the risk are on DIFFERENT streams

verified while the blocks above were assembled, and it narrows the render risk materially:

| stream | carries | written by |
|---|---|---|
| **stderr** | the live frames — spinner, `\r` overwrite, the header/detail split | `genContextCliEmit.ts:50, :62` |
| **stdout** | the settled tree the snapshot records | captured at `:78` |

⇒ **the interleave hazard case 8 describes lives on stderr. the 36-snapshot oracle lives on stdout.**
so a botched live render cannot silently corrupt the recorded verdict trail, and the two can be
clamped independently — the floor render against stderr, acceptance 2 against stdout.

⚠️ **one thread left for the execution stage, and it is named rather than assumed:** this bound
holds only if the stdout tree is composed from the results array at the end, sorted by declared
index — never streamed as lanes settle. i verified the two streams differ; **i did not read the
stdout composer.** that read is owed before the bound is leaned on.

### the before / after

| | today | after |
|---|---|---|
| a level of four at 35s, 52s, 28s, 20s | **~135s** — the sum | **~52s** — the slowest member |
| 🔴 this repo's own l1 — **8 reviewers** (`5.3.verification`) | the sum of 8 | the slowest of 8 |
| a convergence loop of 5 rounds | ~11 min of wait | ~4.5 min |
| a rate limited level under fan-out | *(not reachable — all runs are serial)* | declares `concurrency: 1`, stays correct |
| a level with 3 cached-approved of 5 | serial walk over 5, skips 3 | 2 enter the pool, 3 never take a slot |

⚠️ **read every "after" as an upper bound, not an expectation** — flagged in self-review r3
(assumptions). the durations above are **solo** measurements, and fulcrum F7 argues at length that
lanes which share a machine and a provider quota each run slower. so the honest form is:

```
today:  sum(solo)          after:  max(inflated)     where max(inflated) > max(solo)
```

⇒ **the win is untouched in kind** — a sum collapses to a max, which is the whole point, and it
holds however much each term inflates. what the table overstates is the *ratio*, and the multiplier
is unmeasured precisely because concurrency does not exist yet to measure it (F7's own reason). **a
reader should not plan against the unqualified number.**

### the aha

**a level no longer costs the sum of its parts.**

and the second aha, the one that makes the first shippable: **the bound is not a limitation on the
feature — it is what lets the feature be turned on at all.** full fan-out at a rate limited level
does not merely run slow; it 429s, returns `malfunction`, and sends the driver to diagnose a
reviewer that was never broken. the two outcomes ship together because either alone is worse than
neither.

## .the mental model

### how a user would describe it to a friend

> "reviews at the same rung all go at once now. and if a rung can't take the crowd, you tell it
> how many at a time."

### the metaphor that fits — and it is the wisher's own

a **bottleneck**, in the sense `with-bottleneck` already uses: the neck of a bottle is not a
defect, it is deliberate. it controls the pour so the drink does not go down your shirt. level 1
has no neck. level 3 has a narrow one, on purpose.

⚠️ the metaphor the model must **avoid** is *the queue*. a queue implies order and fairness
matter — which reviewer goes first. they do not: within a level, order is irrelevant and any
consumer that depends on it is a defect (see determinism, below).

### their words vs ours

| they say | we say | why |
|---|---|---|
| "run them at the same time" | **concurrent** | *parallel* implies separate cores; this is i/o wait, not cpu |
| "how many at once" | **concurrency** | the wisher's own word — fulcrum F5 |
| "rung" / "tier" | **level** | extant declared term; do not coin a synonym |
| "the cap" | **concurrency** | *cap* is fine in prose, never in the contract |

## 🔴 .the meter, verified — acceptance 6

the wish inherited a hazard from the prior perspective: *"the meter-write race — two reviews that
settle together can clobber one another's write."*

**i checked it, and the file is not where the race is.**

`setRouteStoneGuardReviewPeerMeter.ts:27` is a bare `fs.appendFile` to
`.route/reviewPeerMeters.jsonl`, and the read (`getAllRouteStoneGuardReviewPeerMeters`) takes the
**last entry per `(stone, slug)`**. two concurrent appends interleave *lines*; they cannot clobber
one another, because each writes its own slug's row and no reader-modifier sits between them.
there is no read-modify-write to lose.

⇒ **the real race is in-process, and it is the level gate.** these three are mutated inside the
loop —

| line | mutation |
|---|---|
| `:615` | `meterBySlug.set(...)` |
| `:663` | `reviews.push(...)` |
| `:479` | `exhaustedReviewerSlugs.push(...)` |

— and `computeVerdicts()` at `:536` **reads `reviews` and `meterBySlug`** to evaluate the gate on
every pass. run that loop body concurrently and the gate reads state mid-write.

**the answer is structural, not a lock:** partition into level groups → run a group → settle it
fully → evaluate the gate → open the next group. the gate moves *between* groups instead of
*inside* the walk, and then no task ever reads a co-member's in-flight state. no mutex is
introduced, because none is needed once the shared read is moved out of the concurrent region.

⚠️ this contradicts the prior perspective, which listed the meter write as hazard #1. it was
written against an older tree. **the code wins**, as the wish instructed.

### 🔴 there is a THIRD piece of shared state, and it is the one genuinely unsafe write

found in self-review r3 (assumptions). the two paragraphs above answer acceptance 6 and **did not
enumerate the space** — they answered the criterion's noun (*the meter*), then correctly re-aimed
its intent at the in-process gate, and stopped there because two items sufficed.

| shared state | verdict |
|---|---|
| the meter file | ✅ append-only, last-per-slug ⇒ safe |
| the in-process gate state | 🔴 real ⇒ answered by the between-groups gate above |
| 🔴 **the review log directory** | 🔴 **overwrite-by-path ⇒ the one genuinely unsafe write** |

`stepReview.ts:294` keys the log dir on **wall-clock time alone**:

```ts
const logDir = path.join(cwd, '.log', 'bhrain', 'review', genLogTimestamp());
await fs.mkdir(logDir, { recursive: true });   // :295 — silent on an extant dir
```

`genLogTimestamp()` (`:126-128`) is an iso timestamp with its separators stripped —
**millisecond resolution, no slug, no index, no pid.** its `.why` claims uniqueness, and uniqueness
held only because the caller was serial.

⇒ two lanes that share a millisecond **share a directory**, and each overwrites the other's
`input.scope.json`, `metrics.*.json`, and input/output artifacts.

🔴 **the harm is a corrupted diagnosis, and it lands only under failure.** `logDirRelative` is what
the failure hint hands the driver (`:475` — *"inspect …/input.scope.debug.json to see what was
matched"*), so **a driver sent to diagnose reviewer A opens reviewer B's evidence** — and finds a
plausible file rather than an absent one. nobody opens these artifacts on a clean run, so the
corruption stays invisible until the moment it costs the most.

⚠️ **it is the second hazard this feature CREATES rather than exposes** (F7 is the first). under the
serial loop two reviews cannot share a millisecond. under fan-out, N lanes spawn in a tight loop, so
at this repo's measured 8-wide l1 a collision on the first arrive is close to certain — **routine,
not a rare edge.**

**the answer:** key the log dir on the reviewer's `index` as well as the clock. the index is already
a durable identity key (below) and already unique per pass by construction, so this is additive and
keeps every directory attributable.

⚠️ **not more clock precision.** a finer timestamp shrinks the window and does not close it, which
converts a certain defect into an intermittent one — strictly worse to diagnose.

⇒ **the clamp:** run a level of N concurrently; assert N distinct log directories. under the current
key it goes red the moment two lanes share a millisecond.

🔴 **this now has a demo — [`case=10`](./1.vision.experience.case=10.a-corrupted-log-trail-misroutes-the-diagnosis.md).**
peer review i002/r2 found the hazard argued here in prose and verdicted in no cell: *"it lives
entirely outside the walked matrix … either promote it to a case or declare it out of the experience
space."* the reviewer was right that a coverage contract cannot hold a critipath as an argument in an
adjacent document — **an experience described in the yield and absent from the inventory is exactly
the drift the contract exists to refuse** — and the yield's own *"routine, not a rare edge"* picks
the branch. c10 also adds what this prose lacked: **why the clamp must assert the COUNT of
directories rather than the content of one.** the writer that survives leaves perfectly well-formed
artifacts, so a single-directory check passes under the defect.

## 🔴 .the reviewer index is a durable identity key, not a display ordinal

this began as a determinism-of-snapshots argument. self-review r1 found it is considerably more
than that, and the sharper version is a **correctness** requirement.

**counted, not estimated: 36** peer acceptance snapshots. every one renders reviewers as
`r1: alpha-checker` … `r3: final-checker` in declared order, in both the live stream and the guard
tree. so settle-order collection would churn all 36 on every run — the original argument, and it
holds.

🔴 **but the index is also written into the review artifact's filename**, and the guard reads it
back:

```
.reviews/peer/1.vision._.review.i001.8739656801d5e77f22.r001._.given.by_peer.alpha-checker.md
                                                        ^^^^ the reviewer index
```

- `getLatestReviewArtifactForSlug.ts` documents the format and recovers an exhausted reviewer's
  prior review
- `getCacheSafePeerReviewArtifact.ts:44` — `cachedReviews.find((r) => r.index === input.index)` is
  the cached-approved cache key, called from `runStoneGuardReviews.ts:385` and `:417`

⇒ **if a concurrent implementation re-derived the index from completion order, three failures
follow, and only the first is visible:**

| failure | severity |
|---|---|
| 36 snapshots churn nondeterministically | loud — someone notices at once |
| an exhausted reviewer is handed **another reviewer's** prior review | 🔴 silent |
| a clean cached review is credited to the **wrong** reviewer, so a review is skipped that should have run | 🔴 **silent, and it is `rule.forbid.failhide`** — a review that never ran reads as approved |

## 🔴 .upstream reached the third row independently, and shipped a guard for it

`getCacheSafePeerReviewArtifact` was added by #466 for a **different** cause than concurrency — an
author who edits the guard's peer list mid-drive — and it names the identical failure in its own
`.note`: *"a stricter reviewer enrolled at a rung whose predecessor approved is never run and is
reported approved. it never speaks; the stone passes on a verdict it never gave."*

⇒ **that is corroboration rather than coincidence.** the cache-key/identity coupling has now
produced the same silent failure by two unrelated routes, which is what parts a real hazard from a
theorized one.

⚠️ **and it narrows what this wish owes.** the read now reconciles index against slug, so a
mismatched cache is discarded rather than reused. **the false green is already closed** — a
concurrent implementation that shuffled indices would now cost needless re-runs rather than skip
reviews silently. that moves the third row from *silent* to *loud*, and it is a mitigation this
wish inherits rather than builds.

✅ **the good news, verified post-rebase:** `runStoneGuardReviews.ts:347` still assigns
`index: i + 1` from the **declared array position, before** the level sort. so the identity is
stable and concurrency-safe by construction. the requirement is therefore narrow and cheap —
**never re-derive it. merge results by `pr.index`, never by settle position** — but it is the
requirement whose breach is quietest, so cases 1 and 8 assert it explicitly.

## 🔴 .a `.guard` edit does NOT move the artifact hash — and this feature's whole surface is `.guard` keys

`getCacheSafePeerReviewArtifact.ts:19-22` states it outright:

> *"a `.guard` file is not in the hashed artifact set, so that edit does not move the artifact hash

⇒ **so an author who changes a concurrency bound changes nothing the cache can see.** every cached

| the edit | what it costs |
|---|---|
| add `group:` to a reviewer, in place | ✅ nothing — no index moves, and a bound governs schedule rather than verdict |
| change a `concurrency:` value | ✅ nothing — same reason. it is not a verdict input |
| 🔴 **reorder reviewers to cluster group members together** | 🔴 **every later index shifts.** the slug reconciliation discards those caches — one budget round each |

⚠️ **the third row is the one this feature invites**, and that is the whole reason it is recorded

a swap and far easier to do unnoticed, because you remove no one — it shifts every later lane by one

## 🔴 .the hazard this feature CREATES rather than inherits — the wall-clock timeout

found in self-review r3. every other risk in this vision is one concurrency *exposes*. this is the
one it **manufactures**, so it is stated in the body rather than filed as a fulcrum note.

`runStoneGuardReviews.ts:74` sets `DEFAULT_REVIEW_TIMEOUT: IsoDuration = 'PT21M'`, passed
per-reviewer at `:170`. it is a **wall-clock** bound, and every value of it — the default, and any
`timeout:` an author tuned by hand — was calibrated while a lane ran **alone**.

⇒ eight `rhx enroll claude` lanes share one machine and one provider quota. **the level gets
faster; each lane gets slower.** the timeout measures the quantity that degrades.

🔴 **and there are TWO such bounds per lane, not one** — verified in r3's second pass:

| bound | where | what it guards |
|---|---|---|
| the **subprocess** bound | `runStoneGuardReviews.ts:74` · a per-reviewer `timeout?` · `RHACHET_REVIEW_TIMEOUT_MS` (`runOneReview.ts:46-49`) | the reviewer child process |
| 🔴 the **fallback-brain** bound | `getReviewCountsViaBrain.ts:21` — `FALLBACK_BRAIN_TIMEOUT = 'PT21M'` | the sub-brain tally that **rescues** a lane whose stdout could not be parsed |

⚠️ the second is the worse: its own `.why` warns that a tight bound *"would spuriously malfunction
the very reviews this fallback exists to rescue"* — so contention squeezes the rescue path for the
slowest lane, which is exactly the lane most likely to need it.

🔴 **and a tripped timeout does not merely retry — it escalates into a spend:**

| step | what happens |
|---|---|
| 1 | contention pushes a lane past `PT21M` |
| 2 | it exits with no parseable verdict → **`malfunction`** |
| 3 | malfunction is **terminal for unlock** (`isReviewPeerVerdictTerminal.ts:18-21`) |
| 4 | 🔴 **l3 opens and spends opus budget** |
| 5 | the stone still cannot pass — a malfunction blocks passage |
| 6 | the driver diagnoses a reviewer that was never broken |

⚠️ it lands against the wish's own boundary — *"do not lower the bar to make the clock look
better"* — as the **inverse: the clock genuinely improves while the bar quietly gives way**, since a
timed-out lane reads as a defect in a reviewer that was never broken.

### 🔴 how bad it is, corrected — the failure is already legible, and i had said it was not

my first draft claimed *"a timed-out lane is indistinguishable from a broken one."* **that is
false**, and the correction matters because it is the sentence the severity rested on:

```ts
// runOneReview.ts:90
stderr: `💥 malfunction: review timed out after ${formatTimeoutForHuman({ ms: input.timeoutMs })}`,
```

— with a `.why` that cites `rule.forbid.failhide` by name, and an extant acceptance clamp on it
(`driver.route.peer-review-timeout.acceptance.test.ts:64` asserts the output contains
`'timed out'`). ⇒ **a driver reads *"timed out after 21 minutes"*, never a bare `malfunction`.**

⚠️ what the message does **not** carry is the in-flight count, so *"was this lane slow, or were
seven co-members?"* is still a guess. **the hazard is real and narrower than i first stated.**

**taken: leave the timeout as-is, and declare it.** the contention multiplier is unmeasurable until
concurrency exists, so any factor chosen now would be invented; `PT21M` is generous; **and two
valves already exist** — an author can cap the level (this wish's own mechanism), and an operator
can raise the bound via `RHACHET_REVIEW_TIMEOUT_MS` with no code change at all. carried as
**fulcrum F7 at 78% — still the lowest confidence here**, because the multiplier remains unmeasured.

⇒ **what the deferral owes:** the execution stage measures per-lane duration against solo baselines,
and the timeout message — which already names the bound — should also name the **in-flight count**,
so contention is a visible candidate rather than one the driver must infer.

## .what is awkward

honest discomforts, not a list of risks already answered above.

1. 🔴 **`level` and `concurrency` are two numbers that read alike and mean opposite kinds of
   quantity.** `level: 3` is an *ordinal* — a position in a sequence. `concurrency: 3` is a
   *cardinal* — a count of slots. a guard that carries `level: 3` and `concurrency: 3` on adjacent
   lines invites a reader to relate them, and they are unrelated. i have no repair for this beyond
   the word choice; it is the sharpest ergonomic edge in the design and i want it on record rather
   than smoothed over.

   🔴 **and execution found a SECOND instance, which is what makes this a family rather than one
   awkward pair.** `r$index` is a durable **identity** key — it is written into the review
   artifact's filename and it is the cache key — and it renders inside a tree where a reader takes
   it for a **display position**. so a guard that declares a high level first renders `r2 → r3 →
   r1`, correctly, and a driver meets the lowest number last (`peer-exhaustion-boundary`, raised
   i022/r011). ⇒ no harm lands, because every row names its own reviewer and a misread self-corrects
   on the same line. what recurs is the shape: **a number whose KIND is not legible from where it
   sits.** the repair is the same one and it is the same non-repair — name it well, then say so.

2. **the vision commits to a restructure of a function it also promises not to change the
   semantics of.** cases 1–7 all say "behaves exactly as before, but concurrent" — and the way to
   get there is to rewrite the loop that implements *all* of that behavior. the diff will be large
   and mostly-neutral, which is the hardest kind to review carefully.

3. **acceptance 6 is answered by a discovery that the hazard was misdiagnosed.** that is the right
   answer and it is an uncomfortable one to hand back, because "we checked and the risk you named
   is already covered" reads as a dodge. the in-process race that *is* real is a less obvious one,
   and it would have been easy to miss while the letter of the criterion got satisfied with a lock
   nobody needed.

4. **the default is a behavior change dressed as a default.** F2 is argued and i believe it, but a
   permissive default means the first `--as arrived` after this merges behaves differently on
   every guard in the org. to call that a default choice rather than a migration is technically
   true and slightly slippery.
   - 🔴 **and the discomfort survives the value change.** `10` softens the resource con but not this
     one: a level of four still goes from serial to four-at-once, because a cap of ten does not bind
     over four. **the migration is in the permissiveness, never in the number.**

5. ~~**case 8 carries two targets, and a two-target commitment is weaker than one.**~~ ✅ **closed
   2026-09-08 — the wisher struck the second target.** the peak was per-lane spinners; `\r` gives one
   mutable line, so it was never buildable. live status moved into the floor as one aggregate tail
   line, and **case 8 now carries a single target.** what stays optional is cosmetic polish, which
   asks no judgment of a reviewer.

   ⚠️ **the discomfort was real and i had misdiagnosed it.** i wrote that a two-target commitment
   *"puts a judgment on the reviewer"* — true, and the deeper problem was that **one of the two
   targets did not exist.** the unease was a correct signal read at the wrong depth.

6. 🔴 **two of my claims about `Promise.all` were simply false**, caught in i016/r2 and i018/r2.
   the requirements they were attached to held; the mechanisms cited did not. **a demo's mechanism
   is what an implementer builds against**, so a wrong one is worse than an absent one — and no
   internal re-read finds this class, because the artifact stays self-consistent. it is the world it
   disagrees with.
