# 🌙 dream: hoist findsertRouteGitignore to a single per-pass writer

- kind: fix
- owner: bhrain/driver
- caught: 2026-09-13

## .the cue that fired

arch-hazards-behavior r007 nitpick.3: `findsertRouteGitignore` runs a classic
read-modify-write on a `.gitignore` with no lock, and it is still invoked from per-lane
code (`setRouteStoneGuardReviewPeerMeter`), so the unlocked write remains reachable from
concurrent lanes in the production flow. its sibling `findsertReviewPeerGitignore` was
already hoisted to a single writer per pass; this one was not.

## .the gap, precisely

- `src/domain.operations/route/gitignore/findsertGitignore.ts:32-52` reads the target
  `.gitignore`, compares to the desired content, writes if different — no lock.
- the caller path `setRouteStoneGuardReviewPeerMeter` runs once per lane, so N concurrent
  lanes can each read-then-write the same route `.gitignore`.
- checkable evidence: every concurrent writer emits an identical compile-time-constant
  byte string, so a lost update leaves the file at the correct content regardless of
  interleave. the race is real but its outcome is benign TODAY.

## .the shape of the fix

hoist the `findsertRouteGitignore` call out of the per-lane meter-write and up to the
single per-pass setup that already hosts `findsertReviewPeerGitignore`, so exactly one
writer touches the route `.gitignore` per pass. the two hoists then live side by side and
the cross-lane write disappears.

## .why it is not done in this round

- SAFE: yes — the change alters only where the write happens, not what it writes.
- CLEAN: no — the hoist ripples into the meter-write path
  (`setRouteStoneGuardReviewPeerMeter` and its callers), which this diff did not open. it
  fails the CLEAN test of `rule.always.fix-forward-under-scouts-honor`, so it is deferred
  with this dream plus a fulcrum rather than smuggled in.
