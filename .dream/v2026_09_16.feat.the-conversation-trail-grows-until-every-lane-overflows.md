# 🌙 dream: the peer conversation trail has no bound, so every lane overflows eventually

- **kind** = feat
- **owner** = `ehmpathy/rhachet-roles-bhrain`
- **caught** = 2026-09-16

## .the cue that fired

`mech-external-contracts` returned a clean `0/0` at i022 and `constraint ✋` at i023 — **with no
change to its bind and no change to its rubric.** the same glob, the same rules file, one round
apart.

⇒ a lane that goes dark with its own inputs held fixed is not a lane with a scope problem. the
growth is in a term nobody declared.

## .the gap, precisely

`--conversation $conversation` threads the prior `.given` + `.taken` exchange into every peer
prompt. the glob is **unbounded** — it matches every artifact of every round, for every lane.

the arithmetic, from the lane's own refusal (verbatim from its `constraint` render):

```
✋ prompt exceeds 75% of context window
   ├─ 77.2% of 1000000 tokens
   └─ reduce scope or use --focus pull

   ├─ rules: …rule.require.external-contract-integration-tests.md
   │  ├─ files: 1
   │  └─ tokens: 545
   └─ targets
      └─ joined via intersect
         ├─ files: 120
         └─ tokens: 523.6k
```

⇒ the prompt is **772k**. rules + targets are **524.2k**. the residue is **~248k**, and the only
other term in the prompt is the conversation.

**so the conversation is ~32% of the prompt, and it is the one term that grows on every arrival.**
a round adds one `.given` and one `.taken` per lane; at 12 lanes that is 24 artifacts per round,
appended forever.

### 🔴 why this is worse than a large corpus

| the term | who controls it | does it shrink? |
|---|---|---|
| the target corpus | the driver, via `--paths-with` / `--paths-wout` | ✅ yes, by a guard edit |
| the rules | the guard author | ✅ yes |
| 🔴 **the conversation** | nobody — the glob is generated | 🔴 **never. it only grows** |

⇒ a driver who narrows a lane's corpus buys headroom that the next round spends. **the guard edit
is a stopgap by construction**, and the closer a route gets to done, the more rounds it has
accrued, so the gate bites hardest exactly when the work is nearly finished.

### ⚠️ and it fails in the quietest way there is

a lane that overflows returns `constraint`, which is **terminal for unlock** — so the ladder opens
the next level and spends its budget while the rubric grades not one file. **an unreviewed
reviewer renders identically to a clean one**, and the guard tree says as much on either line.

⇒ so the failure mode of unbounded growth is not a slow review. it is a **silently ungraded
rubric**, on the stone whose whole subject is verification.

## .the shape of the fix

the prompt already knows how many tokens each supply costs — `tokens.expected.md` is written on
every run, and the refusal itself prints the split. so the budget is measurable before the call.

three candidate shapes, cheapest first:

1. **a depth bound** — `--conversation-depth N`, which keeps the last N rounds of the trail and
   drops the rest. cheapest to build; the ceiling is then `N × per-round`, a constant
2. **a per-lane scope** — thread only the lane's OWN thread plus the current round's peers, over
   every lane's every round. a reviewer re-reads its own argument and skips eleven others'
3. 🔴 **a token budget** — the reviewer declares a conversation budget, and the trail is filled
   newest-first until it is spent. this is the one that cannot regress, because it bounds the
   quantity the gate actually measures

⇒ 3 subsumes 1 and 2 and is the honest target. 1 is a legitimate stopgap that could ship first.

🟡 **whichever shape, the drop must be LOUD.** a trail silently truncated is the same class of
defect as a silently ungraded rubric — the reviewer would argue against a `.taken` it can no
longer see. the prompt should say how many rounds it holds and how many it dropped.

## .why it is not done in this round

**SAFE? no.** it changes what every peer reviewer sees, on every route in the org, at once. a
reviewer that loses a `.taken` it needed re-raises a point that was answered — which is
`rule.forbid.unanswered-exits-from-a-blocker`'s failure, arrived at from the tool's side rather
than the driver's.

**CLEAN? no.** it is a product change in `stepReview` + the guard runner's `$conversation`
substitution + a new CLI flag + its acceptance clamps. it ripples well past the diff this route
has open, and this route's stone is `5.3.verification` of a concurrency feature.

⇒ so the deferral is on **both** questions, not merely on size. the in-round remedy taken instead
is a **guard edit** — `mech-external-contracts` split into `-src` and `-blackbox` push lanes,
which buys headroom and repairs none of the growth. that stopgap is recorded as such in the
guard's own comment above the lane.
