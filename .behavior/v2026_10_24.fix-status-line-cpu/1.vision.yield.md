# 1.vision — the route status line costs no measurable cpu

## .the outcome world

a box runs 44 claude seats. each seat's status line repaints on every message update, debounced
~300ms (`stepRouteStatusLine.ts`, header note) — so up to ~3 times a second while a seat streams. today each repaint boots node, loads the whole `cli/route` module
graph, shells to git, and globs the repo for a bind flag — **1.27s of cpu, every repaint**
(measured, `rhx bench.status-line`). a repaint that takes longer than the harness's 300ms
debounce piles up behind the next one, which is the 9-process / 491% pile the wish measured.

after: a repaint whose inputs did not change reads one small cache file and prints the line it
already computed. the cost is node's own boot and naught else. the line still reads
`🗿 1.vision, review.peer, l1@i001 🔍` — byte for byte what it read before — and a passage
change shows on the very next repaint, because the passage file's mtime is part of the key.

| | before | after |
|---|---|---|
| cpu per repaint, no change | 1.27s | ≈ bare node boot (0.06s measured; the floor of any `node -e`) |
| cpu per repaint, a change | 1.27s | the render alone; no repo-wide glob while the bound route's flag still stands |
| lag from passage change to line | ≤ 1 repaint | ≤ 1 repaint |
| what the line shows | the stone + phase + disposition | identical |

**the aha:** the status line is a *display of state that rarely changes*, and it re-derived that
state from scratch 3 times a second. the fix is not a faster derivation — it is no derivation
when the inputs did not move.

## .the contract

### the command

```
node -e "import('rhachet-roles-bhrain/cli/route.status.line').then(m => m.routeStatusLine())"
```

- a new isolated subpath export, `./cli/route.status.line` — the same move `./cli/route.reminder`
  already made (`rule.require.isolated-cli-subpath-exports`)
- its entry imports **only** the cache read and, on a miss, lazily the renderer — never the
  `cli/route` barrel
- chosen over a lazy facade for all of `cli/route`: both reach a consumer at the same `rhx
  upgrade`, and the subpath touches one entrypoint where the facade touches twenty
- `cli/route`'s `routeStatusLine` export stays, so a repo whose settings still name the old
  command keeps a correct line (at the old cost) until its next init
- 🟢 the migration rides the extant init: `init.claude.status-line.sh` already treats any
  command that names `route.status.line` / `routeStatusLine` as ours and rewrites it to the
  jsonc's form. so the one-line change to `init.claude.status-line.jsonc` upgrades every repo at
  its next `rhx upgrade` (which re-runs role inits), with no new migration code

### the cache

- one file per branch, at `.agent/.cache/repo=bhrain/role=driver/skill=route.status.line/branch=<flat>.json` (`.agent/.cache/` is gitignored)
- holds `{ line, route, fingerprint, at }`
- **fingerprint** = the branch, plus the mtime + size of each render input. every input the
  render reads today lives in one of two places, so the stat set is small:
  - `$route/` itself — stones and artifacts appear and vanish here (`getAllStones`,
    `getAllStoneDriveArtifacts`)
  - the render's own files in `$route/.route/`, found by one `readdir` and kept by name:
    `passage.jsonl` (`getAllPassageReportsRaw`), `reviewPeerMeters.jsonl`
    (`getAllRouteStoneGuardReviewPeerMeters.ts:16`), each `*.guard.promise.*.md`
    (`getStonePromises.ts:23,42`), and the bind flag `.bind.<flat>.flag`
  - 🔴 an **allowlist**, never "every file in `.route/`": hooks write files there the render never
    reads — `.drive.blockers.latest.json` on each `route.drive` (behind a `.lock` file, which also
    moves the dir's own mtime), `.bouncer.cache.json`, the `*.triggered.*` stamps. a fingerprint
    over those would miss on nearly every repaint of a seat at work
- **hit** = fingerprint equal AND `at` younger than the max age (30s) → print `line`, done
- 🔴 the hit path imports only node's `fs` and `path` — no `@src` module, no `helpful-errors` —
  and reads the branch from the git dir's HEAD file (a worktree's `.git` is a `gitdir:` pointer),
  with a `git` spawn only when that read fails. these two are what "≈ bare node" rests on; the
  module-graph clamp holds the first
- **miss** → recompute via the extant `stepRouteStatusLine`, then write the cache atomically
  (temp file + rename; never a lock — a last-write-wins cache of a pure render needs no hold)
- the max age is a backstop for an input the fingerprint does not name; it bounds staleness, it
  is not the freshness mechanism
- an unbound seat caches its blank line too, keyed on the branch, so the repo-wide glob runs once
  per max age rather than per repaint; `route.bind.set` / `del` drop the branch's cache so a bind
  shows at once

### the fault contract — unchanged, and the cache never widens it

- a fault (multi-bind, unreadable route) is **never cached**: it recomputes every repaint and
  logs to stderr exactly as today
- an unreadable or corrupt cache is a **miss**, never a fault: the line is computed fresh and the
  cache rewritten, so a broken cache costs one recompute, never correctness
- an **unwritable** cache would silently restore the full per-repaint cost, so a failed write is
  loud: one stderr row `[route.status.line] fault: cache write failed (<code>) at <path>, …` per
  repaint, the line still printed, exit still 0

## .mental model

- a crew would say: *"the status line stopped to eat the box."*
- the analogy: a shop sign. you repaint it when the hours change, not every time a customer looks.
- their words vs ours: they say *refresh*, *the line*; we say *repaint*, *render*, *fingerprint*.
  the stdout never names any of these — the line reads exactly as before.

## .evaluation

| goal (wish) | how |
|---|---|
| no measurable cpu on a repaint with no passage change | cache hit = node boot + one stat set + one read |
| current stone within a second or two of a passage change | passage mtime is in the fingerprint → next repaint |
| a clamp, red without the fix, green with it, at the grain that observes the cost | an integration test that counts the render's work across repeated repaints of an unchanged route (render invoked once, not N times), plus a module-graph clamp: the subpath's entry loads none of the review/brain modules. both go red against today's code |
| ships through normal gates; pnpm patch meanwhile | the pr body names the patch consumers can apply until the release lands |
| no change to what the line shows | the extant acceptance snapshots of `routeStatusLine` run against the new subpath, unchanged |

pros: the floor drops from 1.27s to node boot; no new deps; migration is free; the old command
still works.

cons: a second source of truth on disk (the cache) — bounded by the fingerprint and the max age,
and a cache fault is always a miss. and node's own boot (≈0.06s) remains per repaint — see
*awkward*.

## .open questions & assumptions

- [answered] **does the harness pile up repaints?** the wish measured 9 concurrent processes; a
  1.27s render against a ~300ms debounce explains it. a ~0.06s hit cannot pile.
- [answered] **will the new command reach consumer repos?** yes — via the extant init rewrite
  of our own command (`init.claude.status-line.sh:106-108`, `:262-264`), at each repo's next
  `rhx upgrade`.
- [answered] **is mtime enough to see a passage append?** yes — an append updates the file's
  mtime and size; size is in the fingerprint too, for filesystems with coarse mtime.
- [answered] **which inputs feed the render?** read from `stepRouteStatusLine.ts` and each op it
  calls: stones + artifacts (`$route/`); passage, peer meters, and self promises (all in
  `$route/.route/`). the render reads no file under `.reviews/` or `review/`.
- [answered] **can several seats in one worktree share one cache?** yes — each writes the identical
  render of identical inputs, via temp + rename; a last-write-wins race loses naught.
- [answered] **what max age?** 30s, by logic: long enough that a hit is the norm at ~3 repaints/s
  (≤ 1 recompute per ~90 repaints), short enough that an input the fingerprint misses heals inside
  one glance-gap. it is a backstop, never the freshness path.
- [answered] **what does the consumer pnpm patch carry?** the built new entry under
  `dist/contract/cli/`, the `./cli/route.status.line` export in `package.json`, and the new
  command in `dist/domain.roles/driver/inits/init.claude.status-line.jsonc` — a patch against the
  published 0.42.1, made from the build at execution and named in the pr body.
- [research] **what does a hit cost to learn the branch** — a HEAD file read vs a `git` spawn?
  measured at execution with `rhx bench.status-line`; the HEAD read is the default either way.
- [research] **a sub-node fast path** (a `sh` command that cats the cache) would cut the last
  0.06s. best-guessed against (F2) — the freshness check in pure sh is fragile — and held for the
  fulcrum council at the end of the route, not asked now.

## .groundwork

### external research

- none — no external apis. the claude code status line contract (stdout of a command, re-run on
  message updates, debounced) is the extant one this repo already targets (`route.ts:636-641`).

### internal research

- the renderer: `src/contract/cli/route.ts:810` `routeStatusLine` → `stepRouteStatusLine`
  (`src/domain.operations/route/stepRouteStatusLine.ts`)
- the costly lookup: `getAllBindFlagsByBranch.ts` — `execSync('git rev-parse …')` plus a
  `**/.route/.bind.<branch>.flag` glob with `dot: true` over the whole repo, every repaint
- the module cost: `cli/route.ts:1-92` holds ~90 top-level imports (review, brain supply,
  partitions), each with its own graph, all evaluated before `routeStatusLine` can run
- the subpath precedent: `package.json` `./cli/route.reminder`
- the cache precedent: `.route/.bouncer.cache.json` (gitignored); `.agent/.cache/` is gitignored
- the init: `init.claude.status-line.sh` + `.jsonc` — the ownership match and the rewrite
- measured: `rhx bench.status-line --runs 5` → bare node 0.058s · import only 0.853s · full
  repaint 1.266s (2026-10-24, this worktree)

## .what is awkward

- **node's boot stays.** 0.06s × ~3 repaints/s is still real cpu on a box of 44 seats. it is a
  20× cut, and the floor of the command shape the harness and the init already use. a pure-sh
  fast path would go below it, at the cost of a freshness check in shell (F2).
- **a cache beside the truth.** every cache invites "why does the line say X". the answer is
  bounded by the 30s max age and by a fingerprint that names every input the render reads today
  — and a render input added later must join the fingerprint, which is easy to forget (F1).
- **the old command keeps its cost until re-init.** a repo that never runs `rhx upgrade` keeps
  the 1.27s line. the pr body names a pnpm patch for consumers who cannot wait for the release.
