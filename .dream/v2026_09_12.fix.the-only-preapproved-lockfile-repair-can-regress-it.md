# 🌙 dream: the only pre-approved lockfile repair can regress the lockfile

- **kind** = fix
- **owner** = `ehmpathy/rhachet-roles-ehmpathy` (the mechanic's permission list + `git.branch.rebase take`)
- **caught** = 2026-09-12

## .the cue that fired

a peer reviewer raised an unmerged `pnpm-lock.yaml` as a blocker. i reached for the repair, found the
mechanic's permission list pre-approves exactly one recipe for this file —

```
rhx git.branch.rebase take --whos theirs pnpm-lock.yaml
```

— and then measured the three states before i ran it. **the pre-approved recipe would have caused the
exact harm the reviewer predicted.**

⇒ the cue was not a failure. it was the **absence** of one: the recipe is pre-approved, so it runs with
no prompt, no diff, and no confirmation. i would have learned the regression at CI.

## .the gap, precisely

`--whos theirs` writes conflict **stage 3** over the file on disk. that is correct whenever the file on
disk is one of the two conflict sides. **it is wrong whenever the file on disk is a THIRD state newer
than both** — which is the normal shape after a rebase whose conflict was never settled while an
install ran.

measured on `beav/feat-peer-review-parallelism` at 2026-09-12:

| source | `rhachet` version |
|---|---|
| stage 1 — base | — |
| stage 2 — ours | `1.47.3` |
| stage 3 — theirs | `1.47.4` |
| 🔴 **the file on disk** | **`1.47.5`** |
| `package.json:128` (dev) | **`1.47.5`** |
| the installed `node_modules` tree | **`1.47.5`** |

⇒ the on-disk file is the **only** state that agrees with the manifest and with what is installed. it
carries no conflict markers — verified: `rhx grepsafe --pattern '^<<<<<<<' --path pnpm-lock.yaml` → **0
matches**. so no conflict is left to settle; only an **index entry** is left to mark as done.

🔴 **`--whos theirs` would write `1.47.4` over a manifest that declares `1.47.5`**, which is precisely
the lockfile/manifest mismatch `pnpm install --frozen-lockfile` rejects — the CI break the reviewer
predicted, caused by the repair rather than by the state.

⚠️ **and the recipe is pre-approved, so it is the path of least resistance.** a driver who trusts the
permission list runs it with no prompt. the check that saves them is a three-way read nobody asked for.

## .the shape of the fix

two moves, and the first is the cheap one:

1. **`git.branch.rebase take` should refuse when the file on disk matches neither side.**
   it already knows all three blobs (`git ls-files -u`). a `--whos ours|theirs` whose target differs
   from **both** stage 2 and stage 3 is a request to discard a third, newer state. that is the
   `rule.require.safe-by-default` shape: fail loud, name the third state, and name the alternative —
   ```
   ⚠️ the file on disk matches neither side. it may be newer than both.
      to keep it:     rhx git.stage.add pnpm-lock.yaml
      to discard it:  rhx git.branch.rebase take --whos theirs pnpm-lock.yaml --force
   ```
2. **the mechanic's `.readme` / permission list should name the lockfile case explicitly.**
   the pre-approval reads as *"this is the way to settle a lockfile conflict."* for the common case it
   is. the doc should say the on-disk file wins whenever it agrees with `package.json`, and that the
   repair is then a stage rather than a take.

⚠️ **do not simply drop the pre-approval.** it is correct for the common case and the prompt it avoids
is real friction. the fix is the **refusal**, never the removal.

## .why it is not done in this round

**SAFE = no, CLEAN = no**, and both for the same reason: the artifacts live in another repo.

- `git.branch.rebase take` is `ehmpathy/rhachet-roles-ehmpathy`'s skill, and the permission list is
  that repo's too. a tree adopts only what is scoped to itself
  (`rule.always.scope-onetime-lessons-to-the-behavior`)
- 🔴 and this round is **halted** on a human-gated grant for the very file in question, so it cannot
  even stage its own repair here

⇒ so it is a **reseed**, and it is caught rather than dispatched: the radio was not reachable from this
round. the next traveler with write access to that repo should carry it over.
