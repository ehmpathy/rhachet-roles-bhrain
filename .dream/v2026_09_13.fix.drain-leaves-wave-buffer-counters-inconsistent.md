# 🌙 dream: genReviewWaveBuffer.drain() leaves its counters inconsistent with the released wave

- **kind** = fix
- **owner** = `ehmpathy/rhachet-roles-bhrain`
- **caught** = 2026-09-13

## .the cue that fired

peer review i020/r007 (`arch-hazards-behavior`), nitpick.1:

> *"`drain()` releases every buffered block and sets `cursor = total` but does NOT
> clear `inflight`, does NOT set `done = total`, and does NOT mark the drained slots
> in `settled`. Any caller that reads `status()` after `drain()` gets a counter lie:
> `left = total - done` stays positive and `inflight` still counts lanes that were
> never settled."*

## .the gap, precisely

`genReviewWaveBuffer.drain()` advances `cursor` but leaves `done`, `inflight`, and
`settled` untouched. so a `status()` read after a `drain()` reports a peak/live count
that does not match what was released.

**checkable evidence:** call `drain()` on a buffer with two inflight slots, then read
`status()` — `left` reads `> 0` and `inflight` reads `> 0`, though every slot was
released.

## .why it is not done in this round

- **SAFE:** yes — the fix is additive on the counters.
- **CLEAN:** the edit itself is small, but `drain()` is on a shared buffer and the
  edit lands in `src` → churns the artifact hash → re-runs every l1 lane fresh
  (non-deterministic), and this round already carries that churn from two real
  blocker repairs.
- **the harm is unreachable today:** the reviewer graded it a nitpick precisely
  because `drain()` is only reached from `done()`/`onGuardHalted()` on a close
  render, so no caller reads `status()` after it. it is a tripwire for a future
  caller, never a live defect.

## .the shape of the fix

in `drain()`, before the return: `done = total; inflight.clear(); slots.forEach((s)
=> settled.add(s))` — so a post-drain `status()` reports `left = 0`, `inflight = 0`,
consistent with the released wave. OR document that a post-drain `status()` is
undefined. the first is the pit-of-success choice.
