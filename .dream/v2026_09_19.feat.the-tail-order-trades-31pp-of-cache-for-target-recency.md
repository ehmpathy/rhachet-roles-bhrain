### 🔴 and the flip is NOT a pure gain — one fixture regressed

re-measured against the figures of 2026-09-18:

| fixture | round2 → round3, before | after |
|---|---|---|
| case1 — 1 target, revised EVERY round | **81.9%** | 🔴 **70.1%** |
| case5 — 12 targets, 1 repaired | 50.7% | **81.8%** |

⚠️ **the `before` for case1 reads 81.9%, and an earlier draft of this block read 93.2%.** that
higher figure predates the fixture repair — rounds 2 and 3 shared one conversation object, so
the prefix ran past the conversation and into the target, a state no real round could reach
under the pre-flip layout (`research.review-cost-and-cache`). ⇒ the regression this flip costs
case1 is **11.8pp, not 23.1pp** — still real, and half the size the retracted figure implied.

the crossover is one line, and it was never written down before:

```
target-first prefix       = head + stable target mass
conversation-first prefix = head + prior conversation mass
```

⇒ **target-first wins iff the unchanged target mass exceeds the accumulated conversation.** case1
revises its only target every round, so its stable mass is ~0 and conversation-first wins there.
real lanes look like case5 — but a late, heavy-churn round looks like case1, and there this costs us.

⚠️ so the A/B in `.the shape of the fix` is still owed, and it now has a **second** question beside
the first: does the closer recover the recency the flip spent, and at what corpus churn rate does
the order stop to pay?

## .the cue that fired

the corpus study measured the subject at **91.6%** of every review prompt. that raised an obvious
question the cache work had never asked: is any of that 91.6% cacheable?

it is not. the tail is ordered `conversation ++ target`, and the conversation grows by one exchange
every round — so it **caps** the shared prefix at its own end, and no byte of the target is ever
reached. the target is re-paid at full input rate, every round, forever.

the compiler's own note claimed the opposite, in as many words:

> *"ordered by how fast each moves, slowest first. the conversation only APPENDS round over round,
> so its earlier bytes stay identical … so conversation ahead of target keeps a longer prefix alive
> than the reverse would."*

the reasoning is sound and the conclusion is backwards: the conversation's earlier bytes DO stay
identical, and that is exactly what makes it a wall rather than a bridge.

## .the gap, precisely

measured in `reviewPromptCacheAnatomy.test.ts` case5, over a 12-target corpus where the driver
repairs one file per round and `getAllTargetsByCacheStability` sorts it last:

| tail order | cacheable bytes | share |
|---|---|---|
| **shipped** — conversation, then target | 15,288 | **51.0%** |
| **flipped** — target, then conversation | 24,662 | **82.3%** |

🔴 **the shipped figure is byte-identical to case1's round 2 → 3, where the corpus was half the
size.** the shipped order's cacheable bytes do not grow with the corpus at all. ⇒ the larger the
target corpus, the worse this order performs — and a real lane's corpus is far larger than 12
files.

at the rate card (`cache.get` is 31.4× cheaper than `input`), +31.3pp of cacheable prompt is
roughly **30% off the prompt bill**, which is ~all of the bill.

### checkable evidence

```sh
rhx git.repo.test --what unit --scope 'path://reviewPromptCacheAnatomy' --mode apply
```

case5 `[t1]` also clamps that the flip **reorders bytes and rewrites none** — the two variants are
byte-identical in length, so the counterfactual is honest.

## .the shape of the fix

one edit, in `compileReviewPrompt`'s `promptTailVariable` template: emit `targetSection` first,
then `conversationSection`. no other file changes; no content changes.

🔴 **and that is the whole problem with it — the cheapness hides a real tradeoff.**

| the argument | which way it points |
|---|---|
| the conversation caps the prefix, so 91.6% of the bill is uncacheable | **flip** — measured, +31.3pp |
| the target is the block the reviewer must weigh most heavily, and recency in a prompt drives attention | **hold** — unmeasured, and no byte count can speak to it |

the compiler's note gave two reasons for the current order. the measurement refutes the first
outright and leaves the second entirely untouched.

**so the fix is not the edit — it is the A/B that settles the second reason:**

1. take a real stone with a rejected lane and a known verdict
2. run it both orders against the same corpus and the same brain, N times each
3. compare the verdicts — does the flipped order miss defects the shipped order caught?
4. flip if quality holds; hold and record why if it does not

🟡 note that **lever G is already shipped and inert until this lands.**
`getAllTargetsByCacheStability` sorts repaired files to the end of the corpus, which buys naught
while the corpus sits behind the conversation. it was built for this.

## .why it is not done in this round

**SAFE — no.** it changes what the reviewer reads last, on every review the grove runs. that is a
brain-quality change with no clamp that can catch a regression: a reviewer that misses a defect
still returns a well-formed verdict, and every test here measures BYTES. a silent quality drop is
exactly the failure mode the measurement cannot see.

**CLEAN — yes.** it is one template reorder in a file this branch already opened.

⇒ SAFE answers no, so it is caught rather than ridden along
(`rule.always.fix-forward-under-scouts-honor`). ⚠️ the CLEAN answer is what makes this dangerous:
the edit is a two-line move and will read as trivial to whoever finds it. **it is not trivial, and
the dream exists to say so.**

🟡 what WAS safe and clean, and is therefore done: the compiler's jsdoc no longer states the
refuted claim. it now carries the measurement and points here.
