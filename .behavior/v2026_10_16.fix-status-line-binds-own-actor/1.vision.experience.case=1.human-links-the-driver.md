# case=1 · a human links the driver, and a driver clone shows its stone

coordinates: L=split · I=human · T=absent-key · G=no-statusLine · feel=happy · care=critipath

## .narrative

a human in `sdk-aws-lambda` runs `rhx init --roles driver --hooks`. rhachet lays out the repo
actor's brain dir first, so `<repo>/.claude/settings.of.repo.json` exists before any role init.
the driver's status-line init sees the split layout, merges `statusLine` into that file, and
prints `status = configured · settings = .claude/settings.of.repo.json`. the hook sync then
re-derives every actor. the human enrolls a driver; its session foot reads `🗿 1.vision`.

## .bdd

```
given a repo in the split layout, no statusLine anywhere
  when [t0] the init runs from a shell with no clone
    then statusLine lands in .claude/settings.of.repo.json
    then .claude/settings.json is still a link to settings.of.grove.json
    then stdout says status = configured, settings = .claude/settings.of.repo.json
    then exit 0

given a repo the old init already struck: settings.of.repo.json exists, and settings.json is a
      stray real file that holds our older statusLine (the state every upgrader starts from)
  when [t0] the init runs
    then statusLine lands in .claude/settings.of.repo.json
    then the stray settings.json is untouched — rhachet's next findsert replaces it with the arrow
    then stdout says status = configured, not skipped — the stray's statusLine is ours, and the
         skip reads only the target and the grove at $HOME/.claude/settings.json
```

🟡 the second `given` is the upgrade path: every consumer who ran the old init walks it once. the
split test (`settings.of.repo.json` exists) picks the right target even while `settings.json` is
still a real file, which is why the rule is an OR, never a test of the link alone.
