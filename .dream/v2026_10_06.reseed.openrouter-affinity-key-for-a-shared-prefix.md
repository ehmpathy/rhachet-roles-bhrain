## .what

an `affinity` option on `ask`, like the fireworks adapter's `x-session-affinity` pin, so a SET of
requests that share a prompt prefix land on the SAME served endpoint — and, where the supplier
supports it, the same replica.

## .why

a prompt cache lives with one supplier, and inside it with one replica. rhachet-roles-bhrain
splits an overflowed review into N partitions that share a large common prefix (system prompt +
the route spec, ~200k tokens), primes that prefix with one cheap ask, then pours the N
concurrently. every one of the N should read the prefix from cache.

today each ask ranks endpoints live (`floor` = cheapest; a throttle moves to the next). no ask is
tied to another. a 9-wide pour is exactly when throttles fire, so throttled partitions fall to
suppliers that never saw the prefix and pay it at full rate. the current api offers no way for
the N to follow the prime, even though `output.supply.provider` already names who served it.

the fireworks adapter already solves the replica half: it derives an `x-session-affinity` key from
the system prompt, so asks that share a system prompt reach one replica. the openrouter path has
no equivalent.

## .the shape asked for

```ts
await brainAtom.ask({ role, prompt, schema, affinity: { key } }, context);
```

1. the first ask with a `key` records the endpoint that served it (on disk, like the other caches,
   with a short ttl — e.g. 10 min)
2. later asks with the same `key` order that endpoint FIRST, still inside every filter promise
   (`floor`, `privacy`, `speed`, …); fall back only on refusal or throttle, and say so in
   `supply.attempts`
3. where the supplier supports replica affinity, forward the key (a session / affinity header, or
   openrouter's own session field if one exists) so the request reaches the replica that holds
   the cache — the fireworks pin, carried through
4. `supply` reports `affinity: { key, hit: boolean }`, so a caller can measure whether the pin held

a sane default: derive the key from the system prompt when the caller gives none, as fireworks
does — the system prompt is the one part of a request that repeats.

## .acceptance

- N asks with one key, no throttle → all N report the same `supply.provider`
- the pinned endpoint refuses → the next ask falls back, and `supply` says the pin missed
- an ask with no `affinity` and no system prompt behaves exactly as today
