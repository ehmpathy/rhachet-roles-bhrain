# 1.vision — RouteReminder

illustrate the vision implied in `.behavior/v2026_08_07.driver-cron/0.wish.md`.

## wisher decisions — settled 2026-09-06 (authoritative; supersedes the [research]/[wisher] tags below)

two open items gated the build. the wisher settled both:

1. **U1 nudge efficacy — VALIDATED.** the wisher confirmed firsthand that the injected prose nudge
   re-drives a real enrolled driver (the `{reached:true}` revive path works in practice). this closes
   U1's linchpin must-validate: it is a confirmed-works, no longer an open empirical question.

2. **U3 idle-stall first-fail tradeoff — ACCEPTED, with an observability addition.** the daemon keeps
   its **first-fail self-exit** (the hard no-infiniloop / no-clog guarantee stays intact — no bounded
   retry). to cure the one downside — a transient blip that ends the reminder exits *silently* — the
   daemon now writes an observable **malfunction crash log** on a failed reach:
   `$route/.malfunctions/daemon.driveon._.crash.n<index>.log` (route-level, monotonic index so
   successive crashes never overwrite; the file's own mtime carries "when", the content carries
   reason + session + tick-count + the recovery note). so a first-fail self-exit leaves a durable,
   discoverable trace instead of a quiet death — and `route.drive` still re-findserts a fresh daemon
   on the next live drive.

the **RouteReminder** is a scheduled prose nudge — "you can do it! drive on, fulcrum, and converge" — that
keeps a driver session in motion. it rides an **external, self-exit daemon**: one light
background process per driver session, outside the session where a shell owns its full lifecycle
deterministically.

**the route system wires the reminder itself.** `route.drive` runs as an onBoot/onStop hook
INSIDE the driver clone, continuously while a route is inflight — so the drive is the natural
pulse that upserts the reminder: every drive **findserts** the reminder while the route is a live
drive, and **reaps** it when the route is dead. no human runs `route.reminder.gen` by hand. this
is the wish's headline — "the route system will upsert the reminder into cron as needed… halt it
when the route is blocked" — built in-repo (`syncRouteReminderForDrive`, wired into
`stepRouteDrive`). the shell surface (`route.reminder.gen|get|del`) remains for manual control,
but the automatic path is the default.

## the outcome world

### day-in-the-life

a driver sits mid-drive on a long route. it best-guesses a fulcrum, re-arrives, waits on a peer
review — and the anthropic api hiccups, or the model hesitates and ends the turn with no
re-drive. the drive stops. the session sits idle until a human types "continue".

the RouteReminder poked it instead. the driver's own `route.drive` hook — which ran the moment
the route went live — findserted a daemon for the session. every ~20 minutes the daemon wakes,
reads two facts from disk — is the route an active drive, is the session alive? — and if both
hold, injects "you can do it! drive on, fulcrum, and converge" into the session input, the same
as a human keystroke. the idle drive wakes and resumes.

the moment the route blocks, or the human halts it, or the session dies, the daemon reads that
state on its next tick and **exits itself**. the OS reaps the pid. no dead route gets nudged in
an infiniloop; no stale process clogs the machine.

### before / after

| | before | after |
|---|---|---|
| api outage mid-drive | drive stalls until a human returns | the daemon re-fires the drive next tick |
| brain hesitancy (idle, no re-drive) | drive sits until a human returns | the daemon nudges "drive on" past the stall |
| route blocks / is halted | (no self-nudge existed) | the daemon reads `blocked` and exits itself |
| the driver session dies | (n/a) | the daemon reads the session gone and exits itself |
| who keeps the drive in motion | the human, by hand | the external daemon the drive auto-wired |
| who turns the reminder on | (a manual `route.reminder.gen`) | `route.drive` findserts it every drive while inflight |

### the "aha"

the value clicks when a driver survives an outage untouched: the human walks away from a
stalled session, returns, and finds the drive *advanced* — the daemon poked it past the
transient failure. the deeper aha: **the daemon carries its own kill-switch.** each tick, it
reads two deterministic facts from disk — route active, session alive? — and exits if either is
false. the pid dies with its purpose. the human never manages the daemon; it tends its own life
and death.

## user experience

### usecases / goals

- **U1 — survive intermittent api outages** *(central)*: a transient anthropic failure errors
  the turn and the drive idles; the daemon's next tick injects the nudge, and the drive resumes.
  (empirical linchpin: the nudge must reliably re-drive — see must-validate.)
- **U3 — self-halt on block, and on dead session** *(central safety req)*: when the route blocks
  or is halted for *any* reason — or when the driver session is gone — the daemon exits. this is
  the wish's hard requirement ("no infiniloops"). the external self-exit makes it a **hard,
  deterministic guarantee**: the daemon reads route-state and session-liveness from disk each
  tick, no model in the path. self-exit on a gone clone too, so a stale process cannot clog the
  machine.
- **U4 — hands-off drive continuity** *(follows from U1)*: the human enrolls a route and walks
  away; the daemon keeps the drive in motion, no human per outage.
- **U5 — overcome brain hesitancy** *(central; the reason a time-driven poke is needed)*: beyond
  a transient *malfunction*, the driver sometimes just **hesitates** — ends a turn with no
  re-drive (a needless pause) and idles. a periodic "drive autonomously, go on" nudge overcomes
  that reluctance. the crux: an **onStop hook is event-driven** (fires on turn-end), so a model
  that idles with no fresh turn-end yields no event to re-fire it. a **wall-clock daemon is
  time-driven** — it reaches an idle-hesitant model that no turn-end will wake. the daemon and
  the onStop hook cover different failure axes: the hook re-drives at each turn boundary, the
  daemon re-drives when the boundaries stop.
- **U2 — survive permission-prompt halts** *(OPEN — likely infeasible, needs validation)*: the
  wisher asked this with a "hopefully". a permission prompt **suspends a turn mid-flight** with
  the pty on a y/n answer — an injected "drive on" queues behind the prompt, it does not answer
  it. so the daemon likely does not clear a permission wall. this is a validated open question,
  not a requirement: if the wisher needs it, the honest mechanism is a permission-prompt hook or
  an auto-approve policy, not the daemon.

### contract inputs & outputs

the reminder rides an **external, self-exit daemon** — one light background process per driver
session. the entire lifecycle stays in the shell / OS, where it is deterministic. the daemon's
handle is a **pid file written into the route's own `$route/.route/` dir** — co-located with the
`passage.jsonl` the daemon already reads each tick:

- **register** = `route.drive` findserts the reminder on every drive while the route is a live
  drive: read the extant pid handle first (a live daemon is returned, never re-spawned), else
  spawn a detached daemon process and write its pid to
  `$route/.route/daemon.of=reminder-driveon.pid`. the driver's OWN clone address (from the
  enroller-injected `RHACHET_CLONE_SERIAL`, read in-process) is handed to the daemon so its
  `clone say @:<addr>` targets THIS session
- **detect "is it set?"** = read `daemon.of=reminder-driveon.pid`, then `kill -0 $pid` — a deterministic file
  read + liveness probe, no process-table scan
- **deregister** = two paths converge: (a) the daemon reads dead-route / dead-session and **exits
  itself** (the OS reaps the pid — no residue, no clog), AND (b) `route.drive` reaps the reminder
  on the first drive that observes the route dead (an in-repo backstop; idempotent no-op if the
  daemon already self-exited)

the daemon is the mechanism because its liveness is **self-limited** — the pid *is* its
lifetime, so a stale reminder cannot outlive its purpose. the pid FILE is only an inert
**handle**: a stale one (left by a crash) is a dead pointer that never wakes — `kill -0` fails,
and the next register overwrites it. that is categorically unlike a persistent OS-table entry
(an external cron line), which keeps **waking to fire** until a removal succeeds — a failed
self-remove there leaves a slow clog. so the pid file gives a deterministic, route-local handle
and keeps the self-limited liveness that makes the daemon the whole point.

#### the deterministic lifecycle

an external daemon holds the whole lifecycle in the OS, where the shell rules. each step is a
pure shell / file operation, no model:

| step | mechanism |
|---|---|
| register (auto) | `route.drive` findserts on every drive while live: read pid handle, else spawn + write pid (deterministic) |
| detect "is it set?" | read `daemon.of=reminder-driveon.pid` + `kill -0 $pid` (deterministic) |
| read route-state | `tail -1 .route/passage.jsonl` → `.status` (deterministic, proven) |
| read session-liveness | a `clone say` that fails reach-state IS the dead-session signal |
| deregister on block / dead session | daemon self-exits AND `route.drive` reaps on the first dead-route drive (deterministic, hard-guaranteed) |

the **daemon's own tick** is the whole trick:

```
each tick:
  status = tail -1 .route/passage.jsonl | .status
  if status in {blocked, rewound, exhausted, malfunction}  -> exit   # dead / parked route
  else:
    rhx clone say @:<addr> --what "you can do it! drive on, fulcrum, converge"   # inject the nudge
    if that clone say fails reach-state (clone not LIVE)  -> exit   # dead session (same call)
  sleep
```

> the exit set is the four passage statuses where a human — not a nudge — must act. the
> conceptual `completed` and `in-review` of an earlier draft map onto the real passage model:
> `in-review` = the `arrived` / `promised` / `contemplated` markers, which stay LIVE because the
> driver drives its own review convergence (U5); `completed` = a terminal `passed`, indistinct
> from a mid-route `passed` by status alone, so it is caught by the dead-session door (the
> session exits, the next `clone say` fails reach-state) rather than a status read
> (`isReminderLiveForPassageStatus`).

so **U3 (no-infiniloop) is a hard guarantee, not best-effort**: the teardown is a deterministic
file read + `exit`, no model in the path. the self-exit keeps the machine clean.

> **spike (2026-08-29):** the exit *decision* is proven against live state. the tail of this
> session's `passage.jsonl` is `{"status":"blocked","blocker":"approval"}`, so the exit rule
> (`status in {blocked,...} -> exit`) evaluates to **exit on tick 1**. the "process terminates +
> pid released" half is a host-level spike for the blueprint — the sandbox blocks arbitrary
> background loops (`<daemon> &` then observe `kill -0 $PID` fails).

#### the injection hop — `rhx clone say`

the daemon injects the nudge with **`rhx clone say @:<clone-addr> --what "you can do it! drive
on, fulcrum, and converge"`**. that is the entire mechanism — no tmux, no stdin-json, no socket. `clone say`
exists for exactly this: write a clone's pty input from outside, "with no keyboard".

it works because the **driver runs as an enrolled clone** — spawned by `rhx enroll`, which
injects the clone serial the `clone` family addresses (`invokeCloneWhoami.ts:37-42`). the
daemon, hosted by the same enroller, holds the driver's clone address and says to it directly.
`rhx clone list` enumerates the live clones; `rhx clone say @:<addr>` targets one.

the **reach-state gate is a free win**: `clone say` refuses a non-`LIVE` clone and fails loud
(verified `invokeCloneSay.ts`). so the daemon's "is the driver session alive" check (the U3
dead-session self-exit) is *the same call* — a `clone say` that fails reach-state IS the
dead-session signal. one primitive covers both inject and liveness.

the payload is a **prose nudge** ("you can do it! drive on, fulcrum, and converge") — this is what makes it a
*Reminder* (see mental model / the payload fork).

### what use looks like (timeline)

```
t0  human enrolls route → route goes LIVE → driver's route.drive hook fires
      route.drive findserts the reminder → writes pid to $route/.route/daemon.of=reminder-driveon.pid
t1  driver best-guesses a fulcrum, re-arrives, waits on peer review
      (each drive re-findserts: a live daemon is returned, never duplicated)
t2  api outage — the turn errors; the drive idles
t3  (~20m) daemon tick: passage.jsonl → active; session alive → injects
      "you can do it! drive on, fulcrum, and converge"; driver wakes, re-attempts, converges
t4  driver hits a GENUINE wall → --as blocked
t5  teardown converges from two sides:
      (a) the daemon's next tick reads passage.jsonl → blocked → EXITS ITSELF (pid reaped)
      (b) the next route.drive reads blocked → reaps the reminder (idempotent no-op if already gone)
      (no model, no CronDelete — a deterministic self-exit + in-repo reap, no residue)
t6  human clears the wall, re-drives → route LIVE again → route.drive re-findserts the daemon
      (— OR — the session died at t4; the next tick reads the clone gone → self-exits)
```

## mental model

### how a user describes it to a friend

> "the route spins up a little outside helper — 'keep at it' — that pokes the session every 20
> minutes if the api blips or the model just stalls. it checks each time whether the route's
> still active and whether the session's even alive — the moment either is done, it shuts itself
> off. it never nags a dead session, and it never piles junk on the machine."

### analogies

- a **motion-sensor light that unplugs itself once the room empties** — it re-lights only while
  a person is present (route active, session alive); once the room clears, it powers down.
- a **watchdog process** the route pets by a still-active, live drive; the *absence* of pets (a
  block, or a dead session) makes the watchdog exit rather than fire.
- the learner's own **onStop staleness sweep** — a scheduled self-nudge — but wall-clock and
  external, for *drive continuity* instead of glossary upkeep.

### terms: theirs vs ours

| they say | we say (canonical) |
|---|---|
| "the reminder / the poke / the nudge" | **RouteReminder** (the injected nudge payload) |
| "the outside helper / the little daemon" | the **daemon** (the external self-exit process) |
| "start / kill the reminder" | **register / deregister** (spawn / self-exit) |
| "is it still active?" | the route is an **active drive** (the liveness predicate) |
| "is the session even alive?" | the session **reach** (pid alive / clone reachable) |

**the payload fork (narrowed toward prose):** "RouteReminder" holds *only if* the injected
payload is a **prose nudge**. a **deterministic command** (e.g. `rhx route.drive`) is not a
reminder — it is a **scheduled dispatch / tick** (candidate: `RouteTick`). the wish supplies the
prose ("you can do it! drive on, fulcrum, and converge") and names it "Reminder", so **Reminder is correct
as-wished**; the deterministic-command fork is a *contingency* gated on the nudge-efficacy
must-validate, not an open choice now.

## evaluation

### how well it solves the goals

- **U1 (outages)** — solid, once the nudge-efficacy validation holds: the daemon fires on a wall
  clock regardless of the session's turn state, so it reaches the idle post-outage drive. the
  residual is whether the injected nudge reliably re-drives (must-validate).
- **U2 (permission halts)** — likely infeasible, demoted: an injected nudge queues behind a
  mid-turn permission prompt, it does not answer it. an open question, not a promise.
- **U3 (self-halt, incl. dead session)** — **solid, a hard deterministic guarantee.** the
  daemon's tick reads route-state and session-liveness from disk and exits. no model in the
  teardown path, and the self-exit reaps the pid so no stale process clogs the machine.
- **U4 (hands-off)** — solid, and now truly automatic: the human touches the daemon never;
  `route.drive` findserts it on every drive while the route is live and reaps it when dead, and
  the daemon also tends its own self-exit. no manual `route.reminder.gen` step remains.
- **U5 (brain hesitancy)** — solid, and the sharpest *why-a-daemon* argument: a time-driven
  external poke covers a failure axis the event-driven onStop hook structurally cannot — an
  idle-hesitant model that yields no turn-end.

### pros

- **deterministic lifecycle** — register, detect, and deregister are pure shell / OS operations.
  the model is out of the loop for all of it except the final inject and the drive itself.
- **hard self-halt, self-clean** — the daemon carries its own kill-switch (read state → exit),
  so U3's "no infiniloops" is guaranteed. it self-exits on a **dead session** too, not only a
  dead route, so a stale process cannot clog the machine.
- **self-limited liveness** — the pid IS its lifetime; the OS reaps it on exit. no persistent
  OS-table entry to leave behind, no PID file to garbage-collect.
- **covers a failure axis the onStop hook cannot** — time-driven vs event-driven; together they
  overcome transient malfunctions and brain hesitancy.
- **idempotent by pid file** — findsert on `$route/.route/daemon.of=reminder-driveon.pid` (read extant live pid
  before a spawn) means re-register is safe, and the handle is route-local, not a global scan.
- **auto-wired by the drive itself** — `route.drive` runs as a hook on every session boot/stop
  inside the driver clone, so it is the in-repo pulse that upserts the reminder while the route is
  a live drive and reaps it when dead — the wish's headline, with no human step and no external
  scheduler. because both arms are idempotent, a re-run every drive converges, never accretes.

### cons

- **a background process, not "rides shipped primitives"** — the daemon is a genuine external
  process. (the inject itself rides a shipped primitive — `clone say` — so only the loop-process
  is new.)
- **the OS-level detached spawn is a boundary we inject, not own** — the wire (WHEN to findsert /
  reap) is in-repo (`syncRouteReminderForDrive`, threaded into `route.drive`), but the mechanics of
  the detached background spawn (`detached` + `stdio:'ignore'` + `.unref()`) live behind an
  injected `spawnDaemon` boundary. the in-repo host `spawnRouteReminderDaemon` implements it and
  its test asserts every detach flag; a different host (the enroller's) can substitute without a
  change to the wire.
- **the injected nudge still depends on the model to act** — the inject is deterministic (the
  text lands); the model's *compliance* (actual re-drive) is the nudge-efficacy must-validate.
- **U2 has a limit** — a hard permission / credential wall is not cleared by an injected nudge.

### edgecases & pit-of-success

| edgecase | how the contract keeps the pit of success |
|---|---|
| route blocks but daemon lingers | the daemon's tick reads `blocked` and exits — deterministic, no model |
| driver session dies, daemon lingers | the tick's `clone say` fails reach-state and exits — the anti-clog req |
| duplicate daemons on re-register | findsert by `$route/.route/daemon.of=reminder-driveon.pid` — a second register reads the extant live pid, no dup |
| stale pid file after a crash | an inert dead pointer — `kill -0` fails, so detect reads "not set"; next register overwrites it (never fires on its own) |
| nudge fires mid-turn | a mid-turn inject queues in the pty input; it lands on the next idle, does not interrupt |
| infiniloop of nudges | the self-exit-on-block / dead-session invariant is the guard — deterministic teardown |
| permission prompt open | the nudge queues behind the prompt; it does not answer it (U2 limit, honest) |

### external research

- **claude code session cron** — 5-field cron, session-scoped, fires between turns while idle,
  8-char job id, auto-expires 7d; `durable` flag exists but is **feature-gated OFF** (S2 confirms).
  `CLAUDE_CODE_DISABLE_CRON=1` kills the scheduler. session-only crons write no dedicated state
  file — the only on-disk trace is the append-only session transcript
  `~/.claude/projects/<encoded-cwd>/<session-uuid>.jsonl` (a create/delete event log, not a state
  snapshot). sources: code.claude.com/docs/en/scheduled-tasks; the installed binary
  `@anthropic-ai/claude-code@2.1.87` (functions `smq`/`Lk6`/`ag1`, path `.claude/scheduled_tasks.json`,
  `isDurableCronEnabled` gate), read via research agent.
- **injection paths** — a `.sh` cannot emit a tool, but ordinary cli input can reach a session.
  the raw OS paths (tmux `send-keys`, `--input-format stream-json` stdin, a native supervisor,
  `claude-socket`) all exist, but **rhachet `clone say` supersedes them all** — it is the
  purpose-built primitive (pty input, reach-state gated, fail-loud). the driver is always an
  enrolled clone, so `clone say` is the injection hop and the raw paths are not needed.

## what is awkward

- **a daemon needs a detached-spawn host** — the OS mechanics of a detached background process
  (`detached` + `stdio:'ignore'` + `.unref()`) live behind the injected `spawnDaemon` boundary.
  the in-repo `spawnRouteReminderDaemon` implements it; a crash of the spawn host itself is the
  one path the in-repo reap + self-exit cannot cover (a never-started daemon has no pid to reap).
- **external process, not "pure shell in the route"** — the wish hoped to "manage the cron via
  shell or typescript". the reminder IS managed in-repo (route.drive findserts/reaps; the daemon
  self-exits; `route.reminder.gen|get|del` are the manual shell surface) — which honors the wish —
  but it introduces an OS-level process outside the repo.
- **the term rests on the payload** — "Reminder" holds while the payload is a prose nudge; if it
  ever becomes a deterministic command, the vocabulary shifts to a "tick". narrowed toward prose,
  not fully closed (gated on nudge-efficacy).
