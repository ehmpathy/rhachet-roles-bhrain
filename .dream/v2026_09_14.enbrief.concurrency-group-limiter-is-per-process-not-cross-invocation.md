# 🌙 dream: document that a concurrency group bounds one guard invocation only, not the real ratelimit

- **kind**: enbrief
- **owner**: bhrain / any
- **caught**: 2026-09-14

## .the cue that fired

peer review i022/r011 (enroll-impl-arch-defects) surfaced a scope boundary the `group:`/`groups:`
doc comments never state: the concurrency group is a **per-process, in-memory** limiter.

## .the gap, precisely

`bottleneckByGroup` is constructed fresh inside `runStoneGuardReviews` on every call. two concurrent
CLI invocations — a driver who runs two stones' guards in separate terminals — each build their own
independent bottleneck. so two processes that both declare `group: anthropic` against the same real
provider ratelimit get **zero** shared enforcement.

the whole feature exists to protect a physical ratelimit (*"l3 is 1 at a time due to ratelimits"*),
yet the mechanism no longer holds it the moment two processes run at once. an author who reads
`RouteStoneGuardReviewGroup`'s docblock would reasonably read the bound as *the* ratelimit, full
stop.

**evidence:** `bottleneckByGroup` build site is local to each `runStoneGuardReviews` call; there is
no cross-process lock or shared semaphore. verified by the reviewer against current code.

## .the shape of the fix

a one-line scope note on `RouteStoneGuardReviewGroup`'s docblock, e.g.: *"this bound holds within one
guard invocation only; concurrent CLI processes are not coordinated."* no code change — the
per-process scope may well be an acceptable boundary (the wish only asked about intra-guard-run
concurrency); the defect is that the boundary is undocumented.

## .why it is not done in this round

safe but not clean: the edit touches the group-config docblock, and the round's task is the
malfunction retry (the l3 tally fallback). a docblock edit is out of the diff the retry needs, and it
is a doc obligation rather than a live defect — so it rides a follow-up rather than the retry.
