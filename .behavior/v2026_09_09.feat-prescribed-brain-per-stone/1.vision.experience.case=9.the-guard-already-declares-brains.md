# case 9 — the-guard-already-declares-brains

**actor** = driver-clone (a human hand-edit is the identical outcome) · **feel** = sharp ·
**care** = critipath
**cell** = `driver-clone × prescribe × other-known × any reach`

> 🔴 **measured:** a guard **already** declares brains — one per peer reviewer. a top-level `brain:`
> makes four brain declarations in one file, and no surface states their relation.

```yaml
# src/domain.operations/route/.test/assets/route.peer.budget/1.vision.guard
reviews:
  peer:
    - slug: primo
      run: rhx review --rules ... --brain opus
    - slug: cheapo
      run: rhx review --rules ... --brain sonnet
    - slug: cheap2
      run: rhx review --rules ... --brain haiku
```

## .the narrative — **the ambiguous contract**, and it is the unsafe path

i am the driver, and i am about to add `brain: claude-opus-5[1m]` to a guard so the verification
stone argues with the work properly.

i open the guard to write the field, and the file is already full of brains.

```yaml
brain: claude-opus-5[1m]        # ← the line i am about to add

reviews:
  peer:
    - slug: primo
      run: rhx review ... --brain opus
    - slug: cheapo
      run: rhx review ... --brain sonnet
```

and i stop, because i cannot answer the only question that matters: **what did i just buy?**

- if `brain:` bounds the **driver alone**, i bought one opus-driven stone, and `cheapo` still runs
  its cheap review. that is what i wanted
- if `brain:` is a **stone-wide default**, i just silently upgraded three reviewers, on every drive
  that walks this route, forever. the cheap review that exists precisely to be cheap is now opus
- if it **overrides** the per-review flags, `cheapo` and `cheap2` are dead keys that still read as
  live ones

three reads, all defensible from the field name, and **the guard file itself argues for the
second** — every other brain declaration in it applies to a subprocess, so a reader has no reason to
expect the top-level one is narrower.

⇒ **the "aha": `brain:` is not a new concept in this file. it is a fourth instance of one that is
already there, at a different scope — and scope is the whole content of the field.** the wish and the
issue both describe the field as *"the brain for the stone"*, and *the stone* is exactly the word
that does not part a driver from its reviewers.

the harm is not that a build might pick wrong. it is that **whichever it picks, the guard reads the
same**, and the cost difference between read 1 and read 2 is a factor of four on every review round
the route ever runs.

## 🔴 .the narrative — **with the fail-safe**, and the fail-safe is an OBSERVATION, not a doc

same driver, same guard, same four brain declarations. **what changes is that a surface answers the
question, in the run, without a doc read.**

i write the line and save. i enter the stone. the drive's own output tells me what i bought:

```
🗿 5.3.verification, entered
   ├─ brain
   │  ├─ driver     = claude-opus-5[1m]   ← switched, this stone (guard `brain:`)
   │  └─ reviewers  = unchanged
   │     ├─ primo   = opus     (--brain, on its own run:)
   │     ├─ cheapo  = sonnet   (--brain, on its own run:)
   │     └─ cheap2  = haiku    (--brain, on its own run:)
   └─ 🦉 the brain follows the stone
```

⇒ 🔴 **the question "what did i just buy?" is answered by the run, at the first moment the answer
exists.** i do not read a field's documentation, i do not infer from a key name, and i do not have to
trust that a build made the read i hoped for.

and the shape of the answer teaches the contract without a sentence of prose: **`brain:` is on the
`driver` row, and the `--brain` flags are on the `reviewers` rows.** the two scopes are visible as
two branches of one tree — so a driver who wants cheap reviews under a rich driver can see, at a
glance, which line to edit.

🟡 **it also destroys the case's residual harm.** the narrative above says *"a cheap review that
silently ran expensive is indistinguishable from one that did not."* ✅ **it is now distinguishable,
by a read of one output block** — which is the same instrument `case=8` builds for the driver's own
brain, extended one row.

⚠️ **and the observation is what makes the contract CHECKABLE rather than merely stated.** a
documented bound can be violated by a build and nobody learns; a bound printed on every stone entry
is refuted the first time it is wrong.

## .the bdd `[tn]` timeline

`[t0]`–`[t2]` walk the **ambiguous contract**. 🔴 **`[t3]`–`[t6]` walk the same guard once the scope
is settled AND observable** — and `[t5]` is the step that makes it a demonstrated safe outcome rather
than a promise.

```
given a guard that already declares --brain per peer reviewer (opus, sonnet, haiku)
  and  a driver about to add a top-level `brain:` to that same guard

  # ---- the ambiguous contract: the unsafe path ----

  when [t0] the driver writes `brain: claude-opus-5[1m]` at the top level
    then the file now carries four brain declarations at two scopes
    and  no key name, no comment, and no error states which scope governs which clone

  when [t1] the driver asks what the reviewers will run
    then no surface answers — `route.stone.get` reports the guard's fields, not their scope
    and  the answer differs by a factor of four in review cost, with no way to tell which holds

  when [t2] the drive runs and the reviews execute
    then the reviewers run on SOME brain, and the record does not attribute the choice
    and  a cheap review that silently ran expensive is indistinguishable from one that did not

  # ---- 🔴 the settled, OBSERVABLE contract: the safe path, demonstrated ----

given the same guard, and a contract that bounds `brain:` to the driver clone
  and  a brain line that reports BOTH scopes on stone entry

  when [t3] the driver writes `brain: claude-opus-5[1m]` and enters the stone
    then the hook switches the DRIVER clone via `clone say`, and no subprocess is touched
    and  the reviewers' `--brain` flags are read by `rhx review`, exactly as before this feature

  when [t4] the brain line is rendered
    then it prints `driver = claude-opus-5[1m]  ← switched, this stone (guard `brain:`)`
    and  it prints one `reviewers` row per peer review, each with its own `--brain` value

  when [t5] the driver reads that block
    then "what did i just buy?" is answered by the run, with no doc read and no inference
    and  the two scopes are visible as two branches, so the line to edit is unambiguous

  when [t6] a later reader audits a review's cost
    then the record names which brain each reviewer ran under, per stone
    and  a cheap review that ran expensive is DISTINGUISHABLE from one that did not
```

## .the fail-safe grade

⚠️ **`[t0]`–`[t2]` fail every obligation** — the contract is ambiguous and no surface resolves it.
✅ **`[t3]`–`[t6]` is where each is met, and it is walked above rather than promised.**

| obligation | ambiguous `[t0]`–`[t2]` | 🔴 demonstrated at |
|---|---|---|
| **fast** | 🔴 the driver stops mid-write with no answer available | ✅ `[t4]`–`[t5]` — answered at stone entry, the first moment the answer exists |
| **loud** | 🔴 silent: the guard reads the same under all three reads | ✅ `[t4]` — a printed block, on every entry, that names both scopes |
| **teaches the fix** | 🔴 no message exists | ✅ `[t5]` — the two branches show which line to edit for which clone, with no prose |
| **holds the limit** | 🔴 no limit is held | ✅ `[t3]` — the hook's only lever is `clone say` into the driver's pty; it has **no reach** into a review subprocess, by construction |

🔴 **the last row is the strongest of the four, and it is the one a documentation-only answer cannot
supply.** the bound is not a promise a build might break — it is a property of the apply mechanism.
`clone say` addresses a pty; a peer review is a subprocess `rhx review` spawns. **there is no code
path from the top-level key to a reviewer**, so the scope holds whether or not anyone reads the docs.

⇒ so this case's fail-safe rests on two legs rather than one: a **structural** limit (`[t3]`) that
cannot be violated, and an **observable** report (`[t4]`) that proves it held.

⚠️ **`[t4]` widens `case=8`'s brain line, and that is a real cost against `F9`.** `F9` best-guesses
*"one output line, never a per-stone ledger"*, and the block above is five rows. **it is still not a
ledger** — ephemeral entry output, never a persisted record — but it is more than one line, and a
wisher who wants the terse form should know the trade: **one line answers *what brain am i on*; the
block answers *what did i just buy*, which is the question this case is about.**

⇒ the reviewers' rows are the part a wisher could cut. **the `driver` row alone does not close this
case**, because the ambiguity is precisely about the other three.

## 🟡 .the call this case best-guesses — `F12`

**`brain:` bounds the driver clone only.** the per-review `--brain` flags are untouched.

| | driver-only | stone-wide default |
|---|---|---|
| matches the apply mechanism | ✅ the hook's only lever is `clone say` into the **driver's** pty. it has no reach into a review subprocess | 🔴 would need a second, unrelated mechanism — a rewrite of the `run:` line |
| matches the extant precedent | ✅ `--brain` on a `run:` line already means *"the brain of the clone this line spawns"*. the top-level key means the same for the clone the guard governs | 🔴 introduces a scope no other key in the file has |
| cost behavior | ✅ a rich driver with cheap reviews is the common, wanted shape | 🔴 a rich driver silently buys rich reviews — the exact leak `case=7` is already spent on |
| rework if overturned | clean — it is a documented bound, and no caller is hardened against it | — |

⇒ driver-only, at **85%**. the open 15% is that a wisher may want one lever for the whole stone, and
that is their call to make.

## ⚠️ .why this is a critipath and not a documentation nitpick

it fails the coverage test the same way `case=5` does: **the read a naive build takes is the wrong
one, and the guard file itself pushes toward it.**

⇒ **freq × cost:** frequency is *every guard that declares a brain*, which is every guard this
feature exists for — and every one of them already carries `reviews:`. cost is a silent factor-of-four
on review spend, in a feature whose entire justification is spend. there is no workable route around
it: no surface reports which brain a reviewer ran under.

🟡 and it is sharper than a normal ambiguity because **the wrong read is the expensive one.** a build
that guesses "driver-only" and is wrong under-delivers a feature; a build that guesses "stone-wide"
and is wrong bills four brains for one.
