# 🌙 dream: a prose blocker with no numeric header tallies as zero, and the round closes clean

- **kind** = fix
- **owner** = `ehmpathy/rhachet-roles-bhrain`
- **caught** = 2026-09-16

## .the cue that fired

peer review i016 (`enroll-verif-test-intent`), while it raised a blocker, explained that
the SAME blocker had already been raised one round earlier and never engaged:

> *"`enroll-verif-test-intent` caught it at i015 as an explicit blocker ('test-intent
> violation found'), but the finding fell through a tooling gap: the reviewer didn't use
> the structured `# blocker.N:` header the tally-parser expects, so the artifact's own
> machine tally read '0 blockers, 0 nitpicks' despite the prose blocker — it was never
> engaged (no fix, no dispute)."*

## .the gap, precisely

the reviewer wrote a correct, specific, well-argued blocker in prose. the tally read zero.
so:

- the contemplation gate saw no debt and let the next round through
- the judge saw no blockers from that lane
- the driver was never told, and answered none of it
- the round closed clean, on a review that had found a real defect

⇒ **the defect survived a full round, and the mechanism that hid it is the one built to
prevent exactly this.** `contract.reviewer-output` opens by arguing that where the guard
finds no numeric count it must NOT assume zero, because *"a silent `0/0` would read as a
clean approval where in truth no verdict was seen"* — and it therefore grades an unreadable
review a `💥 malfunction`.

🔴 **here the review WAS readable — the fallback sub-brain tally ran and returned a
number. it returned the WRONG number**, because the prose carried its severity in ordinary
sentences rather than in a header the parser keys on. so the failhide guard never fired:
from the engine's side this looked like a clean review, not an unreadable one.

**checkable evidence:** the i015 artifact for `enroll-verif-test-intent` carries prose that
names a blocker and a `tallied` footer reading `0 blockers`. the same reviewer, at i016,
re-raised it with a structured header and it tallied `1 blocker`.

## .why it is not done in this round

- **SAFE:** no. the repair is in the tally path — either the fallback prompt, the parser,
  or a new "prose names a severity but the count is zero" refusal. every peer review in
  the repo runs through it, so a wrong move here mis-grades every lane at once.
- **CLEAN:** no. it lands in `getReviewCountsViaBrain` / the reviewer harness, not in this
  stone's deliverable, and it wants its own clamps across several prose shapes.
- ⚠️ **and it is a REVIEWER-side contract question, not a driver-side defect** — the
  honest fix may be to make the reviewer's own output contract stricter rather than to
  make the parser cleverer, and that is a judgment this round should not make alone.

## .the shape of the fix

the sharpest framing: **a tally of zero from a review whose prose carries severity language
is not a clean review — it is an unreadable one, and the extant failhide rule already says
what to do with those.**

so, candidates in the order they seem right:

1. **a disagreement check** — where the prose matches severity cues (`blocker`, `must-fix`,
   `🔴`, `unresolved`) and the tally reads `0/0`, refuse as `💥 malfunction` rather than
   accept the zero. this reuses the extant failhide path rather than a new one.
2. **a stricter reviewer contract** — require the `# blocker.N:` header and grade its
   absence unreadable. more honest, and it needs every reviewer rubric updated.
3. ~~a cleverer fallback prompt~~ — rejected on sight: it makes the same class of error
   less often rather than impossible, which is the *"converts a certain defect into an
   intermittent one"* trade that is strictly worse to diagnose.

🟡 whichever is taken, the clamp is the same shape: a review artifact whose prose names a
blocker and whose tally reads zero must NOT pass the gate.
