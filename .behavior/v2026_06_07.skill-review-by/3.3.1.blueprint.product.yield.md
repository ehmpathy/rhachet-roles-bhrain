# blueprint: review.by skill

## summary

implement `rhx review.by --role $role` in bhrain that:
1. locates the role's `rubrics.yml` and reads it
2. runs each rubric one at a time (serial) — each rubric dispatches the SHARED `runOneReview` runner, the same operator the route guard uses — the same `for...of await` shape as `runStoneGuardReviews` (no parallelism for now)
3. emits treestruct stdout with guard-compatible counts
4. writes review output per rubric to `.reviews/by=$role/rubric=$slug.md`
5. exits 0 (no blockers), 1 (malfunction), or 2 (any blockers)

**one runner, not two.** the guard and review.by both "run a review command → capture stdout/exit → tally → promote a no-verdict exit-0 to malfunction". today that lives inline in the guard's `runOneStoneGuardReview`. eject the reusable core as `runOneReview` and have BOTH dispatch it. review.by execs `rhx review …` as a subprocess (exactly as the guard execs its peer cmd) — NOT an in-process `stepReview` call. a single execution path removes the maintenance hazard of parallel in-process-vs-subprocess codepaths that would drift over time.

bhrain owns this skill. ehmpathy roles shipped an adhoc bash version as a stopgap; once this lands, roles delete their adhoc bash and keep only `rubrics.yml`. bhrain reads the rules inline from that yml and drives `review` itself — no per-rubric standalone skill needed.

### shared runner dispatched by both usecases

both usecases run a review command the same way: exec it as a subprocess, capture stdout/stderr/exit, tally via the `getReviewCounts` cascade, then promote an exit-0 review with no numeric verdict into a malfunction (never a fake `0/0`). today that whole sequence sits inline inside `runOneStoneGuardReview` (`runStoneGuardReviews.ts` lines ~228-320). eject the reusable core as ONE runner both dispatch — a single execution path, no in-process fork.

```
runOneReview.ts   [→] EJECT — the shared runner, dispatched by BOTH usecases
├─ input  = { cmd, timeout, cwd? }, context (brain supply for the sub-brain tally tactic)
├─ [+] exec cmd as subprocess (PATH+node_modules/.bin, RHACHET_GUARD_CONTEXT, timeout)  # from runOneStoneGuardReview
├─ [+] capture { stdout, stderr, exitCode } on BOTH success + error branches           # incl. timeout→malfunction
├─ [←] getReviewCounts({ content: stdout, exitCode }, context)  # extant: regex → sub-brain cascade
├─ [+] promote exit-0 + { detected:false } → malfunction        # the failhide-safe verdict
└─ return { stdout, stderr, exitCode, durationMs, verdict: { blockers, nitpicks, outcome, tallier, reason? } }

  dispatched by:
  ├─ runStoneGuardReviews → builds cmd via substituteVars($peer cmd), calls runOneReview,
  │                          then wraps the result into RouteStoneGuardReviewArtifact (its hash/iteration/footer naming)
  └─ stepReviewBy         → builds cmd via genReviewRubricCmd({ rubric }), calls runOneReview,
                            then folds the verdict into ReviewRubricResult
```

**what is shared vs what stays caller-specific:**

| concern | in `runOneReview`? | why |
|---------|--------------------|-----|
| subprocess exec + capture + timeout + tally + malfunction-promotion | ✓ shared runner | the whole drift-prone core; one path, one place to fix |
| serial `for...of await` loop shape | ✓ same pattern | review.by mirrors `runStoneGuardReviews`; no parallelism |
| how the review cmd string is built | ✗ caller-specific | guard = `substituteVars` over a configured `$peer` template; review.by = `genReviewRubricCmd` over a rubric |
| what wraps the result | ✗ caller-specific | guard = artifact w/ hash/iteration/conversation/meter/footer; review.by = plain `ReviewRubricResult` |

runner placement: it serves `route/guard/review/` and `review.by/`, so per rule.prefer.most-common-denominator it lives at the common ancestor `src/domain.operations/review/` (next to `stepReview`, `getReviewCounts`).

**cost of the shared subprocess path (accepted):** one node cold-start (~2s) per rubric on top of the review's LLM time (~10-26s), so ~10-15% overhead; and tests become integration/acceptance-only (no in-process fake to unit-test against). both costs the guard already pays. accepted in exchange for a single execution path + per-rubric timeout/crash isolation.

**snapshot-stability of the eject (behavior must be preserved):** the extraction of `runOneReview` out of `runOneStoneGuardReview` must NOT change guard behavior. the extant `runStoneGuardReviews.integration.test.ts.snap` holds 30 committed cases that cover exactly the ejected logic — subprocess exec (cases 1-8), tally + artifact tree/footer format, and the failhide-safe malfunction-promotion (cases 22, 23, 29, 30: no-verdict / one-dimension / sub-brain-abstain / timeout). the acceptance test for the eject is: **every one of those snapshots stays byte-identical.** a diff there = the extraction changed behavior = defect. so the guard's own snapshot doubles as the regression harness that proves the shared runner is a clean lift. the artifact-format footers (`└─ tallied`, `└─ passage blocked`) stay on the guard side (it wraps the runner's return into its hash/iteration-named artifact), so those snapshot lines stay in the guard's domain and untouched. the reused tree formatters (`formatTreeBucket`, `formatGuardTree`) are not modified, so their snapshots are unaffected.

### how this resolves the prior peer-review blockers

| prior blocker | resolution |
|---------------|------------|
| parseRubric was a "transformer" that did file i/o | split into `getRoleReviewRubricsYml` (communicator, i/o) + `asReviewRubricsConfig` (transformer, pure) |
| orchestrator mixed console.log + process.exit | console.log + process.exit live only in `cli/review.by.ts`; `stepReviewBy` returns a value |
| ambiguous term "focus" | renamed to `rubric` (matches shipped ehmpathy term) |
| ambiguous term "vibe" via cli flags | `vibe` is a declared block in rubrics.yml with a fixed shape (mascot, artifact) |
| failhide in error capture | two guards: (1) rubric malfunction is captured per-rubric, surfaced in stdout, reflected in exit code — no silent swallow; (2) the shared `runOneReview` maps an exit-0 review with no numeric verdict to `malfunctioned`, never a fake `0/0` — the same failhide-safe promotion the guard already enforces (now the single source, not a copy) |

## types

```ts
interface ReviewRubric {
  slug: string;
  purpose?: string;
  rules: string[];
}

interface ReviewRubricsConfig {
  vibe: { mascot: string; artifact: string };  // defaulted to owl 🦉 / 🔍 if absent
  rubrics: ReviewRubric[];
}

// the verdict slice within a review result — the failhide-safe tally
interface ReviewVerdict {
  blockers: number;
  nitpicks: number;
  outcome: 'passed' | 'rejected' | 'malfunctioned';
  tallier: 'deterministic' | 'probabilistic' | null;
  reason?: string;  // set when malfunctioned
}

// returned by the shared runOneReview runner (dispatched by guard + review.by)
interface ReviewRun {
  stdout: string;
  stderr: string;
  exitCode: number;
  durationMs: number;
  verdict: ReviewVerdict;
}

interface ReviewRubricResult {
  slug: string;
  purpose?: string;
  verdict: ReviewVerdict;
  outputPath: string;
  durationMs: number | null;
  // the base review's raw stdout — printed verbatim on a `--for` (disintermediated) run.
  // see rule.require.review-by-disintermediates.
  stdout: string;
}

interface ReviewByResult {
  role: string;
  vibe: { mascot: string; artifact: string };
  results: ReviewRubricResult[];
  blockersTotal: number;
  nitpicksTotal: number;
}
```

### one rubric at a time (`--for`) — DISINTERMEDIATE to the raw review

`rhx review.by --role mechanic --for mech-failhides` narrows to a single rubric, so review.by is a bare resolver around ONE review. it **disintermediates**: it emits that base `rhx review` stdout VERBATIM — no `🔍 review.by` anchor, no `rubrics` bucket, no `r1 <slug>` row. the output is indistinguishable from a plain `rhx review` for that rubric's rules. this is the exact shape a route guard invokes a peer review with: the guard captures the peer stdout, tallies off it, and wraps it in its OWN peer tree — so it wraps a NORMAL review, not a review.by tree nested inside the guard tree (review info doubled). see `rule.require.review-by-disintermediates`.

pass:

```
🦉 not even a vole
   ├─ review: .reviews/by=mechanic/rubric=mech-failhides.md
   └─ summary
      ├─ 0 blockers ✓
      └─ 0 nitpicks ✓
```

findings — the base review's own `summary` block carries the parseable counts, so a guard that consumes this one invocation tallies straight off it:

```
🦉 needs your talons
   ├─ review: .reviews/by=mechanic/rubric=mech-failhides.md
   └─ summary
      ├─ 2 blockers 🔴
      └─ 1 nitpick 🟠
```

the summary lines are parseable by the route guard `reviewed?` mechanism (`getReviewCountsViaRegex`, the deterministic tactic in the `getReviewCounts` cascade that `runOneReview` calls). so a guard can dispatch `review.by --role $role --for $rubric` per peer review and tally straight off stdout — the same contract the guard relies on for a direct `$rhx review …` peer. disintermediation is what makes review.by --for a drop-in for that direct review peer.

the AGGREGATE run (no `--for`) keeps the review.by tree shown above — it composes many reviews, so the tree is the value.

## exit codes

| code | when |
|------|------|
| 0 | no blockers and no malfunction (all pass, or nitpicks-only) |
| 1 | malfunction — config (role absent, rubrics.yml absent, invalid yaml) OR runtime (a rubric's review yielded no trustworthy verdict), when no rubric has blockers |
| 2 | constraint (any rubric has blockers) — takes precedence over a malfunction |

## execution timeline

1. cli parses args, validates `--role` present
2. `getRoleReviewRubricsYml` locates + reads rubrics.yml (throws if role or yml absent)
3. `asReviewRubricsConfig` parses yaml, validates unique slugs + non-empty, defaults vibe
4. `stepReviewBy` filters by `--for` if present
5. `stepReviewBy` runs each rubric one at a time (serial `for...of await`): `genReviewRubricCmd` builds the `rhx review …` cmd (paths/diffs/mode/brain forwarded), then the shared `runOneReview` execs it as a subprocess
6. inside `runOneReview`, the `getReviewCounts` cascade tallies blockers/nitpicks and a no-verdict exit-0 is promoted to malfunction; `computeReviewRubricTotals` sums the in-memory results
7. `stepReviewBy` returns the aggregate result (each rubric result carries its base review's raw `stdout`)
8. cli renders by scope: if `--for` (one review) it writes `result.results[0].stdout` verbatim (DISINTERMEDIATE — the raw review, drop-in for a guard peer); else it prints `genReviewByStdout` (the review.by tree)
9. cli exits by worst outcome: 2 if any blocker, else 1 if any rubric malfunctioned or a config error threw, else 0 — UNCHANGED by disintermediation (only the print differs)
