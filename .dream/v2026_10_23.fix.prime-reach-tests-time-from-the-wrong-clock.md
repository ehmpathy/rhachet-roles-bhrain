# 🌙 dream: the prime reach tests time the wait from the wrong clock

- kind: fix
- owner: rhachet-roles-bhrain (review/prime)
- caught 2026-10-23

## .the cue that fired

`genReviewPrefixPrime.integration.test.ts` failed CI twice in a row on PR #661, on commits that do
not touch review/prime:

| run | case | received | floor |
|---|---|---|---|
| 39912438854 | `[case8]` the late lane waits out the reach | 286ms | 350ms |
| 39915971384 | `[case11]` the second review departs no sooner than the reach | 172ms | 350ms |

both pass locally (54 of 54).

## .the gap, precisely

the late lane waits out `msOfReach` (400ms) measured from the first lane's **release stamp**. the
test starts its own clock at `before = Date.now()`, taken **after** the first lane's
`runOneLane` has returned. on a loaded runner the gap between the release and that return eats
into the wait, so `waited` reads short while the code waited the full reach. the assertion is a
latency claim about the runner, not about the prime.

## .the shape of the fix

measure each wait from the event the code measures from: read the first lane's release time out
of the `log` the fake records (`{ name, event, at }`), and assert
`laneDeparture.at - firstRelease.at >= msOfReach - 50`. the same change applies to `[case11]`'s
`gap`. no product change.

## .why it is not done in this round

it is safe but not clean for this PR: it is main's code, outside the token inventory's diff, and
the PR's route is complete. a rerun clears it meanwhile.
