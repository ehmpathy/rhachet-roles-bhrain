# 🌙 dream: `--scope path://X` matches the ABSOLUTE path, so a word from the branch dir widens it to all

**kind**: reseed · **owner**: `ehmpathy/rhachet-roles-ehmpathy` (`git.repo.test`) · **caught** 2026-09-23

## .the cue that fired

a verification stone cited its integration proof as *"`--scope path://review` · 125 files"*. a
re-read asked the obvious question — **125 of how many?** — and the answer inverted:

```
$ rhx git.repo.test --what integration
   ├─ scope: all
   │  └─ matched: 17 files

$ rhx git.repo.test --what integration --scope path://review
   ├─ scope: path://review
   │  └─ matched: 125 files
```

🔴 **a filter that WIDENS is the cue.** a scope is a narrowing by definition; 17 → 125 is the
opposite, so either the default is narrower than "all" (it is — it is changed-files scoped) or the
filter is broken. both turned out true, and only the second is a defect.

## .the gap, precisely

the substring match runs against the **absolute** path, never the repo-relative one. this worktree
is:

```
/home/camper/git/ehmpathy/_worktrees/rhachet-roles-bhrain.beav.feat-review-cost-meter
```

⇒ every absolute path under it contains `review`, and also `cost-meter`, `beav`, `bhrain`, `roles`,
`ehmpathy`, `home`, `git`. **proven with a token that appears in NO repo-relative path:**

```
$ rhx git.repo.test --what integration --scope path://cost-meter
   ├─ scope: path://cost-meter
   │  └─ matched: 125 files
```

no file in this repo has `cost-meter` in its path. it matched **all 125**.

for contrast, a token absent from the worktree name narrows correctly:

```
$ rhx git.repo.test --what integration --mode apply --scope path://getAllFileDiffsFromRange
   └─ matched: 1 files
```

### 🟡 the harm direction, stated honestly

it fails **wide**, never narrow — so a run is slow, not falsely green. that is the mild half.

🔴 **the sharp half is that it makes a PROOF CLAIM false.** a buttonup gate demands the exact
command beside its output. a driver who pastes `--scope path://meter` on a branch named
`feat/meter` has pasted a narrowing that did not happen — and the reverse read is worse: a
reviewer who sees a narrow scope in a proof block will reasonably ask *"where is the full run?"*
and be answered with a number that was already the full run. the label and the deed disagree, in
the one artifact whose whole job is to not do that.

⚠️ and it is **invisible from the inside**. the tool prints `matched: 125 files` honestly; it is
only a lie relative to the word you typed. the one tell is a comparison against the default, and
no cue prompts that comparison.

## .the shape of the fix

match against the path **relative to the repo root**, never the absolute one:

1. derive the repo root once (the skill already does, for its cwd guard)
2. `path.relative(repoRoot, file)` before the substring test, for both `path://` and the bare form
3. 🔴 **the clamp, and it must be seen red first**: a test whose temp repo sits under a directory
   whose NAME contains the scope token, asserting the match set excludes files that do not carry
   the token in their relative path. against today's code that clamp goes green-when-it-should-be-
   red — it must be authored to fail first (`rule.require.clamp-edge-cases`)
4. 🟡 consider a **warn** when a scope matches the full set: *"scope matched every file — did you
   mean to narrow?"*. that is the cue no comparison currently prompts

⛔ **not a fix**: an anchor on `src/` or `blackbox/`. the scope is a free substring by design, and
`blackbox/.test/` is a legitimate target; an anchor trades one silent wrong answer for another.

## .why it is not done in this round

the SAFE/CLEAN test (`rule.always.fix-forward-under-scouts-honor`):

| leg | verdict |
|---|---|
| SAFE? | 🔴 **not ours to judge.** the skill is consumed by every repo in the org; its match semantics are a published contract |
| CLEAN? | 🔴 **no.** the file is not in this tree at all |

proven:

```
$ file .agent/repo=ehmpathy/role=mechanic/skills
  symbolic link to ../../../node_modules/.pnpm/rhachet-roles-ehmpathy@1.38.12_…/
    node_modules/rhachet-roles-ehmpathy/dist/domain.roles/mechanic/skills
```

⇒ an edit here would land in `node_modules` and be erased by the next install. **a tree adopts only
what is scoped to itself** — so this is a `reseed`, owed to `ehmpathy/rhachet-roles-ehmpathy`, not a
fix deferred for size.

## .the fulcrum

> **a filter that widens is not a filter.** the defect is not that the match is too loose — it is
> that the tool answers a question about the REPO with a fact about the MACHINE, and the caller
> cannot tell from the output which one they got.
> the cost lands where it hurts most: in a proof block, where the command and its result are
> supposed to be the same claim twice.
