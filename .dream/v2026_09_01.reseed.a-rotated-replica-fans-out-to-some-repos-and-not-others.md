# 🌙 dream: a rotated `PERMANENT_VIA_REPLICA` key fans out to SOME repos, and no artifact names the ones it missed

**kind**: reseed · **owner**: `ehmpathy/rhachet` (it owns `keyrack`) · **caught** 2026-09-01

## .the cue that fired

`rhachet-roles-bhrain` PR #399 failed every brained integration shard with `401 Unauthorized` at
`rhachet-brains-fireworksai@0.1.6/…/genBrainAtom.ts:189`.

three explanations were eliminated by measurement before this one was reached:

| hypothesis | measurement | verdict |
|---|---|---|
| the secret is absent | `gh api repos/…/actions/secrets` lists `FIREWORKS_API_KEY` | ❌ present |
| the secret does not reach the job | the shard's step env logs `FIREWORKS_API_KEY: ***`; the keyrack firewall logs `granted 🔑` | ❌ it arrives |
| the package or the account is broken | same `0.1.6` locally, same account, same model — `stepReflect.caseUnclearFeedback` passes locally in 14s, 3/3 | ❌ both fine |

⇒ the secret is **present, injected, granted — and holds a value the provider revoked.**

## 🔴 .the gap, precisely — one org, one key, four replicas, one left behind

`keyrack` calls this mechanism `PERMANENT_VIA_REPLICA`: one credential in the host vault, mirrored
into each repo's GitHub Actions secrets. **the mirror is per-repo and the rotation is not.**

| repo | `FIREWORKS_API_KEY` updated | CI today |
|---|---|---|
| `rhachet-brains-fireworksai` | 2026-08-15 | ✅ green |
| `rhachet-roles-ehmpathy` | 2026-08-16 | ✅ green |
| `rhachet` | 2026-08-19 | ✅ green |
| 🔴 **`rhachet-roles-bhrain`** | 🔴 **2026-06-16** | 🔴 **401 on every brained shard** |

the dates bracket the incident exactly. bhrain's last green `test` run is **2026-08-06** — before
the rotation window — and its first red one follows it. **three repos received the new value in a
five-day window; the fourth was never visited.**

⚠️ **and no artifact anywhere names the fourth.** the vault knows the key. each repo knows its own
copy. **no artifact knows the SET** — so a rotation is complete when the person doing it runs out
of repos they remember, and the omission surfaces weeks later as a test failure in an unrelated PR.

## .why the symptom is so badly misleading

a revoked replica does not present as a credential fault. it presents as **a product defect in
whatever PR happens to run next**:

- every check that exists returns green — the key is **declared** (`keyrack.yml`), **injected**
  (the step env), and **granted** (the firewall's own report). all three pass on a dead value
- the failure lands in the shards, so it reads as N broken tests, not one broken credential
- the repo left behind is by construction the **least active** one, so the gap is longest-lived
  exactly where it is least likely to be noticed

🔴 **measured cost of that misdirection, in this incident: a diagnosis pass reached the wrong
conclusion twice** — first *"the key is stale, rotate it"* with no evidence that the value rather
than the wiring was at fault, then a second pass that only closed it by comparing `updated_at`
across four repos by hand. **the fan-out gap is invisible from inside the failing repo.**

## .the shape of the fix

the mechanism already names itself `PERMANENT_VIA_REPLICA`, so keyrack has the concept of a
replica and lacks only the plural:

- **`keyrack replica list --key <KEY> --org <org>`** — enumerate every repo that holds a replica of
  this key, with each one's `updated_at`. **the census is the whole fix**; a table like the one
  above should be one command, not an afternoon
- **`keyrack replica sync --key <KEY> --org <org>`** — push the vault's current value to every repo
  in that census, so a rotation is one operation over the set rather than N over a memory
- ⚠️ **the census must be derivable, never a hand-kept list** — a hand-kept list is the same
  artifact as the memory it replaces, and it goes stale by the same mechanism. derive it: a repo
  holds a replica iff its `keyrack.yml` declares the key

⇒ pairs with **#585** (the preflight that names a rejected key at job start). **the two are
complementary and neither subsumes the other**: the preflight makes the failure *legible* when it
happens; this makes it *not happen*. a preflight alone still lets a rotation silently orphan a repo
until that repo's next PR.

## .why it is not done in this round

it is **another repo's** — `keyrack` is `ehmpathy/rhachet`'s, which is what makes this a `reseed`.
and the local unblock is one command a human owns, since the value lives in a vault this session
must not read out:

```sh
gh secret set FIREWORKS_API_KEY --repo ehmpathy/rhachet-roles-bhrain   # value from the host vault
```

## .the fulcrum

> **a credential mirrored into N repos is rotated in the repos someone remembers.** the vault knows
> the key and each repo knows its copy, so **no artifact knows the SET** — and the repo left behind
> is the least active one, where the gap survives longest and surfaces as a product defect in an
> unrelated PR.
> rework: **clean** — a census command and a sync command over an already-declared manifest; no
> artifact hardens against it.
