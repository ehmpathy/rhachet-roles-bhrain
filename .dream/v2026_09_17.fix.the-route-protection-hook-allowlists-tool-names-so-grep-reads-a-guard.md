# 🌙 dream: the route-protection hook allowlists TOOL NAMES, so `Grep` reads a guard

- **kind** = `fix`
- **owner** = whoever owns `route.mutate.guard` — the pretooluse hook and how it is wired
- **caught** = 2026-09-17, from `.behavior/v2026_09_17.fix-budget-grant-needs-urgent-concession`,
  stone `1.vision`, `r3` self-review slug `has-questioned-requirements`

⚠️ **found and reported, never exercised.** no guard, stone, or `.route/**` file was read by this
path while the gap was confirmed — the two source files below are sufficient evidence on their own.

## .the cue that fired

a peer find (`F13`) had just established a pattern: **a bound stated over a MECHANISM leaks wherever
a second mechanism reaches the same effect.** with that lens, the obvious next question was *"the
route-protection hook bounds which tools — so which tools does it not bound?"*

## .the gap, precisely

the bound is declared twice, and **both declarations allowlist the same four tool names**:

```ts
// getDriverRole.ts:54-61 — the harness filter
{
  command: './node_modules/.bin/rhx route.mutate.guard --mode hook',
  filter: { what: 'Read|Write|Edit|Bash', when: 'before' },
}
```

```sh
# route.mutate.guard.sh:48-51 — the hook's own early exit
if [[ "$TOOL_NAME" != "Read" && "$TOOL_NAME" != "Write" && "$TOOL_NAME" != "Edit" && "$TOOL_NAME" != "Bash" ]]; then
  exit 0
fi
```

🔴 **`Grep` returns file contents and is in neither list.** so a pattern search over the route yields
matched lines from `*.guard`, `*.stone`, and `$route/.route/**` — the three path classes the hook's
own header (`:5-8`) exists to protect.

### what it defeats, and what it does not

| the hook's stated purpose (`:5-8`) | against `Grep` |
|---|---|
| *"peeks ahead at future stones"* | 🔴 **defeated** — a stone's instructions are text |
| a **read** of guard files — the review criteria | 🔴 **defeated**, and this is the costly one: the criteria a stone is graded against become legible before the work is done |
| a direct **mutate** of `passage.jsonl` | ✅ **holds** — `Grep` cannot write, and `Write`/`Edit` are both on the list |

⇒ **the WRITE half of the protection is intact; the SECRECY half is not.**

🟡 **and the two halves lean on one mechanism for a reason that no longer holds.** a write has one
shape, so a tool-name allowlist catches it. a read has many shapes, and the list was authored when
four names covered them.

## .the shape of the fix

🔴 **do not simply append `Grep|Glob` to both lists** — the hook's parse logic would then look for
the wrong fields and silently fail open. two steps:

1. **widen both declarations** — `getDriverRole.ts:58` and `route.mutate.guard.sh:49`
2. **teach the hook `Grep`'s input shape.** it currently extracts `.tool_input.file_path` (Read /
   Write / Edit) and `.tool_input.command` (Bash). `Grep` supplies `.tool_input.path` and
   `.tool_input.glob` instead — so a third extraction branch is owed, and the protected-pattern match
   must run against a **directory scope plus a glob** rather than one concrete path

⚠️ **the second step is where the care is.** a `Grep` with `path: .behavior/$route` and no glob
**would** return guard content, and it is also the single most common legitimate call a driver makes
inside its own route. ⇒ **the refusal must bound the MATCHED FILES, never the search**, or the driver
loses its most-used tool over a narrow secrecy concern.

🟡 a cheaper interim that captures most of the value: refuse only where the `glob` names a protected
extension (`*.guard`, `*.stone`) or the `path` reaches into `$route/.route/`. it leaves a broad
unscoped search open, and it closes the deliberate case.

### the deeper option, and why it is not the recommendation

the root shape is that **the bound names tools where the invariant is about an effect** — the same
class as `.dream/v2026_09_17.fix.the-privilege-grant-claims-human-only-and-checks-no-actor.md`. an
effect-scoped guard (*"any tool that returns the bytes of a protected path"*) would need no list at
all. ⇒ **that is the right shape and the wrong size for one dream** — it is a harness-level
capability, not a one-file edit.

## .why it is not done in this round

the SAFE/CLEAN test (`rule.always.fix-forward-under-scouts-honor`):

- **safe?** 🔴 **no.** a wrong bound here blocks the driver's most-used search tool inside the one
  directory it exists to tend — the exact failure `init.claude.permissions.route.jsonc:1-10` was
  authored to heal for `Write`
- **clean?** 🔴 **no.** it touches a role definition, a hook's parse logic, and that hook's
  integration snapshots, in a repo this route's wish does not otherwise open

⇒ and it is **wholly out of the budget-gate wish's scope** — it reaches the review budget not at all.
it is caught here because the lens that found it was this route's, and a find with no record is a
deletion in a polite coat.

🟡 **no fulcrum is owed.** the deferral is not a judgment call about this design — the work simply
belongs to another behavior. (contrast `F13`, where the deferral *was* a judgment and a fulcrum was
owed alongside its dream.)
