# 🌙 dream: a driver can read a failed CI job's test output through a paved skill

- kind: fix
- owner: this repo (`gh.workflow.logs`) · ehmpathy/rhachet-roles-ehmpathy (`show.gh.action.logs`, `show.gh.test.errors`) — reseed there
- caught 2026-11-18

## .the cue that fired

pr #803 failed four shards. each paved log skill came back empty or broken, and the failures were
read only by `gh api --method GET repos/<repo>/actions/jobs/<id>/logs --allow-escape-sequences`
piped to `rhx teesafe`.

## .the gap, precisely

- `show.gh.test.errors` and `show.gh.action.logs` print a job header and no body. `--full` prints
  `the response contains terminal escape sequences; pass --allow-escape-sequences`: the skill calls
  `gh` with no tty and never passes that flag
- `rhx gh.workflow.logs` fails on every call with `unknown argument: --skill`: `rhx` forwards
  `--skill`, and the script's arg parser refuses it

## .the shape of the fix

- the log skills fetch job logs via `gh api …/actions/jobs/<id>/logs --allow-escape-sequences`,
  strip ansi, and print the jest `●` blocks and the `Tests:` line per failed job
- `gh.workflow.logs` ignores the `--skill`/`--repo`/`--role` args rhx forwards, as other skills do

## .why it is not done in this round

the first lives in another repo; the second is a skill fix outside this route's wish, and the pr
deadline held the round.
