# 🌙 dream: rebase take must not drift a lockfile past the side it took

- kind: reseed
- owner: ehmpathy/rhachet-roles-ehmpathy (role=mechanic, skill=git.branch.rebase)
- caught: 2026-11-18

## .the cue that fired

a rebase of #765 onto main conflicted only in `pnpm-lock.yaml`. `rhx git.branch.rebase take
--whos theirs pnpm-lock.yaml` auto-ran `lock refresh`, and the staged lockfile differed from main's
while `package.json` matched main byte for byte.

## .the gap, precisely

the refresh re-resolves rather than keeps the side taken:

- `with-simple-cache` 0.17.3 → 0.15.1 (a downgrade, a peer of `simple-on-disk-cache`)
- `@smithy/core` 3.39.0 → 3.41.0

so a branch whose `package.json` equals main still ships a lockfile diff that changes deps. the
only cure was to stage main's lockfile by hand, which a global commit block also refuses.

## .the shape of the fix

- when `package.json` (and patches) equal the taken side after the merge, `take` keeps that
  side's lockfile verbatim and skips the refresh
- else refresh with `pnpm install --lockfile-only` and assert no installed version moves backward
  versus the taken side; refuse with the downgraded packages named
- a `--refresh skip` flag for the case a human knows the taken side is right

## .why it is not done in this round

the skill lives in another repo; this route's stone is a blueprint review, not mechanic tools.
