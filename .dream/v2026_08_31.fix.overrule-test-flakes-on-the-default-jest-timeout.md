# 🌙 fix → this repo: the malfunction-overrule test flakes on jest's default timeout

**kind**: fix · **owner**: this repo — `src/domain.operations/route/stones/setStoneAsPassed.test.ts`
· **caught** 2026-08-31

- **why it was not fixed at first** — the round was briefs-only by the wish's own hard bound, and
  the repair is a `.test.ts` edit. caught rather than done
- **dispatched** — 2026-08-31, `ehmpathy/rhachet-roles-bhrain` #398, status `QUEUED`
- **fixed** — 2026-08-31, the wisher lifted the briefs-only bound (*"why dont you just fix the
  flakes now?"*)
  - the repair is one line in `jest.unit.config.ts`: `testTimeout: 30_000`

## 🔴 .the clamp climbed twice, and the second climb is the lesson

| attempt | the bound | why it was not enough |
|---|---|---|
| 1. this dream's own prescription | `, 30_000` **per case** | a list of ~40 annotations, maintained by hand |
| 2. the first repair | `jest.setTimeout` **per file**, in 3 files | 🔴 **still a hand-maintained list**, one level up |
| 3. what landed | `testTimeout` in the **unit config** | cannot be forgotten |

🟡 attempt 2 felt like a boundary clamp and was not:

- it required a grep to decide which files were "in the class"
  - and that judgment is precisely what a bound is supposed to retire
- the tell: the third file was clamped on a guess — *"it drives stones through `setStoneAsPassed`,
  so it probably spawns"*
- ⇒ a bound you must reason your way into is a list

⇒ so the next unit test that spawns a subprocess flakes under either of the first two, because
nobody will remember. under the third it does not.

🟡 and the wisher's question is the one worth a record — *"why not just set the timeout to 30s
everywhere? for units"*:

- the answer is that there was no reason, only an unexamined instinct to scope the fix narrowly
- ⇒ **the narrow scope was the defect, never the caution**

the cost is honest and small: a fast test does not become slow because it is allowed to be; the
only price is that a genuinely hung test takes 30s to fail rather than 5s.

verification: `--what unit` 1029/1029, plus types · lint · format green.

## .the cue that fired

a scoped unit run over `path://src/domain` — 165 suites — failed one test of 1,380:

```
● setStoneAsPassed › [case5] guard with malfunctioned reviewer
  › [t1] overrule marker present › passes despite malfunction (human overruled)

thrown: "Exceeded timeout of 5000 ms for a test."
```

**it took 5188 ms against a 5000 ms limit — a 4% overrun.** the same file, run alone, passes all
12 tests in 11 s. two earlier runs of the same 165-file scope passed 1,380/1,380.

## .the gap, precisely

the test spawns a real guard subprocess and waits for its verdict. that is legitimate work, and it
sits just under jest's 5 s default when the machine is idle:

| the case | what it does | measured |
|---|---|---|
| `[case6] [t1]` overrule a **constraint** | the same spawn-and-wait | 3890 ms ✅ |
| `[case5] [t1]` overrule a **malfunction** | the same spawn-and-wait | **5188 ms** 🔴 |
| `[case5] [t0]` no overrule marker | shorter path | 2061 ms ✅ |

⇒ so the failure is contention, never logic. under 164 concurrent suites the same call crosses
a line it clears with room to spare in isolation.

🟡 **the shape is the hazard, not the number.** a test whose honest runtime sits at 78% of its
limit will fail on a loaded CI box and pass on the author's laptop — which reads as a defect in the
code under test rather than in the budget granted to the test.

## .the shape of the fix

give the spawn-and-wait cases an explicit timeout, so the budget is a stated decision rather than
an inherited default:

```ts
then('passes despite malfunction (human overruled)', async () => {
  // …
}, 30_000);
```

⇒ **state it on every case in the file that spawns a guard**, never on the one that failed. the
neighbour at 3890 ms is the same test one busy moment away, and a fix applied to the observed
failure alone leaves the class open — which is `rule.require.clamp-edge-cases` (ehmpathy/mechanic)
almost verbatim: clamp the boundary, not the single value that broke.

**the alternative, if a bound is judged wrong:** make the guard spawn injectable so the unit test
need not pay real process time. that is the better artifact and a much larger change; the timeout
is the honest fix for today.

## 🔴 .the prediction was confirmed, twice over — 2026-08-31, same day

this dream argued *"the neighbour at 3890 ms is the same test one busy moment away, and a fix
applied to the observed failure alone leaves the class open."* a later run of the same 118-file
scope failed three tests:

| the case | measured | what it is |
|---|---|---|
| `setStoneAsPassed [case6] [t1]` overrule a constraint | 6462 ms 🔴 | the exact neighbour this dream named at 3890 ms. it crossed |
| `stepRouteDrive [case6] [t0]` fewer than 7 hooks | 5002 ms 🔴 | a second file, never named here |
| `stepRouteDrive [case6] [t1]` 7 or more hooks | 5011 ms 🔴 | same |

⇒ **the class is wider than the one file it was filed against:**

- the same 108 route files pass 922/922 in isolation, in 21 s — so the mechanism is contention,
  as this dream said
- 🟡 so the fix must widen too
  - `stepRouteDrive` loops `stepRouteDrive({ when: 'hook.onStop' })` three and seven times, each
    a real spawn
  - ⇒ the budget it needs scales with the loop count, so its honest runtime sat even closer to
    the 5 s line than the case first measured

**every test in this repo that spawns a real subprocess owes an explicit timeout**, in
`setStoneAsPassed.test.ts` and `stepRouteDrive.test.ts` alike. that is
`rule.require.clamp-edge-cases` exactly: clamp the boundary, never the single value that broke —
and here the boundary produced two more failures before the first fix landed.

## .what makes this worth a record rather than a retry

the run that surfaced it was a **verification** run — its whole job is to say whether the round's
edits hold. a flake there reports a defect that does not exist, and the cost is a driver who hunts
for one. that is the same class as an overflowed reviewer: **a process that rendered no verdict,
dressed as a verdict.**
