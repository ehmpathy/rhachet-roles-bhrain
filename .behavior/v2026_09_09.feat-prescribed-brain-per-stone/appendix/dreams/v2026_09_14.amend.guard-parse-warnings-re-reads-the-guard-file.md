## .the gap, precisely

`getGuardParseWarnings` (`src/domain.operations/route/guard/getGuardParseWarnings.ts:41`) does its own `fs.readFile` of the guard file, independently of `parseStoneGuard` which already read it via `getAllStones`. every `stepRouteDrive` invocation (onBoot, every onStop turn, direct-mode) re-reads and re-walks the guard file line-by-line — a second, simplified state machine (a `flatMap`) beside the real parser's stateful loop.

the two share `asDeclaredGuardKey`/`asGuardKeyValue` (the low-level primitives), so key-match logic cannot drift independently. the perf cost is bounded: guard files are small, and `fs.readFile` on a recently-read file hits the page cache.

## .the shape of the fix

have `parseStoneGuard` collect warnings inline during its extant single-pass scan and return them alongside the guard (`{ guard, warnings }`). this eliminates the second file read + second line scan. the caller-count cost: 2 callers and ~25 test call sites need a return-shape change to carry a value only the drive renders.

alternative: a narrower fix that memoizes `getGuardParseWarnings` per (path, mtime) within a single process invocation.

## .why it is not done in this round

the return-shape change across 2 callers and ~25 test call sites is CLEAN but not SMALL — it ripples past the diff this feature opened. the two implementations share primitives and cannot drift on key-match logic. the perf cost is bounded by page-cache reuse on small files.

## 🔴 .amended 2026-09-15 (i016 r011) — it is a VIOLATED COST-CONTRACT, not just duplication

a fresh architectural pass sharpened WHY this should be prioritized. it is not merely a
duplicate read — it is an ASYMMETRY within this feature's own bound:

- `applyStoneBrainOnEntry` short-circuits before any I/O when a stone declares no `brain:`
  — case=10's "a stone that never asked for this pays naught" contract, built AND tested.
- but `getStoneGuardWarns` → `getGuardParseWarnings` (a NEW file this PR introduced, per git
  status) has no equivalent guard: for ANY stone with a `.guard` file it does a second
  `fs.readFile` + full line-walk on every tick, regardless of whether that guard declares
  `brain:`/`model:` or has any dropped key at all. the near-miss detector covers ALL known
  keys, not just brain-related ones.

⇒ so the same PR that built one half (`applyStoneBrainOnEntry`) against the "pays naught"
bound shipped a companion half (`getStoneGuardWarns`) that adds a read + walk to EVERY guarded
stone in EVERY repo, whether or not that repo ever heard of `brain:`. graded a NITPICK by
`rule.forbid.overzealous-blockers` (no user harm, no wrong output — an avoidable read + walk),
but the parser-merge fix above closes BOTH the duplication and the cost-contract violation at
once, which is the argument to prioritize it as the "two guard parsers" debt's real driver.

## 🔴 .a SMALLER-scoped fix (i017 r011) — thread the raw content, no 25-call-site migration

a second architectural pass named a narrower fix than the full `{ guard, warnings }` merge:
`getAllStones` already read + parsed the guard's RAW content moments earlier. so instead of the
full return-shape migration, hand back the raw `content` string alongside the parsed
`RouteStoneGuard`, and change `getStoneGuardWarns` to accept an OPTIONAL pre-read `content`. only
`getAllStones` and `getGuardParseWarnings`'s one caller need to change — NOT all ~25 call sites.

⇒ still a contract change (`getAllStones`'s return grows a `content` field, and the warn op grows
an optional param), so it is deferred with the full merge rather than folded into an execution
stone's diff — but it is the cheaper of the two, and the one to reach for first when this is picked
up. the per-tick frequency (every onBoot/onStop/direct for the current stone, not just halted
stones) is what makes it worth the smaller change sooner rather than the full merge later.
