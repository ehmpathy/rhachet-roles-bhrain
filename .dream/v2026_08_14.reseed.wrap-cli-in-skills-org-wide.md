## .deliverable 1 — `rule.require.wrap-cli-in-skills.md`, hoisted org-wide

it currently lives under `repo=.this/`, which claims it is a fact of one repo. it is not. every
claim it makes is about **any** repo that reaches **any** external tool.

the rewrite should carry:

1. **the claim, generalized past "external CLI"** — the honest scope is *any invocation whose
   knowledge lives in the invocation*. four wrappable kinds, all evidenced in that repo:

   | kind | example | why the rule reached it |
   |---|---|---|
   | an external cli | `aws.whoami`, `aws.ec2.get` | the original case |
   | a remote reach | the `duct.*` + `git.grove.*` family | `reach-a-grove-through-its-duct` |
   | a **local play** | `git.grove.push.verify` → `verify.grove.push.layout.play.sh` | `bash <play>` is unallowlisted, so unrunnable |
   | a flag incantation | `git.repo.test`, `git.release` | the flags were the knowledge |

   the third row is the sharpest: the wrapped subject is that repo's **own** executable, with no
   external tool involved at all.

2. **the two arguments as PEERS.** today the second is a buried paragraph, and it is the one that
   makes a robot act:
   - the **practice** argument — reviewable, repeatable, fails loud with the fix
   - the **mechanism** argument — *the permission hook evaluates only the OUTER command string*,
     so `rhx <skill>` passes while the nested `aws ...` stays invisible to it. ⇒ **to wrap is not
     hygiene applied after the work; it is how the work becomes possible.** the allowlist reads
     the outer call, so **a skill is the unit of trust**

3. **the counter-evidence, carried and not buried.** on 2026-07-29, in a session where the rule
   **and** its grove specialization were both booted and had been read aloud, a robot ran raw
   `ssh grove-1` roughly **ten times in one hour**. ⇒ the rule was read, believed, agreed with,
   and lost to a keystroke of convenience. **so the brief is necessary and not sufficient** — a
   preToolUse hook that rejects a bare wrappable invocation and names the skill is the half that
   is absent:

   ```
   ✋ raw `ssh grove-1` — this belongs in a skill
      └─ fix: rhx git.grove.send grove-1 --what '<cmd>'
         why: rule.require.reach-a-grove-through-its-duct
   ```

## .deliverable 2 — `rule.require.name-every-guard.md`

> **an unnameable guard is a guard that has already failed.**

dated evidence, 2026-07-29: a layout check was written as `verify.grove.push.layout.play.sh`. it
was correct, complete, and **unrunnable** — `bash <play>` is not on the allowlist, so it could not
be invoked, so it never ran, so the defect it existed to catch (a `src/src/` shadow copy) survived
**three** credited fixes.

**the check's absence was invisible because the check existed.** a file that asserts a truth
nobody can invoke is worse than no file, because its presence reads as coverage.

this is a **nature** invariant, not a preference about which tools to use: it follows from what a
check is for. it generalizes far past clis — to tests, lint gates, and diagnostics.

## .deliverable 3 — `template.wrapped-cli-skill.sh`

the rule's `.how` lists five things a skill owes:

1. `--env` whose credentials come from keyrack
2. the active account/identity reported **before** any result
3. tree-struct output
4. errors that name the fix, not the symptom
5. a `.what` / `.why` header, and a `guarantee` block that says read-only when it is

**five requirements in prose is a checklist nobody diffs against.** `domain.terms/` already proved
the better shape (`template.domain-term.md`): a concrete skeleton to copy, so the contract is
satisfied by construction rather than by recall.

🟡 item 5 smuggles in a claim worth its own line. a skill that declares

```
# guarantee:
#   - READ-ONLY with respect to the repo; writes only under temp dirs it makes, and removes both
```

has told a human what it **cannot** do — which is what makes it allowlistable without a read, and
is the whole economic argument for the rule.
