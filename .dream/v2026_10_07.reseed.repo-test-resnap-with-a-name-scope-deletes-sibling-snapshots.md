# 🌙 dream: a `--resnap` scoped by `name://` deletes every other snapshot in the file

- kind: reseed
- owner: ehmpathy/rhachet-roles-ehmpathy (role=mechanic — the `git.repo.test` skill)
- caught: 2026-10-07

## .the cue that fired

a repair agent ran `rhx git.repo.test --what integration --scope path://…stepRouteDrive.integration.test.ts --scope name://case16 --resnap --mode apply`
to write three new snapshots in one case. the run passed — and the `.snap` file lost every key
outside `case16`. the agent noticed only because a `git diff` showed a wholesale deletion, then
re-ran the whole file with `--resnap` to restore them.

## .the gap, precisely

- `--scope name://x` maps to jest `--testNamePattern`; `--resnap` maps to `-u`
- under `-u`, jest treats each snapshot whose test did not run as obsolete and removes it, so a
  name filter plus `-u` deletes all keys of the file the filter skipped
- the skill's own help recommends the narrow stack (`--scope path:// --scope name://`) as the
  fastest loop, and recommends `--resnap` to update snapshots — the two recommended moves compose
  into silent data loss. the run exits 0 and prints naught about it
- a driver who does not diff the `.snap` ships a suite that lost its coverage, and the next
  reviewer reads "snapshot deleted" as an intentional change

## .the shape of the fix

- refuse `--resnap` beside any `name://` scope, exit 2, and print the fix: drop the name scope,
  keep the path scope (a whole-file resnap)
- clamp: a temp repo with one test file of two cases, each snapshotted; run the skill with
  `--scope name://case1 --resnap`; assert the refusal, and that case2's key survives

## .why it is not done in this round

the skill lives in `rhachet-roles-ehmpathy`, not this repo. a tree adopts only what is scoped to
itself; this repo's copy is a linked dependency.
