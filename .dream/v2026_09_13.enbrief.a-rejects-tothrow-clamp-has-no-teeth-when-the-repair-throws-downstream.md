# 🌙 dream: a `.rejects.toThrow()` clamp has no teeth when the defect throws downstream anyway

- kind: enbrief
- owner: bhrain/role=mechanic (`code.test/pitofsuccess.errors/`)
- caught: 2026-09-13

## .the cue that fired

i wrote a regression clamp for a `rule.forbid.failhide` repair, reverted the repair to prove the
clamp bit, and **the clamp stayed green while two unrelated peer suites went red.**

the operation was a findsert of a fixed-content `.gitignore`. the repair was a rethrow of any
non-ENOENT read error, where the defect swallowed every error via `.catch(() => null)`. my clamp put
a **directory** at the target path and asserted `.rejects.toThrow()`.

```
repaired:  readFile(dir)  → EISDIR → rethrown  ⇒ throws
swallowed: readFile(dir)  → EISDIR → null
           writeFile(dir) → EISDIR            ⇒ throws ANYWAY
```

⇒ **both arms throw.** the assertion could not tell them apart, so it clamped naught.

## .the gap, precisely

> a `.rejects.toThrow()` is an assertion about the EXISTENCE of a throw. a failhide repair is a
> claim about the **origin** of one. those are different propositions, and the loose form cannot
> express the second.

the shape generalizes past this operation. it fires wherever a swallowed fault is followed by a
second operation that hits the same bad state:

| the repair | the downstream op that throws anyway |
|---|---|
| rethrow a read error | the write that follows onto the same path |
| rethrow a parse error | the consumer that dereferences the unparsed value |
| rethrow a lookup error | the caller that asserts the absent record is present |

**in each, the defect still ends in an exception — later, from a different site, with a worse
message.** that is precisely what makes a failhide expensive, and precisely what makes the loose
clamp useless: the symptom the clamp watches survives the defect.

⚠️ **the two peer suites had teeth and their authors may not have known why.** they asserted
`.rejects.toMatchSnapshot('error-eisdir')` — a snapshot of the whole error object. it bit only
because the two faults differ in fields the snapshot happened to record. a snapshot is teeth by
**accident**; a named field is teeth by **construction**.

## .the shape of the fix

a brief under `code.test/pitofsuccess.errors/`, paired with the extant `rule.forbid.failhide` and
`rule.require.failloud`. its test:

> **if the defect were present, would this assertion still pass?** for a throw assertion, ask it
> again narrower: *would a DIFFERENT throw, from a different site, satisfy this?*

and its rule: **a clamp on a rethrow asserts which fault propagated, never that one did.** name the
field that parts them —

```ts
// 👎 no teeth — the swallowed path throws too, from the write
await expect(findsertGitignore({ dir, content })).rejects.toThrow();

// 👍 teeth — `read` is reachable only when the READ error propagated
expect(error?.code).toEqual('EISDIR');
expect(error?.syscall).toEqual('read');
expect(error?.syscall).not.toEqual('open');   // the swallowed path's write
```

🔴 **and the general lesson is the larger half:** the rule that caught this is not a test-style
preference, it is `rule.require.clamp-edge-cases`' own dogfood step — *revert the fix, watch it go
red.* i ran that step, **and it is the only reason i learned the clamp was empty.** a clamp adopted
on inspection would have shipped, read as protection, and guarded naught.

## .why it is not done in this round

**safe, and not clean.** the brief belongs to `ehmpathy/role=mechanic`, a different tree from the one
this route's stone is scoped to (`src/**`, `blackbox/**`), so it is a re-seed rather than an in-diff
fix. the instance is repaired and clamped here; only the generalization is deferred.
