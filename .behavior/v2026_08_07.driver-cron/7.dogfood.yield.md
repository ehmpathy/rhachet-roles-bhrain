## what was observed

### the reach-fault reproduces — it is not a one-off

the earlier dogfood (2026-09-09) hit the same `sayToClone` fault once. this round hit it
again, twice more, deterministically correlated with ONE condition: **every fault occurred
while this driver session was mid-tool-call (an active turn)**. every clean tick occurred
in a brief idle gap between tool calls.

### root cause — corrected mid-round

first pass diagnosed the cause as `CLONE_SUBMIT_DELAY_FLOOR_MS` (rhachet's fixed 50ms
paste-to-Enter delay) too short under host load, and patched it locally to 300ms
(`node_modules`, not committed — a stopgap for this host only). that patch reduced but did
NOT eliminate the fault — a later tick reproduced it even at 300ms, so the theory does not
fully hold.

a human review then supplied a better-fit diagnosis: **claude code queues a message sent
while a turn is in progress** (shown above the input line, dispatched once the current
turn ends) rather than reject it. `rhx clone say`'s self-verify (`getCloneSubmitLanded`)
polls only the target's TRANSCRIPT with a fixed 15s timeout — a message that is correctly
queued, but whose target's current turn runs longer than 15s (true for every fault repro
here — this session's tool chains routinely exceed that), times out and is misreported as
a hard failure, even though the message will land safely once the current turn ends. this
fits 100% of the observed data far better than a paste-commit race: every fault happened
mid-turn; every success happened at an idle gap.

### upstream reported

filed, then corrected, `ehmpathy/rhachet#527` with both the original (likely wrong)
delay-floor theory and the corrected queue-vs-poll-timeout diagnosis, plus the ask: `say`'s
verify needs to read the pty SCREEN STATE (input line vs the queued-messages region vs
absent), not only the transcript, so a safely-queued message is not misreported as a
failed dispatch.

### the RouteReminder daemon's OWN design held up under the fault

this is the real proof this stone existed to get: when the fault fires, the daemon's
crash-loud design works exactly as designed —

1. `sayToClone` throws with full context (addr, exit code, stderr)
2. `runRouteReminderDaemon` durably logs the crash (route-level, monotonic-indexed) before
   the process exits
3. the process exits — no retry storm, no infiniloop
4. `route.reminder.get` reads the log presence + dead pid and reports the true state
   ("gone quiet (self-exited or crashed)"), never a false "live"
5. no orphan pid was ever left behind — `kill -0` on a self-exited daemon's pid always
   failed, and `route.reminder.del` correctly no-op'd on an already-dead daemon

so the vision's U3 guarantee (self-halt, no infiniloop, no clog) is proven under a REAL,
repeatedly-reproduced upstream fault — not just in a fake-sayToClone unit test. the
fault's root cause lives in rhachet (now reported, with a corrected diagnosis), not in
this repo's own reminder logic.
