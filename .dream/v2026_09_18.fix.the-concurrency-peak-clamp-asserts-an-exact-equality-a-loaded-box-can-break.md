- **caught** = 2026-09-18, from `.behavior/v2026_09_17.fix-budget-grant-needs-urgent-concession`,

## .the cue that fired

the full acceptance sweep failed **1 of 3586**, at `[case1]`:

```
● driver.route.peer-concurrency.acceptance › … › CLAMP: [case1] all four l1 reviewers are in flight at once

  Expected: 4
  Received: 3

  > 233 |         expect(observed.l1Peak).toEqual(4);
```

⇒ `observed.l1Count` **held at 4** on the same run. all four lanes ran; they were simply never all

**re-run in isolation: 5 suites, 124 tests, 0 failed, 293s.** ⇒ a load flake, and the full sweep it
failed under took **2215s across 131 suites** on a saturated box.

## .the gap, precisely

`l1Peak` is `computeMaxInFlight({ windows })` — the maximum **wall-clock overlap** of the lanes'
open/close windows. so an exact equality on it makes two claims at once, and only one is an oracle:

| the half | is it the oracle? | can the scheduler break it? |
|---|---|---|
| *"at least 4 were aloft together"* | ✅ **yes** — it refutes the serial arm | 🔴 **yes.** under load, lane A closes before lane D opens |
| *"no more than 4 were aloft"* | 🔴 no — there are only 4 lanes, so it is free | no |

⇒ **the exact form pins a ceiling that costs naught and a floor that a loaded box can push under.**
the failure is not the pour's; it is the measure's.

🔴 **and the file already speaks BOTH dialects, on one measure, in one author's hand:**

| site | the form |
|---|---|
| `:233`, `:401`, `:509` | `expect(observed.l1Peak).toEqual(4)` |
| `:598` | `expect(observed.l1Peak).toEqual(2)` |
| `:394` | `expect(observed.l3Peak).toEqual(1)` |
| 🔴 `:751` | `expect(observedAfterAppend.l1Peak).toBeGreaterThanOrEqual(2)` |
| 🔴 `:896` + `:897` | `toBeGreaterThan(1)` **and** `toEqual(2)` — belt and braces |

⚠️ **`:751` is the sharpest row.** its own comment reads *"all three must be aloft together"* and its
assertion is `>= 2`. ⇒ the author who wrote it had already met the fragility and chose a floor — and
the three `toEqual(4)` sites above it were left as they stood.

### 🟡 the split is NOT uniform, and a blanket rewrite would be wrong

`:394`'s `toEqual(1)` is a **different claim in kind**: it asserts a declared bound of 1 is HELD —
a ceiling on a group whose concurrency is configured to 1. load cannot push a peak below 1 while a
lane ran at all, so that site is sound as written.

⇒ **the defect is narrow: an exact equality where a FLOOR is the oracle** — the unbounded-level
sites, never the bounded-group ones.

## .the shape of the fix

1. at each unbounded-level site, assert the floor that IS the oracle, and say what it refutes:
   ```ts
   // >= 2 refutes the serial arm, which peaks at 1. the exact width is the pour's
   // announced bound, and `[case…]` already clamps that from the announce
   expect(observed.l1Peak).toBeGreaterThanOrEqual(2);
   ```
2. keep the **width** claim where it belongs — on the pour's **announce**, which is deterministic
   text rather than a wall-clock race. `.dream/v2026_09_13.feat.a-shared-concurrency-bound-topology-both-models-derive-from.md`
   already argues this exact move: *"asserts the two models agree (observed peak === announced
   bound)"* ⇒ 🔴 **read that dream first; this one may be a slice of it rather than a peer**
3. leave `:394`'s `toEqual(1)` alone, and add one line that says why it is exempt
4. 🟡 **and state the dialect rule once**, so the next author does not re-derive it: a peak is a
   floor claim; a configured bound is an equality claim

## .why it is not done in this round

the SAFE/CLEAN test (`rule.always.fix-forward-under-scouts-honor`):

- **safe?** 🔴 **no.** a peak clamp is a behavior claim about the pour. `toEqual(4)` →
  `toBeGreaterThanOrEqual(2)` genuinely **loses oracle strength** — it would no longer catch a
  regression from 4-wide to 2-wide. the honest fix moves that width claim onto the announce, which
  is a second edit in a second place, and a partial fix ships a blind clamp
- **clean?** 🔴 **no.** `driver.route.peer-concurrency.acceptance.test.ts` is untouched by this
  behavior's diff. the one file this round changed on that path is `runStoneGuardReviews.ts`, and
  the change there is a **pure synchronous extraction** — `computeReviewCompleted` returns
  `passed || (constraint && blockers > 0)`, byte-equivalent to the inline conjunction it replaced,
  with no `await` and no reach into the pour

⇒ **defer**, and it owes **no fulcrum**: the deferral is about SIZE and BLAST RADIUS, never a
judgment about ripple this route reserved. the vision named no concurrency fork.

⚠️ **the cost of the deferral, on the record:** the full acceptance suite carries a ~1-in-N flake
under load, at a site whose failure reads as a **concurrency regression**. ⇒ the next driver to meet
it will spend the diagnosis this dream already holds — which is why the isolation result and the
purity argument are written down above rather than left to be re-derived.
