# 🌙 dream: reset the drive-blocker count when the stone changes

**kind** = fix · **owner** = `ehmpathy/rhachet-roles-bhrain` · **caught** 2026-09-09

## .the cue that fired

a line-by-line read of `stepRouteDrive.ts`'s `onStop` branch, done to settle fulcrum `F7` of
`.behavior/v2026_09_09.feat-prescribed-brain-per-stone`. the read was for a **different** question —
*does a stone-entry signal exist?* — and it walked past this on the way.

## .the gap, precisely

`DriveBlockerState` carries `{ count, stone }`, and **`setDriveBlockerState` increments the count
unconditionally, whatever the stone:**

```
src/domain.operations/route/drive/setDriveBlockerState.ts:22-28

  const stateBefore = await getDriveBlockerState({ route: input.route });
  const stateAfter = new DriveBlockerState({
    count: stateBefore.count + 1,     // 🔴 never compared against stateBefore.stone
    stone: input.stone,
  });
```

at the time this was caught, `.stone` was **written and never read** — its only consumer would be a
reset, and no reset existed.

🔴 **.amended 2026-09-14 (i010 r011)** — `.stone` is NO LONGER a dead field. `applyStoneBrainOnEntry`
now reads it every hook tick as the brain-dispatch entry edge (`stateBefore.stone !== stone.name`),
and `setDriveEntryStone` is a second writer that sets it with the count preserved. so the "dead field"
note below is stale: the field is live for entry detection. **the count-never-resets bug it describes
is still open** — the 21-block cutoff still accumulates across stones — but the fix shape must now
account for TWO writers of the file, not one (see the shape-of-fix amendment below).

⇒ the consequence is at `stepRouteDrive.ts:297-299`:

```
  const maxBlocks = 21;
  if (state.count > maxBlocks) { ...exit 1, malfunction: "the route is stuck"... }
```

**the 21-block cutoff is a per-ROUTE budget where its own message claims a per-STONE one.** a route
that spends 15 stop-blocks on stone 1 and 7 on stone 2 halts as *"stuck"* on a stone it has visited
seven times.

### .the checkable evidence

- `.stone` is set at `setDriveBlockerState.ts:27` and defaulted at `getDriveBlockerState.ts:24`
- 🔴 **no branch anywhere compares it.** a grep for a read of the field returns no hit — the tell of a
  dead field
- the reset, if it existed, would be exactly the compare `F7` now proposes to reuse for stone entry

## .the shape of the fix

🔴 **.amended 2026-09-14 (i010 r011)** — both writers now go through
`mutateDriveBlockerState({ route, project })`, so the fix is one branch in
`setDriveBlockerState`'s `project`:

```ts
mutateDriveBlockerState({
  route: input.route,
  project: (before) => {
    const stoneChanged = before.stone !== null && before.stone !== input.stone;
    return new DriveBlockerState({
      count: stoneChanged ? 1 : before.count + 1,
      stone: input.stone,
    });
  },
});
```

⚠️ `setDriveEntryStone` (the SECOND writer) preserves the count, so it is unaffected — the reset
belongs to the push counter alone. the original single-writer shape was:

```ts
const stateBefore = await getDriveBlockerState({ route: input.route });
const stoneChanged = stateBefore.stone !== null && stateBefore.stone !== input.stone;
const stateAfter = new DriveBlockerState({
  count: stoneChanged ? 1 : stateBefore.count + 1,
  stone: input.stone,
});
```

⚠️ **`stateBefore.stone !== null` matters** — a fresh state has `stone: null`, and without the guard
the first hook of a drive reads as a stone change and starts at 1 rather than 1. harmless here, and
it stops to be harmless the moment the same compare feeds a brain switch.

**the clamp it owes:** two `onStop` calls on stone A, then one on stone B → count is 1, never 3.
the extant `getMaxStoneGuardIteration` tests are the shape to follow.

## .why it is not done in this round

**SAFE — no.** the cutoff is a live safety mechanism on every route in this repo. to change when it
fires is to change when a stuck drive escalates to a human, which is behavior far outside a vision
stone's diff.

**CLEAN — no.** it ripples into the 21-block semantics, its message text (*"the route is stuck"*),
and any snapshot that pins a count.

⇒ both answers are no, so `rule.always.fix-forward-under-scouts-honor` sends it here rather than into
the diff. and the deferral is for **safety**, not size — so it earns a dream and no fulcrum: there
was no judgment call to reserve for the wisher.
