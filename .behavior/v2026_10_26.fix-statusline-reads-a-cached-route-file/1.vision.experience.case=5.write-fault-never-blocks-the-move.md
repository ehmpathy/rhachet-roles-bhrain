# case 5 — a status write fault never blocks the move

sharp · chosen alterpath (rare, and tolerable — the move still lands) · cell bound-once · stale ·
route moved · one · faults · one

## .narrative

the driver runs `rhx route.stone.set --stone 1.vision --as passed` on a box whose disk just
filled. the usual passage tree prints — `1.vision` passed, the next stone named — so the driver
moves on. beneath it sits one extra row:
`🗿 status line not refreshed: ENOSPC at $route/.route/.status.line.json — free space, then rhx route.drive`.

the human glances down and sees the old stone with `· stale, rhx route.drive`. they free some
space, run the command once, and the line catches up. at no point did a full disk stop the route;
it only made the display admit it was behind.

## .behind the move

the passage append (a few bytes) landed; the status file's temp write failed. the passage is the
state and the file is a display cache, so a cache fault never vetoes the state it displays. the
prior file is untouched, so the reader's `-nt` test sees a ledger newer than it (case 3). this cell
is the densest of the write path: it crosses the passage ledger, the status writer, the fs, and the
reader in one walk.
