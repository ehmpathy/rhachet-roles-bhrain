# case=7 — the guard that still carries a `hashbar:`

**cell** `D1 = route-author` · **feel** sharp · **care** alterpath (chosen)

> the deletion's blast radius. the only cell whose actor is not the driver.

## .the narrative

a route author in a downstream repo wrote a `.guard` months ago with `hashbar: 0`, because at the
time that was the one way to stop the timer from a reset on every repair. they upgrade the package.
the key no longer exists.

three outcomes are available, and they are not equally kind:

| the guard does | what the author experiences |
|---|---|
| **throw on the unknown key** | their whole route halts on a key that was correct when they wrote it. loud, and hostile |
| **ignore it in silence** | the route runs. they never learn the key is dead, and they carry it forward into the next guard they write |
| **accept and say so once** (best guess) | the route runs, and one line tells them the key is retired and why they no longer need it |

```
🗿 hashbar is retired
   │
   ├─ found in 3.3.blueprint.guard → review.self.has-questioned-assumptions
   │
   ├─ the trigger report is hashless now, so a repair never resets the timer
   │  ├─ hashbar was the workaround for exactly that
   │  └─ it never worked — the persist branch tracked the newest trigger, so a
   │     new hash reset it anyway. the defect it aimed at is now gone at the root
   │
   └─ safe to delete the key
```

### .the "aha"

> **`hashbar: 0` was never a config. it was a bug report, written in yaml — and a fix that never
> fired.**

every author who set it was routed around the defect this wish repairs. so the retirement message
is not a deprecation notice — it is the answer to a question they asked months ago.

### 🔴 .and the workaround never worked, at any value

verified first-party by this round's `r1` self review. the branch that is meant to make the timer
persist reads (`getSelfReviewChallengeDecision.ts:110-117`):

```ts
if (count > hashbar && newest) {
  const elapsed = Date.now() - newest.sinceMtime.getTime();
```

`getSelfReviewTriggeredCount.ts:68` defines `newest` as the **maximum** `.since` mtime — and a fresh
hash mints its `.since` at `Date.now()`, so it is instantly the newest. **the persistent branch
measures elapsed against the trigger it just created.**

the docblock at `:23` promises the other predicate — *"any triggered file > 30s allows promise"* —
which would need `oldest`, or a `.some()` across the set. ⇒ **at `hashbar: 1` the second report
crosses the bar; at `hashbar: 0` the first one does. either way every subsequent hash resets.**

⇒ **this changes the retirement line's argument.** it is not *"you no longer need this"* — it is
**"this never did what you thought, and now the reason you wanted it is gone."** the second is the
honest sentence, and the kinder one: an author who reads the first will wonder why their route still
misbehaved for months.

⚠️ **it also removes the last reason to keep the key.** the migration was already free by
measurement (below); it is now free by argument too — **no caller can depend on a behavior the code
does not implement.**

## .the measurement that bounds this

a `Grep` for `hashbar` over `**/*.guard` across this repo returns **no match**. the key is declared
at `RouteStoneGuard.ts:25` and set by no live guard here.

⇒ so in **this** repo the migration is free. it is demoed anyway because this package publishes,
and a downstream `.guard` is invisible to that measurement. **an unmeasurable population is the one
you write the kind path for.**

## 🔴 .the sharper question underneath — asked, MOOTED, then RE-OPENED

`hashbar` is one of two knobs the wish touches, and the other — the 30s threshold — was **never
configurable at all**. the question this cell raised was: if the timer lives on, is the threshold
worth a place on the `.guard`, so a route with a large artifact can ask for more patience?

⇒ best guess was **no**: a knob is how `hashbar` became a bug report. flagged as `F06`.

**the arc, because this cell is where the mootness was written down:**

| | `F06`'s state | why |
|---|---|---|
| `S11` — drop the clock | 🌙 **moot** | no threshold left to expose. and the mootness read as the strongest possible form of the guess |
| 🔴 `S13` — block only within 30s of the ask | 🔴 **RE-OPENED**, at 85% | **a 30s threshold exists again**, and the fork has its operand back, unchanged |

🔴 **so the claim this section made was falsified within a day, and the failure is instructive.** it
read: *"the question 'does the mechanism that lives on earn the knob the deleted one had?' is answered
by the fact that the mechanism does not live on."* **the mechanism lives on.** ⇒ **a 🌙 MOOT marker is
more dangerous than a ✅ RULED one** — a ruled fulcrum invites a re-read of its verdict; a moot one
asserts *the question itself is gone*, so nobody re-checks the premise that killed it.

🟡 **and the guess is strengthened rather than weakened by the reversal.** under `S13` a mis-set
threshold costs *a prompt shown, or not shown, to one driver once* — never a held driver. so the
knob's whole motive (a large artifact deserves more patience) is gone, and what a large artifact now
wants is a **longer default**, which is an argument about the number rather than about per-route
override.

⇒ so this cell's migration line has **two** retirements to state rather than one, and they differ:

| the key | why it retires | what a `.guard` in the wild carries |
|---|---|---|
| `hashbar:` | a declared knob, set by no live guard here, and 🔴 **it never delivered its documented behavior at any value** | accepted with one retirement line |
| the 30s threshold | 🔴 **it does not retire.** `S13` kept it, on a new job — it decides who hears a paragraph, never who passes | 🔴 **naught to migrate**, because it was never a knob. no author could have set it |
