# 🧩 .brief.article: `inventory`

## .what

an **inventory** is the exhaustive enumeration of a concept's entries, when those entries are
**enumerable** — one document per entry, addressed by its **coordinates** in the concept's
dimensions, **by reference only**.

```
inventory.of=$concept._.md                                    # the summary — axes, counts, gaps
inventory.of=$concept.$dimension=$position.md                 # one entry per cell
inventory.of=$concept.$dimension=$position.$dimension=$position.md
```

it is what **itemize** produces. `itemize` is the verb; `inventory` is the noun — exactly as
`catalogize` → `catalog`, `articulate` → `article`, `demonstrate` → `demo`.

---

## 🔬 the distinction that defines it — per-entry content

the librarian already has a catalog (organizational) and a demo (relational). the line between an
inventory and a catalog is **what each entry carries**:

| document | enumerates | each entry carries | the reader gets |
|---|---|---|---|
| **inventory** | every cell the axes generate | **a reference only** | the address. dereference to learn more |
| **catalog** | every member | a reference **+ a preview** | a feel for each concept **without** a dereference |
| **example** (`example=$id`) | one occurrence, as encountered | the full record of that occurrence | one case, in depth |

⇒ **a catalog is an inventory plus minor demos.** the preview is a small materialization — one
line, one visual, one *what it is* — so a reader grasps the shape of every member from the index
alone.

### the cost each pays

this is not a taste distinction; it is a budget one:

- an **inventory** is cheap and **scales without bound** — refs only, so it grows to any size at a
  fixed cost per entry. it belongs at the **`ref` tier**
- a **catalog** costs more per member, because each preview is inlined. it buys **a dereference
  saved**, which is worth the spend when a reader must know the whole shape at once. this is why
  the librarian's own `kno201.documents._.[catalog]` sits at **say** while the per-archetype
  articles sit at **ref**

### the two failure modes

- **an inventory with previews** is a catalog that has not admitted it — it grows past its budget
  while still filed as cheap
- **a catalog with no previews** is an inventory with extra ceremony — it costs a reader a
  dereference per member and pretends to have saved them one

### ⚠️ completeness is common to both, not the line

a natural guess is that a catalog is partial and an inventory is a census. **that is wrong**, and
the correction is worth a permanent note: the periodic table and *Systema Naturae* — the
librarian's own catalog exemplars — are exhaustive by intent.

both archetypes enumerate fully. and there is a second reason to prefer the per-entry-content
line: **completeness is a claim about the world; per-entry content is a property of the
document.** a reviewer verifies the second with a read, and can never fully verify the first.

### what exhaustiveness still buys, in either

because the space is generated from the dimensions **before the next entry is collected**, an
empty cell is a **discovery** rather than a silence. a doc assembled from whatever was found can
never report absence — in it, "not there" and "nobody looked" are identical.

⚠️ note *the next* entry, never *the first*. the space is generated against the axes **as
currently declared**, and those axes are themselves discovered over time — see
*the axes are discovered over time*, below.

---

## ✨ the two benefits

### 1. accrual — knowledge compounds instead of braids

every fact about a concept has **exactly one address**. when a new fact arrives, its home is
computed from its coordinates, never negotiated.

without an inventory, the same fact lands in whichever document the author had open — and within
a season one concept has five partial homes, none authoritative. that is the **braided trail**
(`philosophy.pavement-saves-nature`): no single edit was wrong, and the damage is entirely
emergent.

with an inventory, accrual is **monotonic**: each entry deepens its own cell and disturbs no
other. the structure holds no matter how many hands touch it, because the coordinates — not the
author's memory — decide placement.

### 2. dereference — you address, you do not search

this is the mechanical benefit, and it is large.

| without | with |
|---|---|
| grep the corpus, read candidates, judge relevance | **compute the path from the coordinates, read one file** |
| cost grows with the corpus | cost is constant |
| you must already know what you seek | the dimensions tell you what is askable |

a reader who knows the coordinates knows the **filename**. no scan, no rank order, no judgment —
a lookup. and a **partial** dereference works too: one glob over `$dimension=$position.*` returns
a whole slice of the space.

⇒ for a brain, this is the difference between **a read and a hunt** — which is the same energy
argument `philosophy.entoolment-is-the-pinnacle` makes: a deterministic address replaces a
probabilistic search.

## 🧷 what makes a concept inventoriable

not every concept earns one. two tests, and both must pass:

> **1. can you name the dimensions, and are the positions on each closed?**

- ✅ **yes** → the coordinate space is generable, so the gap walk is possible
- ❌ **no** → the entries are not addressable by coordinates. use a catalog of what is known, or a
  set of `example=` files

⚠️ **ask this of the entries you hold NOW — never of the entries you might one day hold.** the
next section is why.

### ⚠️ the axes are DISCOVERED over time, not required in advance

test 1 reads as a **gate**, asked once before the first entry lands. that is the misread, and it
is expensive: it disqualifies every concept whose shape is not obvious on day one — which is most
of them.

**an inventory's axes emerge from its entries.** the mechanism is comparison:

1. entries accrue, each addressed on whatever axis is declared so far — often just `case=`
2. you set two of them side by side and ask *"what differs?"*
3. **each answer is a dimension**, and the values you just saw are its first positions
4. declare it in the summary, re-walk the space, and the gaps it reveals were always there

⇒ this is `howto.dimensional-decomposition` run **backwards**. decomposition starts from the axes
and generates the cells; accrual starts from the cells and infers the axes. **both end at the same
box** — one arrives by foresight, the other by hindsight, and hindsight is the common case.

| the box is built | by | when |
|---|---|---|
| **forwards** — axes first, cells generated | dimensional decomposition | the concept's shape is known up front |
| **backwards** — cells first, axes inferred | comparison across accrued entries | the shape is learned as entries arrive |

so an inventory may **begin with one axis** and gain a second the round a comparison reveals one.
a new *position* triggers a re-walk (`rule.require.inventory-for-enumerable-concepts`); a new
*dimension* triggers one too, and it is the same move at a larger radius.

⚠️ **the cost is real, and it is why the summary carries the axes.** a newly discovered dimension
changes every entry's coordinates, so it is a rename of the whole set. that rename is mechanical
only because the axes sit declared on one page — an inventory whose axes live in the author's head
cannot be re-walked at all.

⇒ **the question that survives is not *"could you have named the dimensions in advance?"* — it is
*"can you name them now?"*** if yes, declare them and generate. if the answer changes next round,
that is the inventory at work, not a defect in it.

> **2. does a reader need a preview of each entry, or only its address?**

- **an address suffices** → **inventory**. keep it ref-only and let it grow
- **they need the shape of every member at once** → **catalog**. pay for the previews

an inventory over an open-ended dimension is a **lie**: it claims a census it cannot deliver, and
its empty cells report gaps that may not exist.

## 📌 the precedent — this repo already does it

the `$key=$value` coordinate idiom is established here, not invented:

```
.agent/repo=bhrain/role=learner/briefs/     # repo= and role= are dimensions
domain.terms/term=<x>._.choice.reason.md    # term= is a dimension
```

a path in this repo **is** already a set of coordinates. an inventory simply applies that idiom
where the positions are **closed and known**, so the filetree becomes addressable rather than
merely organized.

---

## 🔗 the ancestry

an inventory is the **morphological box** (zwicky) materialized as a filetree: dimensions on the
axes, one cell per combination, the forbidden combinations named as invariants. the architect's
`howto.dimensional-decomposition` is the discovery move that produces the axes; the inventory is
how the librarian **persists** the result so it can be walked, cited, and checked for gaps.

⇒ decomposition finds the space from the axes down; comparison finds the same space from the
entries up. the inventory keeps it either way.
