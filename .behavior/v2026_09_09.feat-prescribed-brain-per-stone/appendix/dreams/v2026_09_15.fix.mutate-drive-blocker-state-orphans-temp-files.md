## .the gap, precisely

the atomic-write in `mutateDriveBlockerState` writes to a per-pid temp file, then renames it over the
target:

```
src/domain.operations/route/drive/mutateDriveBlockerState.ts:52-54

  const tempPath = `${statePath}.${process.pid}.tmp`;
  await fs.writeFile(tempPath, JSON.stringify(after, null, 2));
  await fs.rename(tempPath, statePath);
```

if the process dies BETWEEN the write and the rename — an OOM-kill, a `kill -9`, a host crash, the
exact failure modes a hook process is exposed to — the temp file is orphaned permanently. no later
run globs and reaps `*.tmp` siblings, so orphans accumulate one per crash-between-write-and-rename.

### .the checkable evidence

- the write path is `mutateDriveBlockerState.ts:52-54` — a temp path, a write, a rename, and no
  cleanup of a prior orphan
- a grep for a reap of `.tmp` siblings anywhere in `src/domain.operations/route/drive` returns no hit

## .the shape of the fix

before the write, glob the target's `*.tmp` siblings and unlink any whose pid is not this process's
live one (or simpler: any older than a short threshold). one place, the single choke point:

```ts
// reap stale temp siblings before the write (a crash between write and rename orphans one)
const dir = path.dirname(statePath);
const base = path.basename(statePath);
const siblings = await fs.readdir(dir);
await Promise.all(
  siblings
    .filter((f) => f.startsWith(`${base}.`) && f.endsWith('.tmp'))
    .map((f) => fs.rm(path.join(dir, f), { force: true }).catch(() => undefined)),
);
```

**the clamp it owes:** write an orphan `${statePath}.99999.tmp` by hand, then call
`mutateDriveBlockerState`, and assert the orphan is gone after.

## .why it is not done in this round

**SAFE — borderline.** the reap unlinks files, so a wrong glob could remove a live temp from a
concurrent writer. hooks are serial per route today (no concurrent writer), but the concurrency
question is exactly the one the lost-update dream already reserves — so this fix wants to land WITH
that lock work, not ahead of it.

**CLEAN — no.** it adds a readdir + unlink to every write, and the r11 scope-leak fix just narrowed
this path to brain-declaring stones to REMOVE I/O from the hot path. to re-add a per-write readdir
here cuts against that, so the reap wants to be conditional or batched — a design choice, not a
one-liner.

⇒ low severity (small files, rare trigger), and the fix interacts with the lost-update lock work.
caught here rather than forced into a review round's diff.
