# 🌙 dream: a clean-reviewer cache keys on the artifact, never the rubric

- **kind** = fix
- **owner** = `ehmpathy/rhachet-roles-bhrain`
- **caught** = 2026-09-04

## .the cue that fired

the `1.vision` decomposition of the telepath behavior walked an adoption journey end to end (`case=8`). its last boundary is the guard's clean-reviewer cache, and the walk exposed a seam no single-boundary demo reaches.

per `howdoes.the-guard-caches-a-clean-reviewer-by-artifact-hash`, the guard reuses any reviewer that returned `0 blockers`, keyed on the **artifact hash**.

## .the gap, precisely

the cache key covers the *subject* and not the *rubric*.

⇒ so an edit to a rubric — a new rule file, a tightened rule, a fixed false negative — does not invalidate a cache entry that rubric's older form created. an artifact approved under rubric v1 stays approved under rubric v2, with no re-grade and no signal.

| what changed | does the cache notice? |
|---|---|
| the artifact | yes — that is the key |
| the rubric's rule set | no |
| the rules a rule file globs in | no |

🟡 **the failure is silent and it points the wrong way.** the whole reason to tighten a rubric is to catch what the looser one missed. the artifacts most likely to hold that defect are exactly the ones already cached clean under the looser rubric — so the tightened rule applies to every artifact *except* its intended targets.

⇒ this is the wish's own motivation, one layer down: *"an unreviewed reviewer is indistinguishable from a clean one."* here the reviewer is not merely unreviewed — it is reported as reviewed, from a stale verdict.

## .the shape of the fix

key the cache on `hash(artifact) + hash(rubric)`, so a rubric change invalidates every entry that rubric produced.

- the rubric hash is cheap — the rules glob resolves to a file list the reviewer already enumerates, and it already reports `rules: N` in its own stdout
- an alternative that costs less: stamp the cache entry with the rubric's resolved file list + mtimes, and treat a mismatch as a miss
- 🟡 **do not fix it by disable of the cache.** the cache is what makes a per-arrival prose reviewer affordable at all — `1.vision.yield.md` §4 names the per-arrival brain cost as the behavior's main con, and the cache is its answer

## .why it is not done in this round

**safe? yes. clean? no.**

- it touches the guard's shared cache, which every peer reviewer depends on — not only telepath's
- a key change invalidates every extant cache entry on first deploy, so the first run after it lands re-grades every reviewer on every open route
- the telepath behavior's own scope is a role, its briefs, and one rubric. a guard-cache key change ripples past that diff into machinery this behavior does not otherwise touch

⇒ per `rule.always.fix-forward-under-scouts-honor`, safe-and-clean means fix now. this is safe and dirty, so it is caught rather than done.

🟡 the dirt is also recorded as a fulcrum, since the ripple estimate above is a best guess and the deferral is a decision, not merely deferred work.
