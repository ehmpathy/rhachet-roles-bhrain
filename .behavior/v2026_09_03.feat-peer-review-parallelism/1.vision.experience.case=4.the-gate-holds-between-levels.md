# case=4 — the gate holds between levels

**cell** — `driver × multi-unbounded × all-fresh × happy`, read at the level boundary
**feel · care** — happy · **critipath**

## ⚠️ .this file bears NO NEW cell — it is a second boundary at c1's coordinate

c1 sits at this exact coordinate and demonstrates the **fan-out** — the level runs at the speed of
its slowest member. this file demonstrates the **gate** — level 3 does not open until level 1 is
terminal. two independent boundaries at one cell, neither implied by the other: a level could fan out
correctly and still open the next rung early, and it could gate correctly and never fan out at all.

⇒ it is the **same kind** as c10, which is a second boundary at c5's coordinate. so **three** of the
ten case files add no new cell: c9 (a journey), c4 (here), c10.

🔴 **that was unmarked until peer review i005, and BOTH lanes caught it in the same round.** the
inventory had coined the *"second boundary at one coordinate"* pattern, applied it to c10, and not to
this file — so its reconciliation asserted 8 cell-bearers where its own addends give 7. ⚠️ **the
pattern was right; its application was partial**, and a partial application of a document's own rule
is invisible to the reader who trusts the rule and unfindable by the arithmetic, which balanced.

⚠️ these `[tn]` sketches are illustrative, not proof. no code exists yet.

## .the narrative — the driver's pov

the reason the ladder exists is that a cheap reviewer should find the obvious blockers before an
expensive one is spent on them. if level 3 ran while level 1 was still in flight, i would burn an
opus round on an artifact a sonnet round was about to reject — which is the exact waste the ladder
was built to prevent.

so when i turn on concurrency, what i most need to stay true is what does not change: **level 1
settles completely, then level 3 opens.** four reviewers at level 1 all fly at once; not one
level-3 reviewer starts until every level-1 verdict is terminal.

the aha here is an absence. **i notice no difference at the boundary.** the ladder behaves exactly
as it did, and all that changed is how fast each rung fills.

## 🔴 .why this is a structural change, not a `Promise.all` swap

today the gate is evaluated **per reviewer, inside the loop** — `runStoneGuardReviews.ts:536-541`
computes verdicts and calls `isReviewLevelUnlocked` on each pass. that works only because the list
is sorted low-to-high and each member has fully settled before the next is reached.

concurrency breaks that premise. `computeVerdicts()` reads `reviews[]` and `meterBySlug`, both of
which are mutated inside the loop (`:615`, `:663`). run the loop body concurrently and the gate
reads state that is mid-write.

⇒ the shape that survives: **partition into level groups → run a group → settle it fully →
evaluate the gate → open the next group.** the gate moves *between* groups rather than *inside*
the walk, and then no task ever reads a co-member's in-flight state.

that restructure is also what answers acceptance 6 — see the yield's `## the meter, verified`.

## .the bdd sketch

```gherkin
given [case1] a guard with four reviewers at level 1 (unbounded) and two at level 3
  and each reviewer records its own in-flight window

when [t0] the driver runs `--as arrived`

then all four level-1 windows overlap one another
  and no level-3 window begins before the last level-1 window ends
  and the level-3 reviewers are emitted as `queued` while level 1 is in flight

given [case2] a level-1 reviewer returns blockers, so level 1 is not terminal
when  [t1] the pass completes
then  no level-3 reviewer ran at all
  and level 3's budget is untouched
```

🔴 **`[case2]` is the one that actually protects the money.** a gate that leaks under concurrency
does not fail loudly — it silently spends an expensive budget on an artifact that was about to
change. the observable is *budget untouched*, not merely *did not run*.

## .the clamp this owes (acceptance 2 + 7)

```gherkin
given [case1] the four-at-l1 / two-at-l3 guard, with l1 rejected
when  [t0] the level executes concurrently
then  the l3 meter shows 0 rounds consumed
```

⇒ **prove it bites**: move the gate evaluation inside the concurrent group (the naive port) and
re-run — l3 runs early, meter reads > 0, test goes red. restore the between-groups gate — green.

✅ **this is the one clamp in the vision that needs no fixture change** — checked in self-review r3,
where every *overlap*-based clamp turned out to require a mock that delays (see `case=2` § *the
fixture this clamp requires*). this one asserts what the **meter holds**, not when a window opened,
so it bites whatever the mock's duration.

⇒ that is not luck; it is the `[case2]` argument above, paid out. **an observable chosen for what it
COST rather than for WHEN it happened is immune to the scheduler** — the preferred shape wherever a
clamp could be written either way.

## ⚠️ .what this demo deliberately does NOT change

two open tasks — **#420** and **#422** — report that a level which becomes terminal *within* a
pass does not unlock the next level in that same pass. #422 names it *"exhaustion is recognized
one arrive LATE"*.

that behavior lives at `:371` (`wasExhausted = !hasReviewForHash && rounds >= pr.budget`), and it
survives this change **unaltered**. the demos above assert the gate behaves *exactly as today* —
that lateness among them.

⇒ the reason is `rule.forbid.failhide` applied to a diff rather than to code: a change that alters
both *what runs concurrently* and *when a level unlocks* leaves every one of the 36 snapshot
deltas with two candidate causes, and acceptance 2 asks that the gate be shown **unchanged**.

carried as **fulcrum F6** — the one fulcrum with an expiry.
