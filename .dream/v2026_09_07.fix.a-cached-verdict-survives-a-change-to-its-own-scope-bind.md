# 🌙 dream: a cached verdict survives a change to its own scope bind

| | |
|---|---|
| **kind** | `fix` |
| **owner** | `ehmpathy/rhachet-roles-bhrain` (this repo) |
| **caught** | 2026-09-07, at stone `5.3.verification` i028 |

## .the cue that fired

`rule.always.diagnose-reviewer-malfunctions` names the driver-owned remedy for an overflowed lane:
**re-run the rubric scoped.** I applied that remedy to the guard binds — and then noticed the
remedy cannot reach the lanes that most need it.

## .the gap, precisely

`computeStoneReviewInputHash.ts` hashes `getAllStoneArtifacts(input)` — the `artifacts:` list.
For this stone that is `$route/5.3.verification.yield.md` plus `src/**/*`.

🔴 **the guard file is not in that set.** so the cache key covers *the files a reviewer reads* and
omits *the bind that decides which files it reads*.

| the change | moves the hash? | cached clean verdict |
|---|---|---|
| a `src` file edited | ✅ yes | correctly invalidated |
| a lane's `--paths-with` rescoped | ⛔ **no** | **reused, at the old scope** |
| a lane's `--rules` swapped for a different rubric | ⛔ **no** | **reused, against a rubric it never read** |

⇒ the second row is the live one. the third is worse and follows from the same omission.

## ⚠️ .why it bites exactly where it hurts

the failure is **selective in the wrong direction**:

- a lane whose last verdict was `constraint` or a rejection has no clean verdict to cache, so it
  **re-runs** and picks up the new bind ✅
- a lane whose last verdict was **clean** is skipped, so it **keeps** the approval it earned under
  the old bind ⛔

**so a rescope reaches every lane except the ones that already said yes** — and a lane that
approved a corpus it should never have read is precisely the lane whose approval is suspect.

**measured here.** three lanes (`behavior-experience-coverage`, `mech-given-when-then`,
`mech-test-intent`) approved while bound, in effect, to `**/*.snap` alone — a second
`--paths-with` was silently dropped by `parseReviewArgs`. a corrected bind cannot re-run them,
because their clean verdicts are cached against an unmoved hash.

## .the shape of the fix

fold the lane's own invocation into its cache key. two candidate seams, both narrow:

1. **hash the guard file with the artifacts** — one entry appended in `getAllStoneArtifacts`.
   coarse: any guard edit invalidates every lane, even an edit to unrelated `say:` prose.
2. 🔴 **hash each lane's resolved `run:` string into its own key** — per-lane, so a rescope of one
   lane invalidates that lane alone. `input.scope.json` already records each reviewer's resolved
   `targetFiles`, so the material is on disk.

⇒ **(2) is the better shape** and composes with the extant catch
`.dream/v2026_09_05.fix.guard-review-cache-is-keyed-by-index-not-slug.md` — both are defects in
the same key, and a repair that touches it should settle them together.

## .why it is not done in this round

**safe? no.** it changes the cache key for every lane on every stone, so every cached verdict on
every live route invalidates at once. on this branch that means nine lanes re-run into a window
that five of them already overflow.

**clean? no.** `computeStoneReviewInputHash` is consumed by the entrance gate, the exit gate, the
overrule short-circuit, and the stophook. a key change ripples to all four and to their snapshots.

⇒ dirty on both axes, and the stone it was found on is already halted on a human grant. the
correct move is to record it with the evidence and leave the repair to a round that can verify it.

⚠️ **the workaround, so the next traveler is not stuck:** a rescope takes effect at once for any
lane whose last verdict was NOT clean. for a lane with a cached approval it takes effect on the
next `src` change — which arrives on its own with the next real edit. do **not** touch a `src` file
merely to bust the cache; that buys a re-run with a counterfeit input change.
