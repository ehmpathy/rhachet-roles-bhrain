# case=1 — a driver reads this tree's review bill

- cell = `tree` × `cost` × `observe`
- path = **critipath** · feel = happy · care = criti

## .the narrative

a driver has just pushed a stone through four review rounds. the guard approved, the stone
passed, and the driver wants one answer before they move on: **what did that cost?**

they do not want a projection, a rate card, or an estimate. they want the number the brain
actually charged, and they want it without a browser, a dashboard, or a credential.

```sh
rhx review._.cost --of tree
```

```
🦉 review meter
   ├─ corpus: …/.log/bhrain/review
   │  ├─ runs: 5 (5 metered)
   │  ├─ tokens
   │  │  ├─ input:     74.4k
   │  │  ├─ cache.set: 0
   │  │  ├─ cache.get: 58.2k
   │  │  └─ output:    24.4k
   │  ├─ cache: 43.9% of prompt tokens served from cache
   │  └─ cost: $0.032900425
   │
   ├─ by reviewer …
   ├─ by stone …
   └─ by round …
```

the header's second line carries the point: `runs: 5 (5 metered)`. the meter does not
merely print a total — it states **how much of the corpus it could price**. a driver who
reads `5 (3 metered)` knows at once the total under-reports, and by how many runs.

the three roll-ups answer the follow-up before it is asked: *which reviewer, which
stone, which round* carried the spend. a driver who sees one lane at 80% of the bill knows
where the guard edit goes.

## .the bdd sketch

```
given [case1] a tree whose review log holds N runs, each with measured tokens
  when [t0] `rhx review._.cost --of tree` is run
    then the header states the run count AND how many were metered
    then the four token lines are summed across every metered run
    then the cache line is a share of PROMPT tokens (input + cache.get), never of all tokens
    then the cost is a sum of measured per-run costs, never a rate card applied to a total
    then a roll-up is emitted by reviewer, by stone, and by round
  when [t1] the log dir does not exist
    then the skill says so plainly, names the fix, and exits 2 — a CONSTRAINT
    then it never exits 1 — an absent corpus is not a malfunction
```

### `[t1]` exits 2, not 0

an absent corpus is not a malfunction — it is a precondition the caller can fix (push a
stone through review first). `rule.require.exit-code-semantics` reserves exit 1 for
external/transient failures and exit 2 for a caller-fixable precondition, the same shape
as "no PR for branch (user needs to push)".

exit 0 would claim the query succeeded and found a real zero — a measurement nobody made
(`rule.forbid.failhide`, and the same conflation `asAccountedCost` refuses between
`refused` and `unknown`).

## .what it depends on

- `getAllReviewRunMeters` — reads `metrics.realized.json` per run
- `asAccountedCost` — grades each run `metered` / `refused` / `unknown`
- `genReviewMeterStdout` — the treestruct render, snapshotted

## .why it is a critipath

it is the **highest-frequency** read on the branch and the entry point to every other
surface. a driver who cannot price their own tree will not reach for the grove view at all,
and the cost work that follows has no baseline to be measured against.
