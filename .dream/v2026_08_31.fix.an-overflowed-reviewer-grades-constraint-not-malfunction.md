# 🌙 dream: an overflowed reviewer grades `constraint` where the taxonomy says `malfunction`

**kind**: fix · **owner**: `@this` — `src/domain.operations/route/guard/` · **caught** 2026-08-31

## .the cue that fired

the wisher asked, of a dark reviewer: *"shouldnt it malfunction if it doesnt come?"*

that question sent me to the code, and the answer is **yes it should, and it does not.**

## .the gap, precisely

`getExitCodeClass.ts` maps exit codes to verdict classes:

| exit code | class |
|---|---|
| `0` | `passed` |
| `2` | `constraint` |
| every other | `malfunction` |

a reviewer whose prompt blows the context window exits 2. so it grades `constraint` — a
legitimate hold, reported by a process that ran and chose to report it.

but the repo's own two definitions say otherwise, and they agree with each other:

- `term=route.guard.review.malfunction` declares a malfunction to be *a process that rendered
  no verdict at all*
- `contract.reviewer-output` states it mechanically: *stdout without a numeric count for both
  dimensions = `💥 malfunction` = blocker*

**an overflowed reviewer reviewed naught and emitted no counts. it satisfies both definitions of a
malfunction, and the exit code calls it a constraint.**

🟡 and the two classes route a reader in opposite directions, which is what makes this a defect
rather than a quibble:

| the class says | the reader does |
|---|---|
| `constraint` | *a legitimate hold stands* — satisfy it, or ask for it to be lifted |
| `malfunction` | *the process broke* — diagnose it, per `rule.always.diagnose-reviewer-malfunctions` |

so a dark reviewer currently tells a driver to treat a break as a hold.

## 🟡 .the tell — a brief existed to compensate for it

🟡 the brief named below no longer exists — it was retired the same day, and this section
speaks of it as it stood, because it is the evidence that justified the retirement. see *the brief
that compensated is already retired*, below.

`rule.always.rerun-dark-review-lanes-scoped` was a whole driver brief whose entire job was to
teach a driver that this particular `constraint` is a task, never a verdict — to re-run the
rubric scoped rather than report the overflow upward.

⇒ **a brief that compensates for a classification defect is evidence of the defect.** the rule is
correct and worth a keep regardless; but part of what it teaches would be unnecessary if the class
were right, and the driver would arrive at the correct move via
`rule.always.diagnose-reviewer-malfunctions`, which already exists for exactly this case.

## .the shape of the fix

the exit code alone cannot carry this, because `2` legitimately means *constraint* for every skill
that reports an honest hold. so the discriminator must be the **output**, not the code — which is
what `contract.reviewer-output` already prescribes:

> **a reviewer that exits 2 AND emits no numeric count for both dimensions is a `malfunction`, not a
> `constraint`.** a reviewer that exits 2 and DOES emit counts is a genuine constraint.

⇒ that is one predicate, and the parse that computes it already exists — the guard already reads
reviewer stdout for the two counts, since an absent count is what it grades a malfunction today.
**the two paths disagree**, and the repair is to make the exit-code class defer to the parse.

## ✅ .the brief that compensated is already retired — the repair inherits a cleaner target

**2026-08-31, the same day.** `rule.always.rerun-dark-review-lanes-scoped` no longer exists. the
wisher's read — *"once its fixed upstream will not be even relevant right?"* — held, and the audit
it forced showed most of the brief dies with this defect:

| what it taught | survives the fix? |
|---|---|
| *"a dark reviewer reads much like a reviewer that ran — treat it as a task"* | 🔴 dies. the generic rule says this once the class is right |
| the `constraint` / `malfunction` disambiguation | 🔴 dies. already in the generic rule |
| the **scoped re-run recipe** | ✅ survives |
| *"do NOT re-derive the inherited diff scope"* + its evidence | ✅ survives |

⇒ so the residue was one cause row, and it now lives inside
`rule.always.diagnose-reviewer-malfunctions` under *"the overflowed reviewer"*.

what this changes for the repair:

- the trim step is done, so the fix is purely the predicate below
- and it now has a clamp — once an overflowed reviewer grades `malfunction`, the recipe already
  sits under the class that routes a driver to it
  - ⇒ so the two agree by construction rather than by a brief that bridges them

🟡 **one row in that cause survives the fix too, and must not be trimmed with it:**

- an overflowed reviewer is terminal-for-unlock whatever its class
  - so it will still read on the ladder much like a reviewer that ran
- ⇒ the class fixes what the driver is *told*; it does not fix what the ladder *looks like*

## .why it is not done in this round

**scope**: this behavior is **briefs-only** by its wish's hard bound — *"no new skills"*, and this
is a change to `src/domain.operations/route/guard/`.

**and it is dirty rather than clean** (`rule.always.defer-fulcrums-to-last`): the class is read by
the ladder logic, the tree formatters, and their snapshots, so the change ripples past the one
predicate into the meter and its tests. that ripple is the estimate, and it is a best guess — so
it owes a fulcrum as well as this dream.
