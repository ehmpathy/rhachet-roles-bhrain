# 🌙 dream: the self-review timer resets on every repair the driver makes

**kind** — `fix` · **owner** — this repo · **caught** 2026-09-03

## .the cue that fired

i ran `--as promised` three times across ~30 minutes of genuine review, and was challenged with
`the pond barely rippled` every time. i had assumed the reviews were judged thin. they were not.

## .the gap, precisely

`getSelfReviewChallengeDecision.ts` measures the wait against the **artifact hash's** trigger
report:

```ts
// before hashbar → check this hash's mtime (hash change resets timer)
const elapsed = Date.now() - report.sinceMtime.getTime();
if (elapsed < threshold) return { decision: isRush ? 'challenge:rushed' : 'challenge:first' };
```

and `:62-67` — when no report exists for a hash, one is minted **with the timer started now**.

⇒ so **each artifact edit mints a fresh hash, and each fresh hash restarts the 30s wait.**

🔴 **the incentive is inverted, and that is the defect:**

| the driver who… | what the guard does |
|---|---|
| reads, finds no issues, waits 30s | **passes** |
| reads, finds 9 issues, repairs each one | 🔴 restarts the timer on every repair, and is challenged again |

the guard's own instruction is *"when you found issues, **fix them before you continue**."* a driver
who obeys that instruction is held longer than one who does not. the more thorough the review, the
harsher the hold.

⚠️ **the plowthrough hatch does not catch this either.** `:98` allows after `attempts >= 3` — but
attempts are counted **per hash**, and a driver who repairs between attempts is on a new hash each
time, so the count never reaches 3. **the liveness hatch is unreachable for exactly the driver who
does the work properly.**

## .why it is a real cost, not merely an annoyance

it teaches the wrong lesson. a driver who meets this a few times learns: **batch every repair
until after the promise clears**, or make no repairs at all during review. both are worse than what
the guard asks for, and the second is the failure `rule.always.bear-every-self-review` names — *"a
promise without a true review is a daydream."*

## .the shape of the fix

the intent of the timer is *"you did not spend real time on this."* the current proxy — elapsed
since this hash appeared — is a poor measure of that, because artifact edits are **evidence of
review**, not evidence of a rush.

candidate directions, in rough order of preference:

1. **count an artifact edit as review time, never as a reset.** carry the elapsed forward when the
   hash changes *while an articulation file is present* — the driver demonstrably reviewed
2. **measure from the articulation file** rather than the artifact hash. the articulation is the
   review; its mtime is the honest clock
3. **make plowthrough count attempts per `(stone, slug)`** rather than per hash, so the hatch stays
   reachable for a driver who repairs. this alone would prevent the hard hold
4. **set `hashbar: 0`** so the timer persists across hash changes at once — `:110` already
   implements this path; it merely is not the default

⚠️ **do not simply drop the timer.** it exists for a good reason, and
`research.selfreview-effectiveness` is presumably its evidence. the goal is a measure that counts
the review, not one that punishes it.

## .why it is not done in this round

**safe** — no. it changes a guard's challenge decision, which every route in this repo and
downstream depends on, and `getSelfReviewChallengeDecision.test.ts` plus the route snapshots encode
the current behavior.

**clean** — no. four candidate directions with different blast radii, and the right one needs the
timer's original rationale read first (`research.selfreview-effectiveness`) so the repair does not
undo what the timer was for.

**and the scope bound**: this round's stone is `1.vision`, whose artifacts glob is
`$route/1.vision*.md`. a vision stone emits no code.
