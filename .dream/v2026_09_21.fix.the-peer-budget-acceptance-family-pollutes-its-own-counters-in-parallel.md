# 🌙 dream: the peer-budget acceptance family pollutes its own counters when it runs in parallel

- kind = fix
- owner = this repo
- caught 2026-09-21

## .the cue that fired

a 16-file `--scope path://peer-budget` run returned **19 failed**. the failures were sorted before
any resnap, and they split into two unrelated classes:

- **copy** — the one-line `WARN_TEXT_CONCESSION_URGENT` change, expected, real
- 🔴 **counters that moved with no code behind them** — `7/∞` → `6/∞`, `i007` → `i006`, and an
  artifact hash `f349fccd9ea124b5ab` → `f3f272257af6779ffe`, in
  `driver.route.peer-budget-defaults`

**a round count that goes DOWN is the cue.** no change in this diff can lower a counter.

## .the gap, precisely

`driver.route.peer-budget-defaults` **passes clean in isolation** — 12/12 in 123s, against the
committed snapshot, with the `7/∞` it has always carried. the same suite, in a 16-file parallel run,
renders `6/∞`.

⇒ so the committed value is right and the parallel render is wrong. **the suite's observed state
depends on what else runs beside it**, which a blackbox acceptance suite must never do.

two failure modes ride along with it, both measured the same session:

| symptom | measurement |
|---|---|
| a setup step hits the 240s cap | `peer-budget-bulk` failed at exactly `240047 ms` on `[t0] budgets consumed`, three times. **it then passed alone, 28/28 in 413s** — so the work is legitimate and the cap is not |
| the counter/hash drift above | `peer-budget-defaults`, green alone, red at 16-way |

## 🔴 .why it is worth a fix rather than a retry

**it turns a resnap into a live weapon.** the obvious response to 19 red snapshots is
`--resnap`. that would have written `6/∞` and a wrong artifact hash into a committed baseline, and
the suite would then be green **while it asserts a state the code never produces alone**.

⇒ that is a `rule.forbid.failhide` defect manufactured by the fix, not found by it — a baseline that
lies, exactly the case `rule.forbid.overzealous-blockers` grades a blocker.

## .the shape of the fix

1. **find the shared state.** a blackbox suite sets up its own temp route, so the drift points at a
   resource outside it — a shared `.log`/`.meter` path, a cwd-relative artifact the hash reads, or a
   counter keyed on a path two suites collide on. the artifact hash moved, so **start with what the
   hash is computed over** and check whether its input is suite-local
2. **clamp it** — set up two suites against one parent dir concurrently and assert the counters are
   independent. it must go red under the current code (`rule.require.clamp-edge-cases`)
3. **the 240s cap is a separate call** — `peer-budget-bulk` needs >240s under load and 413s alone.
   either raise that suite's timeout, or cut its setup cost. do not raise it globally; the cap
   catches a real cost

## .why it is not done in this round

**it fails CLEAN, not SAFE.** the repair is a hunt through test setup across ~16 blackbox suites,
and the fix lands nowhere near this diff — which changes one stdout literal and its snapshots. to
pull it in would put a concurrency-isolation refactor inside a copy change.

🟡 **and the copy change did not need it.** the 13 affected snapshots were corrected by a targeted
substitution of the one literal, then each suite was verified green **in isolation** — so no
polluted counter entered the baseline, and the pollution stayed a diagnosis rather than a blocker.
