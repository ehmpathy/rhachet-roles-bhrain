# 🌙 dream: conform `RouteStoneGuard` to `rule.forbid.undefined-attributes`

- **kind** = fix
- **owner** = `ehmpathy/rhachet-roles-bhrain`
- **caught** = 2026-09-14

## .the cue that fired

a `brain?: string` field was added to `RouteStoneGuard` while a mechanic role was booted, and
`rule.forbid.undefined-attributes` grades an optional domain-object attribute a **blocker**:

> *"never allow undefined attributes for domain objects unless database-generated metadata …
> if null: set as null and explain why; forbid if no good reason; otherwise: define exact type."*

the self-review that added the field graded it against its five peers on **doc style** and
concluded it was consistent. it never asked the optionality question — so the field shipped
conformant to its neighbours and divergent from the rule.

## .the gap, precisely

`RouteStoneGuard` carries **three** optional attributes, and the new one is only the third:

```
src/domain.objects/Driver/RouteStoneGuard.ts:109   self?: RouteStoneGuardReviewSelf[];
src/domain.objects/Driver/RouteStoneGuard.ts:110   peer?: RouteStoneGuardReviewPeer[];
src/domain.objects/Driver/RouteStoneGuard.ts:168   brain?: string;
```

⇒ **the two prior ones are what make this a whole-object conform rather than a one-field fix.** to
change `brain` alone leaves the object internally inconsistent in a new way: five required fields,
two optional ones, and one nullable one. that is three conventions where there were two.

## .the shape of the fix

`brain: string | null`, `self: … | null`, `peer: … | null`, and a `null` written at every
construct site. **the ripple is measured, never estimated** — the `brain` half alone was applied
and the compiler counted it:

```
$ rhx git.repo.test --what types          → ✋ failed (15s), 54 errors
   ├─ src/domain.operations/route/guard/parseStoneGuard.ts               1   ← the one prod site
   ├─ src/domain.operations/route/brain/setStoneBrain.integration.test.ts  1
   ├─ …/guard/review/runStoneGuardReviews.integration.test.ts           34
   ├─ …/judges/runStoneGuardJudges.integration.test.ts                  13
   ├─ …/stones/delStone.test.ts                                          2
   ├─ …/guard/upgrade/getBudgetClobberWarnings.test.ts                   1
   ├─ …/guard/review/computeStoneReviewInputHash.test.ts                 1
   └─ …/stones/getAllStoneArtifacts.test.ts                              1
```

⇒ 🔴 **exactly one of the 54 is production code.** the other 53 are object literals in seven test
suites, each of which would gain a `brain: null` line that asserts naught and is read by nobody.
the `self`/`peer` half would add more.

⚠️ so the fix is mechanical and compiler-checked, which makes it **safe**; and it opens seven
suites whose subject is judges, reviews, stone deletion, artifact enumeration, input hashes, and
budget warnings, which makes it **unclean**. that asymmetry is the whole reason it is here rather
than in the diff.

## .why it is not done in this round

the SAFE/CLEAN test, answered by a run rather than by a guess:

| question | answer |
|---|---|
| **safe?** | ✅ yes — a widened type, every miss caught at compile time |
| **clean?** | 🔴 **no** — 53 of 54 edits land in six suites this feature never opened |

⇒ `rule.always.fix-forward-under-scouts-honor`: safe ✅ + clean 🔴 → defer, **and raise a fulcrum**,
because the dirt call is a judgment about ripple cost and a judgment made alone is what a fulcrum
list exists to surface.

🟡 **and the deferral is not merely about cost.** a one-field conform would make the object *less*
self-consistent while it makes the object *more* rule-consistent — a real design call that belongs
to whoever owns `RouteStoneGuard`, not to a feature that happened to add a sixth field to it.
