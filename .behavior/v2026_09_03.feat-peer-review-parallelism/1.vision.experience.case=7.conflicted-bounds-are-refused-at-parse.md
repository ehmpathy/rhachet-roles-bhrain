## .the invariant

> **a level carries exactly one concurrency. two declarations that disagree are refused where they
> are written, never where they are run.**

kind: **nurture**. an author can absolutely write two values that disagree; the behavior must
refuse them.

## .the narrative — the guard author's pov

i am mid-edit on a guard. i cap level 3 at 1. later, in the same file, i cap it again at 3 — maybe
i copied a block, maybe i changed my mind and edited the wrong line.

what must not happen: the guard parses, and at run time the machinery quietly picks one. picks
which? the first? the last? the smaller? every answer is a coin flip i did not know i tossed, and
the failure lands *mid-flight* with three opus subprocesses already spawned against a provider
that permits one. i would then diagnose a rate limit and never suspect my own file.

what happens: the parse refuses. before a single subprocess exists.

```
🗿 route.mutate guard
   ├─ ✋ level 3 carries two concurrency declarations that disagree
   │  ├─ concurrency: 1   (reviews.levels.3)
   │  └─ concurrency: 3   (reviews.levels.3, second entry)
   │
   └─ fix: a level carries exactly one concurrency. delete one.
```

the sharp edge fails safe: **fast, loud, before any cost is incurred, and it names the fix.**

## 🔴 .why parse and not run — the reason the walk exists

| refuse at | what the author gets | what the driver gets |
|---|---|---|
| **parse** | an error on the file they are editing, with both values quoted | never sees it at all |
| run | no signal — the file looked fine | an ambiguity they did not author, mid-flight, dressed as a rate limit |

⇒ this is `rule.prefer.prevent-over-correct` at rung 3 — catch it at the boundary, before harm.
and it is why **a driver never meets a conflicted bound at all**: the author's cell is forbidden, so
the run that would have carried one never starts.

⚠️ **`driver × conflicted` is not a cell, and so it bears no verdict** — caught in peer review
i023/r1. the driver's walk carries **no E axis**, so there is no coordinate for any declaration
verdict to sit at (`dimensions.md`, `.the product`). this sentence names the **cause**; a sentence
that named a verdict here would assert a coordinate the grid refuses.

## 🔴 .the precedent — the guard parser ALREADY refuses ambiguity this way

found in self-review r1. this invariant applies an extant pattern rather than a coined one.

`parseStoneGuard.ts:61-74` throws a `BadRequestError` when one slug is used by both a self and a
peer reviewer, and its `.why` is this case's argument verbatim:

> *"a loud throw at parse makes the ambiguity structurally impossible rather than settled by
> convention"*

⇒ the guard could have settled that collision by a convention — *"peer wins"* — and deliberately
does not. **so the shape of case 7's refusal, its error class, and its reason are all already
established in the exact function that would host it.**

## 🔴 .the LARGER hazard the same read exposed — the valve can be silently absent

⚠️ this widens the case, and it matters more than the duplicate it was written for.

`parseStoneGuard.ts:47-53` builds the guard from four known keys — `artifacts`, `reviews`,
`judges`, `protect` — out of a hand-rolled `parseSimpleYaml`. **there is no schema that rejects an
unknown or misplaced key.**

⇒ an author who writes the bound under a key the parser does not read — a typo, a wrong depth in
the tree, a plausible-but-wrong name — gets **no error and no cap**:

| what the author believes | what actually happens |
|---|---|
| level 3 is capped at 1 | level 3 has no cap at all |
| the rate limit is respected | every l3 reviewer fans out at once |
| — | the provider 429s; each lane returns `malfunction` |
| — | a driver diagnoses reviewers that were never broken |

🔴 **a safety valve that fails OPEN is worse than no valve, because the author stops to watch for
the failure.** and this is the exact outcome the wish's second half exists to prevent — *"full
fan-out at a rate limited level does not merely run slow. it **fails**."*

⇒ so the refusal this case demands is **broader than a duplicate**: any concurrency declaration the
parser does not recognize must be **refused**, never ignored. that constraint lands on fulcrum F1 —
the declaration site must be one the parser actively reads and validates.

## .the bdd sketch

```gherkin
given [case1] a guard whose `reviews.levels` declares level 3 twice, with 1 and 3
when  [t0] the guard is parsed
then  parse fails with a constraint error (exit 2)
  and the message names level 3
  and the message quotes BOTH values
  and the message names the fix — one concurrency per level
  and no reviewer subprocess was spawned

given [case2] a guard that declares level 3 once
when  [t1] the guard is parsed
then  parse succeeds and level 3 carries that one value

given [case3] the same level declared twice with the SAME value
when  [t2] the guard is parsed
then  parse fails anyway — a repeat is a duplicate declaration, not a confirmation

given [case4] a concurrency written under a key the parser does not recognize
when  [t3] the guard is parsed
then  parse fails with a constraint error naming the unrecognized key
  and it does NOT parse cleanly with the bound silently absent
```

⚠️ **`[case3]` is a judgment call, carried as fulcrum F3** — raised to 88% by the parse-time
precedent above. to accept a matching repeat would be lenient and harmless today; to refuse it
keeps the rule one sentence long (*one level, one declaration*) rather than two.

🔴 **`[case4]` is the one that protects the wish's second outcome.** `[case1]`–`[case3]` guard
against an author who declares too much. `[case4]` guards against a valve that is silently absent —
the failure mode where the author believes they capped a level and did not.

## .the clamp this owes (acceptance 7)

**two clamps, one per forbidden slice** — they fail independently, so one cannot cover both.

```gherkin
given [case1] the doubly-declared guard
when  [t0] the guard is parsed
then  exit code is 2 and stderr names level 3 and both values

given [case4] a guard with the bound at an unrecognized key
when  [t3] the guard is parsed
then  exit code is 2 and stderr names the unrecognized key
```

⇒ **prove `[case1]` bites**: remove the duplicate-check and re-run — parse succeeds, test goes red.
restore — green.

🔴 **prove `[case4]` bites — and note it goes red against the tree as it stands TODAY.** the other
clamps in this vision need the feature built before they can fail; this one fails now, because
`parseStoneGuard.ts:47-53` rejects no unknown key at all. ⇒ write it first, watch it go red before a
line of concurrency exists, and it has proven its teeth with no revert step at all.

⚠️ **and a clamp on the message alone would be toothless.** it must assert the **exit code**, or a
run that parses clean and warns to stderr would satisfy it — which is the failure-open outcome this
whole slice exists to refuse.
