# 🌙 dream: fold the two verdict/exhaustion computations behind one shared operation

- kind  = fix
- owner = this repo (`rhachet-roles-bhrain`)
- caught = 2026-09-13, at stone `5.1.execution.from_vision`, from peer review i015/r11 (arch-defects)

## .the cue that fired

the reviewer found two independent computations of the same `wasExhausted` predicate in
`runStoneGuardReviews.ts`, with an asymmetry that is explained at one site and not the other:

- `computeVerdicts()` (the per-level gate) computes
  `wasExhausted = !hasReviewForHash && rounds >= pr.budget` — an explicit guard against a stale
  cached review from a prior artifact hash, with a comment that names it a `.fix` for a real bug.
- the pre-pour partition loop computes `wasExhausted = rounds >= pr.budget` directly, with **no
  hash guard**.

## .the gap, precisely

the partition site is safe **today** only because `cachedReviews` there is already hash-scoped
upstream (`getAllStoneGuardArtifactsByHash`) — but that reasoning lives nowhere near the partition.
so the two sites agree by a coincidence of upstream scoping plus comment discipline, not by
construction.

checkable evidence: grep `wasExhausted` in
`src/domain.operations/route/guard/review/runStoneGuardReviews.ts` — two assignments, one with the
`!hasReviewForHash` term, one without.

⚠️ a future maintainer who copies the partition pattern into a third verdict consumer has even odds
of reintroducing the exact stale-hash bug the comment three functions away already fixed once.

## .the shape of the fix

extract one shared `computeReviewerVerdict({ rounds, budget, hasReviewForHash, ... })` used by both
the gate and the partition, so the hash-guard term cannot drift by construction rather than by
comment discipline. give it a unit clamp that goes red if the hash guard is dropped.

## .why it is not done in this round

SAFE = yes (behavior-neutral refactor). CLEAN = **no** — it touches the verdict core of a
~620-line function under active review, ripples into every verdict consumer, and would enlarge the
already-overflowed l1 diff. the reviewer themselves classified it a follow-up, not a re-open:
*"#2–#4 are worth a follow-up pass, not a re-open of this stone."*
