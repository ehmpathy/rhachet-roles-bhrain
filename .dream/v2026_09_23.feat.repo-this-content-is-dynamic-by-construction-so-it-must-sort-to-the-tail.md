# 🌙 dream: `repo=.this` content is dynamic by construction, so it must sort to the tail

- kind = feat
- owner = rhachet-roles-bhrain
- caught 2026-09-23

## .the cue that fired

the prefix census was read lane by lane, and `repo-rules` was thrown out of the sample by the
wisher with the reason that settles this dream:

> `repo-rules` is dynamic, hence must be sorted at end of cached rules.

its glob is `.agent/repo=.this/**/rule.*.md` — **the briefs of the repo under edit**. so on any
branch that touches a brief, that lane's own rubric churns between rounds, and the rubric sits in
the prompt HEAD, which is the one block the whole cache strategy assumes is stable.

⇒ the lane most likely to churn its head is the lane whose head is made of the files we are here
to change.

## .the gap, precisely

`getAllTargetsByCacheStability` orders the **target** corpus by mtime, so an edited file sorts last.
**no peer operation sorts the `rules` or `refs` blocks at all** — they enter in glob order, which
is alphabetical, which is uncorrelated with how likely a file is to move.

that is the same defect the target sort exists to repair, left live one block upstream — and it is
worse there, because the rules block sits in the **head**, where a break voids every byte behind it.

### 🔴 and the fix needs no mtime at all

the target sort infers stability from a clock stamp. for this block the answer is **declared in the
path**:

| coordinate | stability | why |
|---|---|---|
| `repo=.this` | **dynamic** | it is the repo under edit; a branch exists to change it |
| `repo=ehmpathy`, `repo=bhuild`, `repo=bhrain` | **static** | dependency briefs, pinned by version |

⇒ so the sort is computable from the path with no filesystem read, no clock, and no heuristic.
`repo=.this` last, every other repo first, ties alphabetical.

🟡 and it is **strictly better than mtime here**, because mtime is rewritten wholesale by a
formatter, a rebase, or a fresh checkout, where the `repo=` coordinate survives all three.

### the measured contrast

two lanes, same rounds, same corpus, same machine:

| lane | rubric source | head | head stable across rounds? |
|---|---|---|---|
| `mech-decode-friction` | `repo=ehmpathy` dependency briefs | 15,018 ch | ✅ byte-identical i005 → i006 |
| `repo-rules` | `repo=.this` — **the branch's own briefs** | 102,723 ch | ⚠️ identical only where no brief was touched |

`repo-rules` held its head across the pairs measured here — because those rounds happened to touch
no brief. **that is luck, not a property**, and the whole point of a cache strategy is to remove the
dependence on luck.

## .the shape of the fix

1. **sort every fileset by declared stability, never only the targets.** `rules`, `refs`, and
   `targets` each enter as an ordered list; one operation should rank all three.
2. **rank on the `repo=` coordinate first**, then mtime, then path. the coordinate is the strongest
   signal and the cheapest to read.
3. 🟡 **consider whether a `repo=.this` rubric belongs in the head at all.** if the block is known
   dynamic, its place may be the tail with the targets, so a churn costs its own bytes rather than
   every byte behind it. that is a bigger call than a sort, and it is the wisher's.
4. **state the order in the composition census**, so a reader can see which block broke a prefix
   rather than infer it from a byte offset.

## .why it is not done in this round

**SAFE — no.** it reorders what `rhx review` sends, so every compiled-prompt snapshot moves, and a
reorder of the RULES block changes the rubric a reviewer reads first. that is a behavior change on
a stone already inside `5.3.verification`.

**CLEAN — no.** it reaches `compileReviewPrompt`, the target sort, the composition census, and every
snapshot of the three.

⇒ SAFE and CLEAN both answer no, so it is caught (`rule.always.catch-dreams-for-followups`).

## 🟡 .the bound — this is a SORT fix, and the cache misses are not all sort

the census shows two independent failures, and this dream repairs one of them:

- **the prefix collapses** — what this fixes, for the head
- **the cache drops a prefix that DID survive** — untouched here. `mech-decode-friction` i005→i006
  held a **195.5k-char** prefix with a byte-identical head and was served **zero**

⇒ do not read a landed sort fix as a cache repair. the second failure wants its own probe.
