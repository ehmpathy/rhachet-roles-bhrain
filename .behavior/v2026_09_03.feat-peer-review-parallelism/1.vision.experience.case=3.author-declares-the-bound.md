## ⚠️ .why a demo of ONE declaration covers all four B shapes

added after peer review i007/r2, which found the yaml below ran **one reviewer per level** while the
header claimed four `multi-*` cells — *"`then` asserts naught about a multi-member level, and unlike
c5/c6 the file never states why a single-member demo covers multi shapes."* both halves were right,
and both are repaired: **the yaml now runs three reviewers at l3**, and the argument it lacked is
here.

🔴 **the declaration is scoped to the LEVEL, so the roster is invisible to it.** `reviews.levels.3`
names a level, never a reviewer; the parser reads a level key and attaches a number to it. **it never
counts the members**, so a bound declared over three reviewers and a bound declared over one are the
same parse, with the same result.

| the cell | what varies | what the parse does differently | demoed at |
|---|---|---|---|
| 🔴 `consistent × multi-unbounded` | l1 declares `concurrency: 8` over **4** members — a cap that cannot bind | attaches 8; the effective shape is unbounded | `[case1c]` |
| `consistent × multi-capped` | l3 gets `concurrency: 2` over 3 members | attaches 2 | `[case1b]` |
| `consistent × multi-cap-1` | l3 gets `concurrency: 1` over 3 members | attaches 1 | `[case1]` |
| `absent × multi-unbounded` | no `levels:` key at all | reads no key ⇒ default | `[case2]` |

⇒ **the four differ only in the VALUE attached, never in the mechanism.** so one demo covers them,
the same way c5's one demo covers `{multi-unbounded, multi-capped}` because a mid-flight failure does
not consult the cap.

## .the narrative — the guard author's pov

i write a `.guard`. i already know how to say *which* reviewers run and *when* — `level` does
that, and `budget` says how many rounds each gets. now i need to say *how many at once*.

i want to write it once, at the grain it belongs to. concurrency is not a property of a reviewer;
it is a property of a **level**. if i had to repeat `concurrency: 1` on each of the three
reviewers at level 3, i would state one fact three times, and the day one copy drifts i have
written a question the parser has to answer for me.

so i declare it where levels are described:

```yaml
reviews:
  levels:
    3: { concurrency: 1 }      # the heavy brains; the provider permits one

  peer:
    - slug: cheapo                       # ─┐
      run: rhx review --rules ... --brain sonnet
      budget: 10                         #  │ level 1 — FOUR members,
      level: 1                           #  │ no entry above ⇒ unbounded
    - slug: cheapo-two                   #  │
      run: rhx review --rules ... --brain sonnet
      budget: 10                         #  │
      level: 1                           #  │
    - slug: cheapo-three                 #  │
      run: rhx review --rules ... --brain sonnet
      budget: 10                         #  │
      level: 1                           #  │
    - slug: cheapo-four                  # ─┘
      run: rhx review --rules ... --brain sonnet
      budget: 10
      level: 1

    - slug: primo                        # ─┐
      run: rhx review --rules ... --brain opus
      budget: 3                          #  │ level 3 — THREE members,
      level: 3                           #  │ capped at 1 above
    - slug: primo-two                    #  │
      run: rhx review --rules ... --brain opus
      budget: 3                          #  │
      level: 3                           #  │
    - slug: primo-three                  # ─┘
      run: rhx review --rules ... --brain opus
      budget: 3
      level: 3
```

⚠️ **both levels hold several members on purpose** — that is what makes this demo bear the `multi-*`
cells its header claims, and it is what the sentence above about *"three reviewers at level 3"*
describes.

level 1 gets no entry, and that is the point — **the absent declaration is the common case, and
it means unbounded.** i do not write a line to get the behavior i want; i write a line only where
a level cannot take the pour.

the aha: **i say the bottleneck once, at the level, and only where a bottleneck exists.**

## .the bdd sketch

```gherkin
given [case1] a guard with `reviews.levels: { 3: { concurrency: 1 } }`,
      FOUR reviewers at l1 and THREE at l3
when  [t0] the guard is parsed
then  level 3 carries a concurrency of 1, and it governs all THREE of its members
  and level 1 carries the default across all FOUR of its members
      — 🔴 whose EFFECTIVE pour is unbounded at four, under either open candidate
  and the reviewer entries are unchanged; no reviewer carries a concurrency field
  and the parse result is identical to a guard whose levels hold one member each
      — 🔴 the bound is level-scoped, so the roster count does not enter it

given [case1b] the same guard with `3: { concurrency: 2 }`
when  [t0b] the guard is parsed
then  level 3 carries a concurrency of 2
  and 🔴 only the attached VALUE differs from [case1] — the mechanism is identical

given [case1c] the same guard with `1: { concurrency: 8 }` — a cap ABOVE l1's 4 members
when  [t0c] the guard is parsed
then  level 1 carries a concurrency of 8
  and the parse honors it — a generous cap is not an error
  and 🔴 the EFFECTIVE shape of l1 is unbounded, because 8 cannot bind over 4
      — this is `consistent × multi-unbounded`, and it is the only way to reach it:
        a declared bound that exists and never binds

given [case2] a guard with no `reviews.levels` key at all — every extant guard in the repo
when  [t1] the guard is parsed
then  every level carries the default
  and 🔴 no level's EFFECTIVE pour is capped, since no level here exceeds ten members
  and the guard parses without error; the key is additive, never required

given [case3] a guard whose `reviews.levels` names a level no reviewer declares
when  [t2] the guard is parsed
then  parse fails loud, and the error names the level and the reviewers that do exist
```

🔴 **`[case3]` is the drift guard the `levels:` shape owes.** a second place where levels are
named is a second place they can disagree. an entry for a level nobody sits at is almost always a
typo — `4` for `3` — and it would otherwise be silently inert, which is the worst outcome: the
author believes they capped a level and did not.

## .the default, and why

🔴 **the default's VALUE is open — fulcrum F2, awaiting one number from the wisher.** what is
settled is that `absent` yields a **permissive** default, never `1`.

| the candidate | state |
|---|---|
| default `1` (serial) | ❌ **rejected.** delivers acceptance 1 for **no extant guard**, since none declares a bound. the feature would ship dark, and every guard in the repo and downstream would need a migration to receive what the wish asked for |
| default `unbounded` | 🔴 **withdrawn 2026-09-08.** its primary evidence was the wisher's *"l1 is infinite"* — and **the wisher retracted that in seed S3**: *"lets expect that even l1 may have a bottleneck of 10 in parallel"* |
| 🔴 default `10` | ✅ **taken, 82%.** a third value F2's original fork never priced. beats unbounded on the resource con and ties it on the pro |

## 🔴 .the two candidates are INDISTINGUISHABLE below eleven members — which is why the demos survive

this is the reconciliation, and it is why no `[case]` below changes when the number is settled:

| level size | `concurrency: 10` | `unbounded` | distinguishable? |
|---|---|---|---|
| 4 members (this demo) | pours 4 | pours 4 | ❌ **no** — a cap of 10 cannot bind over 4 |
| ≤ 10 members | pours all | pours all | ❌ no |
| 🔴 **11 members** | pours 10, queues 1 | pours 11 | ✅ **yes** |

⇒ **every cell here is named by EFFECTIVE shape, never by the declared number.** so
`absent × multi-unbounded` stays correctly named under either candidate: at four members the
effective pour is unbounded whichever value wins.

⚠️ 🔴 **and the one measured real case sits on the far side of the line.** radio task **#404**
observed **11 lanes at a single level** — so the sole documented instance in this repo is the exact
size at which the two candidates diverge. **that is not a coincidence; it is what made `10` a
candidate at all.**

⇒ so the open number is genuinely open, and it is genuinely **cheap**: it changes one parser
constant and **no demo, no cell, and no clamp on this page.**

⚠️ **stated fairly: any permissive default is a behavior change for every extant guard.** a level of
four goes from one-at-a-time to four-at-once, which multiplies peak memory and brain quota. that is
real, it is the resource-pressure hazard the wish flagged, and it is carried as fulcrum **F2** — a
level that cannot take the pour declares a cap, which is exactly the mechanism this wish adds.

## .the clamp this owes (acceptance 7)

**one clamp, for `[case3]`** — the third parse-time invariant. `[case1]`, `[case1b]`, `[case1c]`, and
`[case2]` assert what a correct declaration parses to; only `[case3]` asserts a **refusal**, and a
refusal is what can silently go absent.

```gherkin
given [case3] a guard whose `reviews.levels` names a level no reviewer declares
when  [t2] the guard is parsed
then  exit code is 2
  and stderr names the phantom level and the levels that do exist
```

⇒ **prove it bites — and, like c7's `[case4]`, it goes red against the tree as it stands TODAY.**
`parseStoneGuard.ts:47-53` validates no level target at all, so a stray `levels` entry parses clean.
write this clamp first, watch it fail before a line of concurrency exists, and it has proven its
teeth with no revert step.

⚠️ **it must assert the EXIT CODE**, not the message alone — a run that parses clean and warns to
stderr would satisfy a message-only check, which is the fail-open outcome this invariant refuses.
