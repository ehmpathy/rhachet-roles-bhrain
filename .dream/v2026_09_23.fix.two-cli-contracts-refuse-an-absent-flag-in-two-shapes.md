- kind  = fix
- owner = rhachet-roles-bhrain
- caught 2026-09-23

## .the cue that fired

`ergo-snapshot-visual-blemishes` blocker.1 at i004 on stone `5.3.verification` named **one**
divergent usage-error render — `route.bind.set` with `--route` absent, which printed a bare
`error: --route is required` where its eight peers in the same snapshot file print
`error: BadRequestError: <msg>` plus a JSON hint payload.

that one site is repaired. the grep that confirmed the repair found the shape alive elsewhere:

```
rhx grepsafe --pattern 'run with --help for usage'
```

## .the gap, precisely

the bare shape is **gone from `route.ts`** and **is still the house shape in the `review` CLI**:

| contract | file | required-flag refusal |
|---|---|---|
| `route.*` | `src/contract/cli/route.ts` | ✅ `throw new BadRequestError(msg, { hint })` — ~14 sites, rendered by `runCliEntrypoint` |
| `review` | `src/contract/cli/review.ts:307,316,321,334,343` | 🔴 bare `console.error(msg)` + `console.error('run with --help for usage')` + `process.exit(2)` |
| `review.by` | `src/contract/cli/review.by.ts:187,198,205` | 🔴 the same bare pair |

⇒ **so the inconsistency did not go away; it moved up a level.** it was a divergence *within* one
contract, and it is now a divergence *between* two contracts a driver meets in one session.

the eight `review*` sites are consistent **with each other** and pinned by their own snapshots —
`blackbox/__snapshots__/review.failfast-flags.acceptance.test.ts.snap:11,17` and
`review.optional-rules.acceptance.test.ts.snap:30,36,42`. so the bare shape is not an accident there;
it is that contract's extant convention, and no single site is the outlier.

🟡 **`route.guard.budget` is a THIRD shape, and it is deliberate.** at `route.ts:2272` and `:2289`
the budget verb prints a bare line and then a full help dump, pinned as `case1` and `case3` of
`driver.route.usage-errors`. its docblock states the reason — usage on an absent required flag is an
error path, so it goes to stderr — and the help dump is `rule.require.help-on-demand` at work. ⇒ a
sweep that flattens every refusal to one shape would **delete** that, so the sweep owes a read rather
than a find-and-replace.

## .the shape of the fix

the `BadRequestError` route is already the better one, for a reason beyond looks: `runCliEntrypoint`
catches it **above** `parseArgs`, so it covers faults the inner allowlists cannot reach — that is the
whole argument of the boundary's own docblock at `route.ts:668-702`.

1. wrap `reviewRun` / `reviewBy` in `runCliEntrypoint`, as the route verbs are
2. replace each `console.error(msg)` + `console.error('run with --help for usage')` + `exit(2)` trio
   with `throw new BadRequestError(msg, { hint: '--help for usage' })`
3. re-take `review.failfast-flags` and `review.optional-rules` snapshots — **scoped**, never a bare
   `--resnap` (`repo-rules` blocker.2 at i003)
4. read `route.guard.budget` and **leave it alone** unless the help-dump is separately argued away

⇒ ~8 call sites, 2 files, 2 snapshot files. the risk is low and the read is the cost.

## .why it is not done in this round

the SAFE/CLEAN test of `rule.always.fix-forward-under-scouts-honor`:

- **safe?** yes — a shape change on an error path already pinned by snapshots
- 🔴 **clean?** **no.** `review.ts` and `review.by.ts` are not in this diff, and the repair moves two
  snapshot files that belong to the review contract. this round's wish is the self-review gate's
  timer and hash key; a re-shaping of the review CLI's usage errors rides along on no part of it

⇒ and the blocker that surfaced it named the **route** contract's snapshot file, so the repair it
asked for is complete. this is the residual the grep found, never the concern the lane raised.
