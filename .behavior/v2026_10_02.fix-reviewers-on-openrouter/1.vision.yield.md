# 1.vision — cut reviewers over from fireworksai to openrouter

## .the outcome world

### before

fireworksai suspended the account. so every path in this repo that names
`fireworks/deepseek/v4-flash` now fails:

- `rhx review` and `rhx review.by` fail when no `--brain` is given
- a guard's prose verdict fails to tally, because the tally sub-brain (`FIXED_FALLBACK_BRAIN`) is fireworks
- the integration and acceptance suites fail in CI, which blocks every release

a crew that drives a route stalls at its first peer review. this has happened across the fleet.

### after

the one cheap review brain is `openrouter/deepseek/flash`, everywhere the repo used fireworks before:

```
$ rhx review --rules 'rules/*.md' --paths 'src/**/*.ts'
   ├─ brain: openrouter/deepseek/flash
   ...
   ├─ 0 blockers
   └─ 0 nitpicks
```

- `DEFAULT_BRAIN` (review), `DEFAULT_REVIEW_BRAIN` (review.by), `FIXED_FALLBACK_BRAIN` (tally),
  and `DEFAULT_TEST_BRAIN` all name `openrouter/deepseek/flash`
- `rhachet-brains-openrouter@0.1.3` (latest) is installed. `rhachet-brains-fireworksai` is gone
- the keyrack manifests declare `OPENROUTER_API_KEY` and no longer declare `FIREWORKS_API_KEY`
- the **driver** role ships its own keyrack (`src/domain.roles/driver/keyrack.yml`, wired the way
  `getReviewerRole.ts:21` wires the reviewer's), which declares `OPENROUTER_API_KEY` in env.prep. a
  driver's guards run peer reviews and the tally fallback, so a repo that enrolls only the driver
  still gets the key declared (seed S03)
- the suites pass against openrouter

### the aha

the tier slug is `openrouter/deepseek/flash`, not a version. openrouter picks the newest deepseek
flash model on its own, so no release is owed when deepseek ships a new flash. what the repo pins
is a **capability** (cheap, fast deepseek), not a vendor's model id. so a vendor outage is a
one-word change, which is exactly the change this wish asks for.

## .mental model

- a human would say: *"reviews run on openrouter now — same cheap deepseek, different shop."*
- analogy: openrouter is a market. the slug names the product (deepseek flash). the filters name
  which stalls may sell it (cheapest, fast enough, no data kept)
- their word is "provider". our word is "brain", with a slug like `openrouter/deepseek/flash`

## .evaluation

**goals**

- reviews and CI unblocked → yes, once the key is in place
- latest openrouter package → `0.1.3` (`0.1.1` at vision time; `0.1.2` and `0.1.3`, both supply
  fixes, shipped mid-route)
- no fireworks credential needed → yes, since the package and the key declarations are removed

**pros**

- one aggregator, so a single host's outage is routed around
- the tier slug tracks new deepseek flash releases with no code change
- `privacy=full` is on by default, so hosts keep no data

**cons**

- a fresh dependency at `0.1.x`, so it is young
- the default filters (`speed=min50tps`, `privacy=full`) narrow the host set. if that set is ever
  empty, the result is a `ConstraintError` before any call
- the tier pick can change within 7 days, so a review's model can drift without a diff. the
  slug in snapshots stays stable

**edge cases**

- a stale guard with `--brain fireworks/...` → refused loud, with the valid choices (forbidden cell
  F-1, pinned by `blackbox/review.brain-stale.acceptance.test.ts`)
- a key absent → refused loud, with the fix (cases 3, 4)

## .groundwork

### external research

- `npm view rhachet-brains-openrouter` → versions `0.0.0-stage`, `0.0.0`, `0.1.1`. latest = `0.1.1` at vision time (superseded by `0.1.3`, which execution pins)
- its readme confirms that `openrouter/deepseek/flash` is a tier slug and one of the names
  rhachet can choose via discovery. it also confirms that the default filters are
  `floor&speed=min50tps&privacy=full` and that the credential is `OPENROUTER_API_KEY` via keyrack
- it exports `getBrainAtomsByOpenRouter`, the twin of `getBrainAtomsByFireworksAI` for
  `genTestBrainContext`

### internal research

- rhachet `1.48.1` discovers brain packages by a scan of package.json for `rhachet-brains-*`
  (`node_modules/rhachet/dist/domain.operations/brains/discoverBrainPackages.js:71`). so an install
  alone registers the openrouter atoms, and an uninstall alone drops the fireworks ones
- an unknown choice throws `BrainChoiceNotFoundError` with the available slugs
  (`genContextBrain.js:94-112`). that is the case-5 refusal

- defaults that name fireworks:
  - `src/contract/cli/review.ts:23` `DEFAULT_BRAIN`
  - `src/contract/cli/review.by.ts:19` `DEFAULT_REVIEW_BRAIN`

  - `src/.test/genTestBrainContext.ts:22` `DEFAULT_TEST_BRAIN`, plus its `getBrainAtomsByFireworksAI` import
- explicit test slugs: ~10 unit and integration tests in `src/`, ~80 lines across `blackbox/*.acceptance.test.ts`
- blackbox fixtures: four `blackbox/.test/assets/*/package.json` pin `rhachet-brains-fireworksai@0.1.2`.
  three `.agent/keyrack.yml` declare `FIREWORKS_API_KEY`. two fixture `.guard` files name `--brain fireworks/...`
  (one more sits in a dormant shipped route; the full list is in `case=_` §forbidden).
  `invokeRouteSkill.ts`, `invokeReviewSkill.ts`, and `driver.route.optional-skip.acceptance.test.ts`

  `review.by*`, and `review.conversation-help` (the discovered brain list)

## .what is awkward?

- 🟡 **the reviewer role's keyrack is published.** `src/domain.roles/reviewer/keyrack.yml` reaches
  every repo that enrolls `bhrain/role=reviewer`. so a swap of `FIREWORKS_API_KEY` →
  `OPENROUTER_API_KEY` there means each consumer repo must have an OPENROUTER key under ehmpath
  `env.prep` before its reviews run on this release. that is the point of the wish, since the
  fireworks key is dead fleet-wide anyway. it ships as an ordinary release, not a major one
  (S05), with a line in the release note, so a consumer knows which key to fill

- a cutover forced by an outage, onto a `0.1.x` package. there is no fallback brain when openrouter
  is down too. the wish asks for a cutover, not redundancy, so redundancy is out of scope
- the credential is a human grant, so the wish's "suites pass" outcome hung on a human act. it is
  granted now (open question 1), and the suites run
- `asConcurrencyGroupLeakAdvisory` and similar tests still read `'fireworks'` as a group label after
  the cutover. that is correct but may look like a leftover to a grep
