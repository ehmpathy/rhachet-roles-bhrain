# 1.vision — one route reminder daemon per clone

## .the solution

key the reminder on the **clone**, not on (route, clone). a clone drives one route at a time, so it owns one daemon, and that daemon nudges about the route the clone drives now.

three moves:

1. **one handle per clone.** the pid, log, and crash-breaker leave `$route/.route/` and move to a clone-scoped home: `<gitroot>/.agent/.cache/repo=bhrain/role=driver/skill=route.reminder/daemon.of=reminder-driveon.session=<token>.{pid,log,crashes}`. `.agent/.cache/` is the paved gitignored home for clone-local state; the status-line cache sits beside it at `…/skill=route.status.line/` (`DIR_OF_ROUTE_STATUS_LINE_CACHE`), and this dir takes the same coordinate shape. the dir gets a `*` `.gitignore` findsert, as the cache does.
2. **a focus pointer.** beside the handle sits `…session=<token>.focus`: one line, the absolute path of the route the clone drives now. every `route.drive` writes it before the reminder sync (`syncRouteReminderForDrive`). the daemon reads it every tick, then reads that route's activity. so a clone that moves from route A to route B **retargets** its live daemon; it never spawns a second.
3. **a legacy reap.** a daemon spawned before this fix holds a per-route handle. the sweep lives inside the findsert and reap leaves, so every caller of them — the drive's sync on either arm, a manual `gen`, a manual `del` — first reaps this clone's legacy handles under `.behavior/*/.route/`. a manual `get` stays read-only (a literal-dot, depth-one glob). after one drive, one daemon remains.

### why it works

- the findsert key is the clone. two routes cannot mint two handles, because both map to one path. the extant atomic claim (exclusive create, `setRouteReminderPidHandle`) still elects one winner under a race.
- the tick asks one question: *is the focus route an active drive?* active → nudge. not active → exit. the daemon never sees a route the clone does not drive, so a stale route cannot nudge.
- a dead or complete focus route reaps the daemon (extant `delRouteReminder` arm). a route the clone left behind gets no nudge, whatever its status. that matches the wish: one nudge, about the route the clone drives now.
- the reap keeps the focus file. so `route.reminder.get` after a reap names the focus route and why it halted, never the false *"no daemon was ever registered"*. that false read ships today (the sync's dead arm calls `delRouteReminder`, which wipes the log); the fix rides along because `get` changes anyway to print the focus.

### why not the simpler rival

the rival: keep per-route handles; before each spawn, sweep this clone's daemons out of the other routes. it changes less code, and it fails on three counts:

| | per-route handle + sweep | clone-keyed handle + focus |
|---|---|---|
| one daemon, by construction | no — only for routes the sweep can glob | yes — one path per clone |
| two drives race on one clone | each sweeps the other: zero or two daemons | one exclusive-create winner |
| a route switch | reap + spawn, a window with no daemon | a focus write, no process churn |

### the contract, testdriven

```sh
# a clone drives route A, then route B, both live
rhx route.drive                       # bound to A → daemon spawned, focus = A
rhx route.bind.set --route .behavior/B
rhx route.drive                       # bound to B → same daemon, focus = B, no spawn
rhx route.reminder.get
# reminder is live — daemon pid 41123, focus .behavior/B
```

the `get` line extends the extant prose (`routeReminderGet`, `route.reminder.ts:431`) with the focus; its form is otherwise unchanged.

## .outcome world

before: a seat with three live routes on one clone wakes to three `🗿 you can do it!` pokes every 20m. the clone cannot tell which route each poke is about; they read identical. a human sees `ps` show three `route.reminder.daemon` processes and wonders which is real.

after: one poke per interval. the clone drives the bound route; the poke follows the bind. `ps` shows one daemon per clone. `route.reminder.get` names the route it watches.

aha: the clone moves to a new route and the next poke is already about it — no daemon came or went.

## .mental model

- a human says: *"each clone has one alarm clock. it rings about whatever you work on now."*
- the old model was *"each route has an alarm clock per clone"* — a clock left on the shelf of every route you ever touched.
- our terms: handle, focus, findsert. their terms: "the reminder", "the nudge", "what i'm on".

## .evaluation

| goal | met by |
|---|---|
| one daemon per clone, any count of routes | handle path keyed on clone alone |
| one nudge per interval | one daemon, one tick per interval |
| nudge about the route driven now | focus pointer, read per tick |
| clamp red then green | the sync + tick case above |

pros
- smaller state: one handle set per clone, not one per (route, clone)
- a route switch costs no spawn, no reap — no window with zero or two daemons
- the per-route `.route/` dir sheds three runtime files that never belonged to the route

cons
- the daemon no longer carries its route in argv; a reader of `ps` sees only the clone. the log line and `get` name the focus instead
- the legacy reap reaches only `.behavior/*/` routes; a route kept elsewhere leaves its legacy daemon to self-exit on its own doors

edgecases, and the pit of success
- **focus file absent** (a daemon booted, the drive never wrote focus): gen writes focus before it spawns. a tick with no focus exits `route-not-live`. never a nudge about a guess
- **focus names a deleted route**: the activity read finds no passage → `route-not-live` → exit
- **two clones on one route**: two clone keys, two daemons — correct, each clone gets its own nudge
- **a branch switch** (the clone checks out branch Y, bound to B, in the same worktree): same gitroot, same clone handle, focus moves to B on the next drive. a "stack" is a rebind or a branch switch; a concurrent multi-bind throws in `route.drive` (`getRouteBindByBranch.ts:23-27`) before any sync
- **focus write faults** (the seam from drive to daemon): the sync reaps the daemon and surfaces the fault to the clone log. a live daemon with a stale focus would poke about the route the clone left; silence is the safe side
- **two drives race on one clone** (A and B at once): one handle path, one exclusive-create winner; the focus write is last-writer-wins, and the next drive rewrites it
- **crash-breaker**: per clone now. a clone whose spawn keeps dying trips once, not once per route

## .open questions & assumptions

assumptions
- the handle dir anchors on the gitroot, derived by `getGitRepoRoot({ from: process.cwd() })` — the paved derivation `spawnRouteReminderDaemon` and `sayToClone` already use. the drive hook runs at gitroot, and the spawn pins the daemon's cwd to gitroot, so both sides compute one dir. the builder turns async; today it is sync off the route
- a clone works in one gitroot. `.agent/.cache/` is per gitroot, so a clone seen from two worktrees would hold two handles. the clone serial is per session and a session runs in one worktree, so this holds today
- the bound route is the route the clone drives now. `route.drive` already reads the bind (`stepRouteDrive.ts:90`), so the focus write sits at the one place that knows
- the surdirector patch was unreachable by any paved read (no `direction.surdirector` worktree; no bhrain patch on `uladkasach/nheuron` main). this vision derives from source. if the patch takes another shape, compare it at execution

questions, triaged
- **[wisher]** where does the surdirector patch sit, by a path a paved read can reach? it does not block: execution can compare its shape with this one. absent a pointer, execution proceeds on this vision
- **[answered]** should a fresh spawn wait one interval before its first poke? the loop ticks before it sleeps (`runRouteReminderDaemon.ts:58-111`). after the fix a spawn happens only at a first drive, a resume from a halt, or a crash respawn — each a moment the clone benefits from a poke. a switch no longer spawns. keep the boot tick
- **[answered]** must the nudge prose name the route? no. one daemon per clone gives the generic poke one referent; the prose is a snapshot-pinned, must-validate lever (`REMINDER_NUDGE_PROSE.test.ts`) with no read that it fails
- **[answered]** what of a clone seen from two worktrees? the serial is per session and a session runs in one worktree (assumptions above)
- **[answered]** what of legacy daemons on routes outside `.behavior/`? they fall back to their own exit doors (F3). both routes checked write under `.behavior/`: this route, and `cicd.deflake/init.sh:88`. other route templates were not checked
- **[answered]** the five fulcrums (F1–F5): each a best guess with a clean rework, below; they go to the fulcrum review at route end
- **[research]** none. no external dependency

## .what is awkward

- `--route` on `route.reminder.get|del` loses its role: the handle no longer depends on it. an accepted-but-ignored flag would surprise; a silent drop breaks no call but lies. the vision refuses it on `get|del` with a constraint error that names the fix (fulcrum F4)
- `.agent/.cache/` reads as "safe to delete". a deleted pid file orphans a live daemon until its own exit doors fire. the extant session-dead and route-not-live doors bound that
- the focus pointer is a second write per drive. it is one small file, rewritten only when its content differs
