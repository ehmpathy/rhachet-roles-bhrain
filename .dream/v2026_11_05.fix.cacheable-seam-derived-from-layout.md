# 🌙 dream: the cacheable seam is derived from the layout, not declared in a table

kind = fix · owner = bhrain/review · caught 2026-11-05

## .the cue that fired

a peer review of `5.1.execution.from_vision` (i004, arch-defects) found that `IS_CACHEABLE_SECTION`
reads `rules` and `refs` as `cacheable` while, in the corpus-first layout, both trail a corpus
that moves across rounds.

## .the gap, precisely

`IS_CACHEABLE_SECTION` (`src/domain.objects/Reviewer/PromptSectionChars.ts:98`) is a static
`Record<section, boolean>`. it cannot express position, so it states the rubric-first seam: the
rubric as stable prefix. in the corpus-first layout the rubric is cacheable only across the lanes
of one round's level when the corpus holds, and not across rounds once a file is repaired. the
census rows (`getOnePromptComposition` `cacheable.head` / `cacheable.tail`) already measure the
seam by offset. the table and the census can disagree, and the table is what `review._.cost`
prints as `seam`.

## .the shape of the fix

derive the per-section seam from the compiled census: a section is cacheable where its whole span
sits ahead of the first variable byte (`cacheable.head`). drop the table, or keep it only as the
declared ORDER of sections. readers: `asPromptSectionRows`, `getOneCharsByCacheSeam`, the
`review._.cost` json `seam` field, and its two acceptance assertions
(`reviewCost.acceptance.test.ts:587`, `:910`).

## .why it is not done in this round

it changes the `seam` field of the `review._.cost` json contract and four readers. that is a
contract change with a ripple, so it fails the CLEAN test of
`rule.always.fix-forward-under-scouts-honor`. the cure of this route moves prompt bytes and is
measured off the census, which already reads the true seam.
