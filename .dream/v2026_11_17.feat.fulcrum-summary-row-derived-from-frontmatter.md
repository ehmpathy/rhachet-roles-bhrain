# 🌙 dream: derive the fulcrum summary row from entry frontmatter

- kind: feat
- owner: rhachet-roles-bhrain (driver)
- caught 2026-11-17

## .the cue that fired

the coverage review of `v2026_11_16.feat-disputes-reconcile-at-human-gate` 5.1 read the wish's invariant 5 line by line: *"the summary row is derived, never typed twice"*. the shipped onStop linter checks each entry's frontmatter, and no tool derives the summary.

## .the gap, precisely

- `$route/.fulcrums/inventory.of=fulcrums._.md` is still hand-typed: `case · title · rework · status · confidence`
- every one of those fields now lives in the entry frontmatter, the one home (`define.invariant.review.peer.dispute.the-fulcrum-is-the-one-home`)
- so a driver types each attribute twice, and the two copies can drift. the gate reads the frontmatter, so a stale summary misleads only a human reader. that is exactly the reader the wish protects

## .the shape of the fix

- a transformer `asFulcrumSummaryRows({ fulcrums })` over `getAllRouteFulcrums`, which renders the table
- either the linter rewrites the summary (findsert, idempotent), or `rhx route.fulcrum.get` renders it on demand and the summary file is retired
- the clamp: an entry edited to `status: ruled` changes the summary with no hand edit

## .why it is not done in this round

the six enforcers the wish lists are shipped and clamped. this is the wish's prose, not one of its enforcers, and a write path into a route artifact needs its own design call (rewrite in the hook vs render on demand). the deadline on this pr did not leave room to make that call well.
