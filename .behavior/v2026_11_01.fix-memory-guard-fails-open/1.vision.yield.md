# vision: memory.guard never halts a tool it cannot judge

## .the first act — the line that fires

one blocked call, captured verbatim. the hook command (`./node_modules/.bin/rhx memory.guard --mode hook`), in a tree where the learner role is not linked:

```
✋ ConstraintError: no skill "memory.guard" found in any linked role
...
tip: did you `npx rhachet roles link` the --role this skill comes from?
exit=2
```

(reproduced 2026-11-01 via `rhx <unlinked-skill> --mode hook`; the same lookup path the crews hit.)

⇒ **suspect 1 fires, and the mechanism is an exit-code collision.** rhx grades its own lookup fault a `ConstraintError` and exits 2. claude code reads exit 2 from a PreToolUse hook as *block*. so a hook that cannot find itself halts every `Write|Edit|Bash` call.

the other two suspects do NOT fail closed in claude code, verified by exit code:

| suspect | exit | claude code reads it as |
|---|---|---|
| absent `./node_modules/.bin/rhx` | 127 | non-block error, call proceeds |
| import rejects in `memory.guard.sh` | 1 | non-block error, call proceeds |
| hook timeout | killed | non-block, call proceeds |
| **rhx cannot find the skill** | **2** | **block** |

they still deserve a fix: each leaves a stderr that names naught about memory, and a guard whose fault is silent is a guard nobody repairs.

## .the outcome world

a crew opens a tree where the learner is not linked. before: every Bash, Write and Edit halts with a message about a skill lookup; the crew is dead in the water until a human strips the hook from settings. after: every call passes, and under each one the human sees a `memory.guard hook error` notice with one line:

```
📜 memory.guard: could not run (skill not linked in this tree); call allowed. fix: npx rhachet roles link --repo bhrain --role learner
```

the crew works on. the human knows the guard is off, why, and the command that turns it back on.

in a healthy tree, naught changes for the crew: a write into `~/.claude/**/memory/` still halts with the owl nudge, exit 2. a `grep x ~/.claude/projects/p/memory/a.md 2>&1` now passes, where before it was graded a write.

**the aha:** the guard has exactly one way to say *stop* — its own verdict. every other path out of it says *go*.

## .the contract

| situation | exit | the call | stderr |
|---|---|---|---|
| a write into native memory (Write, Edit, or a Bash redirect/tee/teesafe/cp/mv into it) | 2 | halted | the owl nudge |
| any other call the guard judged | 0 | proceeds | silent |
| skill not linked in the tree | 1 | proceeds | one line: not linked + the link command |
| cli module absent from the package | 1 | proceeds | one line: cli absent + reinstall |
| cli import or guard throws | 1 | proceeds | one line: the error message + reinstall |
| guard passes its deadline | 1 | proceeds | one line: timed out |
| empty or malformed stdin | 0 | proceeds | silent (unchanged) |

🟡 **fulcrum F1 — a fault exits 1, not 0.** the wish asks for exit 0 with a stderr line. claude code never shows a hook's stderr on exit 0 (debug log only); a non-0, non-2 exit is a non-block error that renders a `hook error` notice to the human and lets the call proceed. so exit 0 would keep the flow and lose the line; exit 1 keeps both. rework to exit 0 is clean (one constant in two files). `.fulcrums/inventory.of=fulcrums.case=F1-a-guard-fault-exits-1-so-its-notice-is-seen.md`.

### the shape

- the hook command runs the linked skill file directly, never through `rhx`'s lookup, anchored at the project root so a drifted cwd cannot unhook it:
  `f="${CLAUDE_PROJECT_DIR:-.}/.agent/repo=bhrain/role=learner/skills/memory.guard.sh"; [ -f "$f" ] && exec bash "$f" --mode hook || { echo '📜 memory.guard: …' >&2; exit 1; }`
- `memory.guard.sh` locates the cli from its own physical path (`<pkg>/dist/contract/cli/memory.js`, resolved from the file, not its link), not via a bare-specifier import resolved from the cwd.
- `memory.guard.sh` maps the node exit: `0` stays `0`, `2` stays `2`; all else becomes `1` with one stderr line that names the fault and its fix. it holds its own deadline (4s, under the hook's PT5S) where `timeout` exists.
- the verdict grades a Bash redirect by its **target**: `>`, `>>` or `>|` (with an optional `N` or `&` before it) whose target is a memory path. `2>&1`, `>&2`, `=>`, `->` are not redirects to a file. tee, cp, mv and teesafe keep their extant rule.

## .mental model

a smoke detector with a dead battery chirps; it never locks the front door. the guard's one job is to stop one act. when it cannot do that job, it says so and steps aside.

crews say *"the memory hook blocked every call"*. we say *"the guard failed closed"*. the fix makes the crew's sentence impossible.

## .evaluation

- solves the blast: the only exit-2 path left is the verdict's own `process.exit(2)`.
- pros: no dependency on `./node_modules/.bin/rhx`, no dependency on the cwd's node resolution, a named fault for each failure.
- cons: a guard that fails open is a guard that can be off unnoticed. the notice is the mitigation; it shows on every call, and only because a fault exits 1 (F1).
- edgecases: macOS has no `timeout` by default → no inner deadline there; claude code's own PT5S timeout still fails open. a cold node over 4s on a loaded grove → the guard skips that call, by design.

## .open questions & assumptions

- **[answered]** where does a hook run? in the CURRENT cwd, which drifts after a `cd` (claude code docs). so the command anchors on `${CLAUDE_PROJECT_DIR:-.}`, with `.` only for a bare shell run (tests, a human run).
- **[answered]** does rhachet write a hook command verbatim? yes — the mechanic's `bash .agent/…` entries sit as written in `.claude/settings.of.repo.json:365-489`.
- **[answered]** which suspect fires? suspect 1, via rhx's exit 2 (`.the first act`).
- **[answered]** do the driver's guards share the hazard? yes by the same mechanism; out of scope, caught as a dream.
- **[research]** is `CLAUDE_PROJECT_DIR` the tree root under the actor layout (where `.claude` links into `.agent/.actors/…`)? it is unset in the Bash tool's env, so it cannot be read from here. the check: once the new hook is installed in this tree, every call of this session runs it; a wrong value prints the fault line at once. execution confirms before it lands.
- **[research]** does an absolute `import()` of the CJS `dist/contract/cli/memory.js` expose `memoryGuard`? the integration suite's healthy-tree cases prove it.
- **[answered]** does a hook's stderr reach the human on exit 0? no — "Claude never sees stderr from a hook that exits 0", and it goes to the debug log only. a non-0, non-2 exit renders a `hook error` notice and the call proceeds (claude code docs).
- **[wisher]** F1: a guard fault exits 1 (visible notice, call proceeds) where the wish wrote exit 0 (invisible line). best-guessed exit 1; the wisher confirms at the vision approval.

## .what is awkward?

- the hook command is a shell expression, not a bare path. it must be, so the absent-skill case exits 0 with a named fault rather than bash's own 127.
- a guard that fails open trades safety for flow. the wish settles the trade; the stderr line is the price we pay to keep it honest.
