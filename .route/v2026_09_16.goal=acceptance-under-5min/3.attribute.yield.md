# 3.attribute — yield

## .the attribution, on the SERIAL run

only a serial run can attribute cost. under parallelism each file's wall clock inflates
with contention, so per-file numbers no longer sum to real work (see the trap below).

| cause | measured | share of jest |
|---|---|---|
| `npx rhachet roles link` — 322 calls × ~2.2s | **708s** | **27.5%** |
| the rest (the actual test work) | 1867s | 72.5% |
| **jest total, serial** | **2575s** | |

**the sum check** (the stone's guard): per-file times total **42m55s = 2575s** against a
jest wall of **42m59s = 2579s** → **99.8%**. the causes account for the whole.

⇒ the 2.2s/call figure is measured, not apportioned: two files that make 7 `roles link`
calls ran 28.7s with the cache off and 13.5s with it on — 15.2s over 7 calls.

## .why that one cause is 27.5% of a test suite

rhachet's `bin/run` dispatches `roles link` to `run.jit` — a full node boot of the CLI —
while only `roles boot|cost` reach the compiled bun binary. the fixtures then call it 322
times for output that is **five symlinks**, byte-identical every time.

## .the parallelism curve, measured

| workers | jest wall | speedup vs serial |
|---|---|---|
| 1 (serial, no cache) | 2575s | 1.00x |
| 8 | 710s | **3.63x** |
| 16 | 591s | **4.36x** |

⇒ real, and **sublinear**. a doubled worker count bought 1.20x. the curve bends toward an
asymptote well above the bar.

## 🔴 .the trap that fooled me — contention-inflated per-file time

per-file totals by worker count, same 117 files, same work:

| run | per-file total |
|---|---|
| serial | 42m55s |
| 8 workers | 93m55s |
| 16 workers | **154m20s** |

the work did not triple. **each file's wall clock stretches while it waits on contended
CPU**, and the total inflates with it.

I read the 8-worker figure (93m55s into 11m50s) as **7.9x parallelism** and told the
human the suite was wait-bound with headroom. it was **3.63x**. the ratio I computed put
an inflated numerator over a real denominator — a quantity that is simply void.

⇒ **a derived ratio needs both terms measured under the SAME conditions.** the honest
denominator is the serial run, and it sat on disk the whole time.

## .what the numbers say to do next

to reach a 5m00s total (≈280s of jest + ~20s build) at the measured 4.36x:

```
required aggregate work  =  280s × 4.36  ≈  1220s
current aggregate work   =                 2575s
```

⇒ **the aggregate must roughly HALVE**, on top of 16 workers. parallelism alone cannot
close it on a 4-core box — the curve already bends.

the blocks left, by size:

1. **subprocess spawn per case** — every case shells `bash → rhx → bun`; the suite does
   this thousands of times and each pays a cold binary boot
2. **`genTempDir` git cost** — 457 calls × (`git init` + 2 commits) ≈ 1,400 git spawns,
   for history most fixtures never read
3. **the long poles** — `review.join-intersect` is 5m06s serial, and becomes the floor
   once the aggregate falls far enough

## .the CI cross-check that redirected the whole diagnosis

CI shard timings, read before any local profile:

| shard | wall |
|---|---|
| the 8 files CI isolates as "longest poles" (real LLM calls) | 50–75s each |
| the 3 dynamic shards of "fast validation" files | 5m36s – 9m52s |

⇒ **the slow half was the fast-labelled half.** without that read I would have tuned the
LLM tests — 8 files that were never the problem — and left the 27.5% untouched.
