## .the gap, precisely

`jest.integration.env.ts:96` is unconditional:

```ts
const keyrackYmlPath = join(process.cwd(), '.agent/keyrack.yml');
if (existsSync(keyrackYmlPath))
  keyrack.source({ env: 'test', owner: 'ehmpath', mode: 'strict' });
```

`mode: 'strict'` calls `process.exit(2)` when any declared key is unfilled. five are —
`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `TAVILY_API_KEY`, `XAI_API_KEY`, `FIREWORKS_API_KEY`.

⚠️ **it is a GLOBAL env hook, so it fires before any test body runs.** the gate is on the presence
of `.agent/keyrack.yml`, never on whether the suite about to run wants a key.

## .the shape of the fix

⚠️ **the obvious fix has a real cost, which is why this is a dream rather than an edit.**

1. **flip to `mode: 'lenient'`.** one word, and it trades a *clear, early* failure for a *late,
   opaque* one — a suite that genuinely needs `ANTHROPIC_API_KEY` would fail deep inside a brain
   call with an auth error rather than at the door with a `rhx keyrack set` tip. that tip is real
   ergonomic value (`rule.require.errors-name-the-fix`), and a blanket flip discards it.
2. 🔴 **declare each suite's key needs, and source only those.** the strict gate stays for a suite
   that names a key, and a suite that names none runs free. it keeps both properties rather than a
   trade of one for the other — and it is the larger change, since it wants a per-suite declaration
   the harness does not have today.
3. **narrow the gate to the keys actually declared as required**, if `keyrack.yml` can express
   optional-vs-required. cheapest of the three if the manifest already supports it — **unverified**;
   the manifest was not read.

⇒ (2) is the one with teeth. (1) is a one-word change that a reviewer should refuse on its own
merits unless the late-failure cost is accepted deliberately.

### 🔴 option (1) is now MEASURED, and it is worse than this dream feared — 2026-09-04

the section below said the fix could not be tested under the condition that motivates it. it has
since been tested, by a temporary local flip to `lenient` in both harnesses, reverted the same round.

| what was run | under `lenient` |
|---|---|
| `setStoneAsPassed` × 3 suites (no keys used) | **62 passed** — previously unrunnable |
| `routeStoneSetContemplation.acceptance` (no keys used) | **13 passed** — previously unrunnable |
| `getRouteDriveBlockerMessage.integration` (no keys used) | **4 passed** — previously unrunnable |
| 🔴 `stepReview.caseBrain.claude-sonnet` (**needs** a key) | **0 passed, 0 failed, 63 SKIPPED** |

⇒ **a key-hungry suite under `lenient` does not fail late and opaquely. it does not fail at all.**
it reports 63 silent skips and a green tick.

that is strictly worse than the cost this dream predicted, and it is a `rule.forbid.failhide`
violation on its face: *"a test that skips is a lie."* the repo's own
`code.test/rule.require.failfast` names the same shape — an absent resource must fail loud, never
skip. **so `mode: 'strict'` bears real load: it is the only mechanism today that converts an absent
key into a stop rather than into 63 quiet passes.**

⇒ **option (1) is dead.** it must not be taken even deliberately, because the late failure it was
thought to trade for does not exist. option (2) is now the only candidate with teeth, and it inherits
a new requirement this measurement surfaced: **whatever removes the strict gate must also remove the
skip-on-absent-key guard inside the suites that drive a brain**, or the guarantee moves from one
silent place to another.

## 🔴 .the ordering constraint — fix this BEFORE anyone reclassifies a test

**measured 2026-09-04: ~45 plain `.test.ts` files in `src/` import `fs`.** by
`rule.forbid.unit.remote-boundaries` (ehmpathy/mechanic) every one is misclassified — a filesystem
read is a remote boundary, so each owes the `.integration.test.ts` suffix. among them are
`enumRouteGuardReviewPeerFiles.test.ts`, `computeStoneReviewInputHash.test.ts`,
`getAllStoneGuardArtifactsByHash.test.ts`, and most of `route/stones/`.

⚠️ **so a well-meant sweep to conform them would move 45 suites behind this strict gate and make
every one of them unrunnable locally.** the repo would go from "45 fs suites a developer can run in
seconds" to "45 fs suites that need five API keys they do not use."

⇒ **the divergence is currently load-carrying, by accident.** `enumRouteGuardReviewPeerFiles.test.ts`
`[case4] [t0]` is the only runnable clamp on the cross-hash glob that P2a depends on, and it runs
**because** it is misclassified.

**the sequence is therefore: fix this harness defect first, then reclassify.** either order alone
makes things worse — reclassify-first destroys local coverage, and the harness fix alone leaves a
45-file convention divergence standing.
