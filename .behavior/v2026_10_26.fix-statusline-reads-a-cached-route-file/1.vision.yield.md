# vision — the status line reads a cached route file

> the render runs when the route moves. a repaint only reads.

tasks: ehmpathy/rhachet-roles-bhrain#673, #660, and #722 (the static-file follow-up named on pr #700).

## the outcome world

### before

every repaint of every seat boots node. pr #700 made that boot cheap: a per-branch cache under
`.agent/.cache/` turns a repaint with no change into node boot plus one file read, 0.059s of cpu
(`bench.status-line`, down from 0.967s). but the floor is node boot itself, paid on every assistant
message of every seat. at 44 seats, 9 held 491% cpu on 2026-10-23.

### after

the statusLine command is a bash executable. per repaint it reads `.git/HEAD`, reads one json
file, runs a few mtime tests, and prints one field. no node, no `git`, no `jq`. the render moves to
the moments a render input is written — each of them already inside a node process (a stone set,
a bind set, a guard review round). each rewrites the status file as its last act.

### the aha

the line is a display of route state, and route state changes only when something writes it.
so the work belongs to the writer, not the watcher. one write serves every repaint of every seat
on that route until the next write. a seat that repaints 200 times between two passages pays one
render, not 200.

## the contract, testdriven

the file:

```json
// $route/.route/.status.line.json — ignored by the route's own .route/.gitignore, rewritten whole via temp + rename
{"route":".behavior/v2026_10_26.fix-…","stone":"5.1.execution.from_vision","phase":"review.peer","line":"🗿 5.1.execution.from_vision, review.peer, l1@i002 🔍"}
```

the wish's "status" is named `phase` here: in this repo a stone's *status* is its passage status
(`passed`, `blocked`, … — `define.passage-statuses`), while what the line shows is the phase
(`yield`, `review.self`, `review.peer`, `judge`, from `StatusLinePhase`) with its halt word.

the format is the writer's to fix, so the reader's parse is exact, not a json parser: one line,
`JSON.stringify` of a fixed key order, `line` last. bash matches `"line":"(.*)"}$` with `=~` and
unescapes `\"` and `\\`. a file that does not match reads as absent.

the clamp — red on today's line, green on the new — is stronger than a node count:

```
when the reader runs with PATH emptied (bash by absolute path)               [t0]
  then it prints the line — so it spawned no child process at all            [t0]
  (today's `node -e …` command fails here: node is not found)
```

the line, per state:

| state | stdout |
|---|---|
| unbound | `` (blank, as today) |
| bound, fresh | `🗿 5.1.execution.from_vision, review.peer, l1@i002 🔍` (byte-equal to today) |
| bound, stale | `🗿 5.1.execution.from_vision, review.peer, l1@i002 🔍 · stale, rhx route.drive` |
| bound, absent or unreadable | `🗿 status unknown, rhx route.drive` |
| two binds on the branch | `🗿 two routes bound to this branch, rhx route.bind.get` |

the settings block:

```json
"statusLine": { "type": "command", "command": "bash <the driver's route.status.line.sh>", "padding": 0, "refreshInterval": 60 }
```

- `refreshInterval: 60` is the wish's "at most once a minute": an idle seat re-reads within a
  minute, so a write made by another seat or a background guard shows with no new message
- stale = any render input newer than the file, by bash `[[ a -nt b ]]` (a builtin, no process).
  the inputs are the `.route/` ledgers the line reads: `passage.jsonl`, `reviewPeerMeters.jsonl`,
  the bind flag, each `*.guard.promise.*.md`. the `$route` dir mtime is left out: a yield file is
  no render input (the next stone comes from `passage.jsonl` alone), so a new yield never marks
  the line stale; a `.stone` added or removed goes through `route.stone.add` / `route.stone.del`,
  which become writers too

## mental model

- **to a friend:** "the status bar used to ask the route what was up, every time it redrew. now
  the route posts a note when it changes, and the status bar reads the note."
- **analogy:** a departures board. the airline posts a change; the board does not phone the gate
  each second.
- **their words vs ours:** they say "the status bar", "it lags", "it is stuck". we say "status
  line", "stale", "the status file". the stale suffix names the fix, `rhx route.drive`.

## evaluation

| goal (wish) | met by |
|---|---|
| route.drive / stone set writes a small json beside the route | every render-input writer, plus `route.drive`, writes `$route/.route/.status.line.json` |
| the current stone, its status, when written | `stone`, `phase` fields (status → phase, see the contract); when written = the file's mtime (awkward #2) |
| read at most once a minute, no node per repaint | the bash reader + `refreshInterval: 60`; the empty-PATH clamp proves zero child processes, node included |
| stale or absent reads as such; the next route.drive refreshes | the `-nt` stale test, the absent line; both name `rhx route.drive` |
| the same stone and status as the old line, in a snapshot | the writer calls `stepRouteStatusLine`, so `line` is the old render byte for byte |

**pros**
- the per-repaint floor drops from node boot (0.059s) to a bash start — expected in
  milliseconds, to be measured by a zero-node arm added to `bench.status-line`: the last order of
  magnitude pr #700 could not reach
- cost scales with route writes, not seats × repaint rate
- the freshness test pr #700 kept in node (its fulcrum F2: "pure sh freshness is fragile") becomes
  a handful of `-nt` builtins over the `.route/` ledgers the render reads

**cons**
- a `.stone` file edited by hand (under a `route.mutate` grant) is not watched; the line catches
  up at the next write or drive. rare, and the same blind spot pr #700's fingerprint has for edits
- a bind flag removed by hand from a multi-bound branch leaves `two routes bound` on the line until
  the next write or drive: the reader trusts a fault record and runs no stale test on it
- the branch → flat-name rule (`sanitizeBranchName`) gains a bash twin that can drift
- bash becomes a runtime dependency of the line; it already is one for every claude hook here.
  macOS ships bash 3.2, so the reader holds to 3.2: `[[ ]]`, `=~`, `-nt`, `${x//a/b}`, `read` —
  no `mapfile`, no `${x,,}`, no associative arrays, no `$EPOCHSECONDS`
- `-nt` reads mtimes at the filesystem's resolution. on a 1s-resolution fs, an input written in the
  same second after the status file is not seen as newer; the next write heals it. ext4 and apfs
  carry nanoseconds

**edge cases, and the pit of success**
- a torn write: temp + rename, so a reader sees the old file or the new one. one that still fails
  to parse reads as absent (inventory case 7), never a blank
- a status write fault (ENOSPC, EACCES): the move it follows still lands; one stderr row names the
  code, the path, and the fix; the line reads stale (case 5)
- two writers race on one route (a guard round and a stone set): if the older render renames
  last, the file holds an older line with the newest mtime, and the stale test is blind to it.
  the cure: each writer, after its rename, re-checks the ledgers it rendered from and renders
  again if any grew since its render began, so the last writer to finish holds the newest state
  (inventory case 16, fulcrum F7)
- a detached HEAD or no `.git`: no branch → blank, as unbound. no `git` fallback spawn
- a multi-bind: today a loud fault (exit 2); the reader cannot glob the repo to detect it, so the
  writer detects it (it already runs the lookup) and writes the fault line into the file
- an unbound seat: no per-branch pointer, so the line is blank, with no repo walk (question 1)

## open questions & assumptions

assumptions, each to verify in execution:
1. every render input is written by node via one of: `setPassageReport` (the one choke point of
   `passage.jsonl`), `setRouteStoneGuardReviewPeerMeter`, the promise write in `setStoneAsPromised`,
   `setRouteBind` / `delRouteBind`, and `route.stone.add` / `route.stone.del` for the stone set. a
   hook at each keeps the file current; the stale test covers the rest (hand edits, crashes)
2. (verified) the file needs no new gitignore: `findsertRouteGitignore` writes
   `$route/.route/.gitignore` as `*` minus `passage.jsonl` and `.bind.*`
3. the command runs from the project root, as pr #700's entry assumes
   (`src/contract/cli/route.status.line.ts`). the docs note a session's cwd can drift from
   `workspace.project_dir`; the reader may anchor at that stdin field if a drifted cwd shows up
4. each writer writes the status file *after* the input it follows (passage, meter, bind), with
   the temp file in the same dir, so the rename is atomic and the mtime order is true
5. the wish names two writers (`route.drive`, the stone set); the vision adds the guard's review
   rounds, the promise write, and the bind ops — inferred, not said — because without them the
   review tick (`l1@i002` → `l1@i003`) and a bind change would read stale until the next drive

open questions, triaged:
1. [settled] **where does the reader find the file?** beside the route, at
   `$route/.route/.status.line.json` — ruled by the director (fulcrum F4, option a), since the wish
   states that placement. the bind lookup is a repo-wide `**/.route/` glob that bash cannot prune,
   so a per-branch pointer at pr #700's fixed cache path (`.agent/.cache/…/branch=<flat>.json`)
   names the route, and the reader follows it to the file beside the route
2. [answered] **does pr #700's node entry retire?** no — by logic: a seat whose settings predate
   the upgrade still runs `node -e …` until `rhx init` rewrites its statusLine, and the legacy
   `cli/route` export and `route.status.line.show` call it. the entry stays and keeps its contract.
   its per-branch cache path now holds the pointer to the route (question 1, fulcrum F5)
3. [answered] **does a new yield file mark the line stale?** no — by code: `computeNextStones`
   picks the next stone from `passage.jsonl` alone (`artifact.passage`), and the phase reads
   blockers, meters, and promises, never yield files. so the stale test watches the `.route/`
   ledgers, not the `$route` dir mtime (fulcrum F6)
4. [research] **what does a bash start cost per repaint?** a zero-node arm in `bench.status-line`,
   measured beside pr #700's 0.059s node arm, on this box
5. [research] **does the bash twin of `sanitizeBranchName` agree?** a parity test over a branch
   corpus (slashes, unicode, doubled and edge specials), ts against bash

## what is awkward?

1. **the bash twin of `sanitizeBranchName`.** one rule, two languages. a parity test over a branch
   corpus (slashes, unicode, doubled specials) clamps it; the duplication stays real
2. **"when it was written" as a field.** `rule.forbid.timestamps-in-route-artifacts` forbids a time
   field in a route artifact, and bash cannot compare an iso string without a process. so the
   file's mtime carries it, and the json holds none. the wish names the field; the vision drops it
3. **"beside the route" fights the cheap read.** the reader must find the route before it can find
   the file, and the only repo-free way to find the route is a fixed per-branch pointer (question 1)
4. **pr #700's cache shipped a day ago.** its fingerprint, age rule, and cancel grace were the right
   step; this vision retires most of it from the hot path
